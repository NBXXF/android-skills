# 网络请求规范

## 0. 使用方式

1. 只要任务涉及网络请求、接口定义、请求/响应模型、JSON 解析、API 封装或网络层改造，就必须先按本规则检查。
2. 本规则优先约束接口声明方式、返回类型优先级、模型命名和 JSON 边界，不负责业务编排、页面状态或数据仓库设计。
3. 网络相关的跨层结构仍需遵守 `aaaaa-xxf-coding-arch`、`aaaaa-xxf-class-declaration-guidelines`、`aaaaa-xxf-code-reviewer` 等上层规则。

## 1. 核心原则

1. 网络层必须以 Retrofit 的接口声明方式为主，使用明确的 `ApiService` 接口描述 HTTP 能力。
   - 声明式的含义是：看到方法签名就能读出请求语义、输入、输出和副作用。
   - 不要把 HTTP 行为藏进统一入口，再通过参数分支决定实际动作。
2. 接口必须满足 RESTful 资源设计，按资源、路径、方法和状态表达能力组织，不得写成“万能接口”。
   - 路径要表达资源，而不是表达流程步骤。
   - 方法要表达操作类型，而不是表达内部实现细节。
   - 同一个接口方法只负责一个资源语义，不要同时承担多个业务动作。
3. 不得把网络层再包装成二次 client、万能 `NetworkManager`、统一 `ApiClient`、`RequestCenter`、`HttpClientManager` 之类的黑盒入口。
   - 业务层不应该知道“先拿 client 再发请求”的抽象。
   - 调用方应直接依赖声明式 API，而不是依赖某个自造 client 的内部状态机。
4. Retrofit 生态已经足够成熟，能解决的能力必须直接下沉到底层，不允许再用业务封装去重复造轮子。
   - token 交换、token 刷新、token 注入，优先交给 `Authenticator`、拦截器、拦截链或统一凭证仓库。
   - 401 / 鉴权失败，优先在网络层统一处理，不要把它伪装成业务成功/失败分支散落到上层。
   - 重试、退避、超时、取消、幂等控制，优先交给网络策略，不要在业务层重复实现。
   - 公共 header、公共 query、公共参数注入，优先在拦截器或 request factory 中统一完成。
   - 日志、埋点、链路追踪、脱敏，优先在底层统一配置，不要在每个调用点单独拼装。
   - gzip、缓存、压缩、编码、解码、SSL/TLS、证书校验、网络安全配置，优先视为平台能力，而不是业务功能。
5. 以下能力一律视为底层职责，不得在业务层再造一层 `client` 概念。
   - token 交换、token 刷新、token 注入
   - 401/鉴权失败处理
   - 重试、退避、超时、取消
   - 公共 header、公共 query、公共参数注入
   - 日志、埋点、链路追踪、脱敏
   - gzip、缓存、压缩、编码、解码
   - SSL/TLS、证书校验、网络安全配置
6. 上述能力应由 Retrofit + OkHttp + converter + call adapter + interceptor + authenticator + DI 等生态组件解决，而不是业务层自定义 client。
   - 如果当前工程已经支持这些能力，就只做配置，不额外包一层适配器再转一遍。
   - 业务代码只关心“发什么请求、拿什么结果”，不关心“底层如何换 token 或怎么重试”。
7. 任何试图把这些底层能力重新打包成“统一请求中心”“网络助手”“数据请求管理器”的设计，默认判定为反模式。
   - 这种设计通常会把协议能力、状态管理和业务流程揉成一个黑盒。
   - 一旦出现黑盒，后续很容易把网络边界改坏。
8. 不得为了“接口简单”阻断响应式编程；`Flow` 和 `Observable` 属于一等公民，必须保留多次发射、first cache、next 多次、流式订阅和可组合性。
   - 如果数据天然会经历加载中、局部更新、最终完成等多个状态，就应该保留响应式流。
   - 不要为了统一成一次性结果，把多阶段数据源压成单个返回值。
9. 只要底层框架支持，响应式返回就应该优先保留，不得强行改写成一次性结果、回调结果或命令式拉取模型。
   - `Flow` / `Observable` 允许用于单次和多次发射场景。
   - 不能把“只发一次”当成否定响应式编程的理由。
10. `SSE` 请求本身就是持续多次响应的协议语义，必须被当作流式场景处理。
    - `SSE` 天然会反复推送事件，不是一次性请求。
    - 任何把 `SSE` 包成单次返回、一次性回调或“请求完成即结束”的封装，都会直接破坏协议语义。
    - `SSE` 场景必须保留多次发射能力、事件增量处理能力和持续订阅能力。
10. 禁止使用 `org.json` 直接拼装、遍历或解析请求/响应。
    - `org.json` 只会让协议代码变成易碎的字符串和字段名操作。
    - 主链路应使用统一的序列化/反序列化机制。
11. 请求和响应都必须使用明确模型，不允许用裸 `Map`、裸 `String`、`Bundle`、`JSONObject` 作为主链路网络载体。
    - 数据结构必须能表达字段含义、可空性和兼容性。
    - 如果协议变化，需要改 DTO，不要在调用点临时补丁。

## 2. 接口声明

1. 所有对外 HTTP 能力优先放在 Retrofit `ApiService` 中声明。
   - 新增接口先想“资源是什么”，再想“方法怎么写”。
   - 不要先设计一个 client 再往里面塞若干随便命名的方法。
2. 每个方法都必须表达明确的资源语义，避免 `doAction`、`requestXXX`、`sendXXX`、`handleXXX` 这类过程式命名。
   - 方法名应能对应资源行为，而不是内部脚本步骤。
   - 一个方法只做一件事，返回结果也只表达这一件事。
3. HTTP 方法必须与语义匹配：
   - `GET` 读取资源
   - `POST` 创建或触发资源行为
   - `PUT` / `PATCH` 更新资源
   - `DELETE` 删除资源
4. 接口路径、query、path 参数、header 参数和 body 必须能从方法签名直接看出，不得依赖隐藏约定。
   - 看到签名就能判断请求发往哪里、带了什么参数、会修改什么资源。
   - 如果需要阅读大量注释才能理解签名，这个接口就还不够清晰。
5. 一个接口方法只表达一个稳定契约，不得把多个业务动作塞进同一个“万能”入口。
   - 万能入口会让返回语义失真，也会让错误处理和缓存策略失去边界。
   - 如果确实有多个资源动作，就拆成多个资源方法。
6. 复用公共头、公共鉴权和通用协议，不通过聚合万能接口实现，而通过拦截器或底层统一配置实现。
   - 例如 token、UA、locale、traceId 之类公共字段，不应由业务方法一条条手动塞。
   - 这类规则应该是网络层配置，而不是接口签名技巧。
7. token 注入、refresh、401 处理、请求重放等能力，不得散落到 repository/service/viewmodel，必须放在底层 HTTP 生态配置中。
   - repository 只负责数据流转，不负责认证状态机。
   - service 只负责业务编排，不负责网络握手细节。

## 3. 返回类型优先级

1. 默认优先返回 `Flow<xxx>`。
   - 如果调用方需要监听多个状态变化，`Flow` 通常是首选。
   - 它适合单次结果、分页流、缓存后刷新、持续监听等不同场景。
2. 其次使用 `RxJava Observable<xxx>`。
   - 如果工程已有成熟 Rx 链路，`Observable` 仍然是合法的一等选择。
   - 不要因为“现在流行 Flow”就强行否定既有 Observable 生态。
3. 再其次使用 `suspend`。
   - 仅适合明确的一次性请求语义。
   - 如果后续可能演进成多阶段/多次发射，不要先写死成 `suspend` 再返工。
4. `Call<xxx>` 只作为最低优先级兼容方案。
   - `Call` 只适合历史兼容或极少量边界场景。
   - 新接口不要默认回到 `Call` 风格。
5. 只要框架和当前工程能力已支持，新增接口默认选择更高优先级的返回形式，不要为了“省事”退回到更低阶写法。
6. 不新增回调式网络 API；如果已有旧式接口，优先按当前工程可接受的最高优先级逐步迁移。
7. 返回类型选择只影响声明式接入方式，不改变“底层解决共性能力、业务层只描述资源契约”的原则。
8. `Flow` / `Observable` 允许用于单次和多次发射场景，不得被降级成“只能返回一个结果”的假响应式接口。
   - first cache、next 多次、局部更新、状态流转都应该保留在流里表达。
   - 不要为了和传统接口形式看齐，把流改成只会吐一次值的薄包装。

## 4. 模型约束

1. 请求模型和响应模型都必须使用 DTO。
   - 请求 DTO 表达“发什么”，响应 DTO 表达“拿什么”。
   - 两者都属于协议层对象，不是 UI 对象，也不是数据库对象。
2. DTO 命名必须以 `DTO` 结尾，不得混用 `Entity`、`Model`、`Bean`、`Param`、`Req`、`Resp`、`VO` 作为网络主模型后缀。
   - 统一后缀可以让调用方一眼看出它是传输模型。
   - 不要让同一个概念在网络层被多套命名切来切去。
3. DTO 只描述接口契约，不承载 UI 状态、不承载页面逻辑、不承载数据库持久化语义。
   - DTO 只反映协议字段，不反映展示状态。
4. 请求 DTO 和响应 DTO 应显式区分，但都必须保留 `DTO` 后缀。
   - 同名不同方向时，仍然建议通过前缀、资源名或上下文区分。
5. 网络层输入输出必须落到明确对象，禁止使用原始 JSON 字符串作为跨层传输载体。
   - JSON 字符串只应存在于序列化边界，不应成为业务层载体。
6. 复杂字段映射、默认值修正和协议兼容处理应在模型边界或 mapper 层完成，不要散落在调用点。
   - 兼容修正集中做，后续协议变化时才知道改哪里。
7. 请求模型和响应模型必须与接口资源语义一致，避免用 `client` 视角重命名 DTO 或把协议字段伪装成业务对象。
   - DTO 命名应按资源语义，而不是按实现方式命名。

## 5. JSON 规则

1. 禁止使用 `org.json` 作为默认 JSON 处理方案。
   - 不要在业务代码里依赖 `JSONObject` / `JSONArray` 的动态字段读写。
2. 不要在业务代码里手写 `JSONObject` / `JSONArray` 的读写流程来拼接主链路请求或解析响应。
   - 这类写法会把协议演进成本放大到每个调用点。
3. JSON 的解析和序列化应由项目统一的 converter、serializer 或底层框架承担。
   - 底层统一解析比散落在业务层更可控，也更容易测试和替换。
4. 如果协议字段、枚举值或错误码需要兼容，优先通过 DTO、adapter、interceptor 或 mapper 解决，不要靠外层临时字符串处理。
   - 协议兼容应该在边界层收敛，不要把字符串修补传到上层。
5. 任何 JSON 兼容修补都应留在协议边界，不要在业务层写二次解析或二次封装。
   - 业务层只处理对象，不处理原始 JSON 结构。

## 6. 设计边界

1. 网络层只负责协议接入和数据搬运，不负责页面展示、不负责业务决策、不负责流程编排。
   - 网络层不是页面状态机，也不是业务流程编排器。
2. 业务规则、状态流转、多数据源组合仍应落在 service / repository 等既有分层中。
   - repository 负责取数和存数，service 负责业务判断。
3. 不要把网络层扩展成“带业务逻辑的 client wrapper”。
   - wrapper 一旦开始决策，就会把职责边界打碎。
4. 网络相关的可复用逻辑如果是通用协议能力，优先下沉到底层统一设施，而不是复制到每个调用点。
   - 复用能力应是统一设施，不是每个业务模块自建一个版本。
5. 如果接口设计已经无法用资源和 DTO 表达，先重构契约，不要继续堆包装层。
   - 契约不清晰时继续写代码，只会把问题放大。
6. 业务层只允许依赖声明式 API，不允许依赖某个自造 client 的调用顺序、内部状态机或重试状态。
   - 业务层如果知道内部重试步骤，说明职责已经串了。

## 7. 快速检查清单

- [ ] 接口是否使用 Retrofit `ApiService` 直接声明？
- [ ] 每个接口是否都是 RESTful 资源语义，而不是万能入口？
- [ ] 返回类型是否按 `Flow > Observable > suspend > Call` 的顺序选择？
- [ ] 请求/响应是否都使用 `DTO` 命名？
- [ ] 是否完全避免了 `org.json`？
- [ ] 是否没有把通用能力包装成新的 client 黑盒？
- [ ] 是否没有把 token、401、重试、header、日志等能力再包进业务 client？
- [ ] 是否没有用裸 JSON 字符串、裸 Map 或原始回调跨层传递？
- [ ] 认证、日志、重试、header 等共性是否已在底层解决，而不是在上层重复封装？
- [ ] 是否没有阻断响应式编程，是否保留了 `Flow` / `Observable` 的多次发射能力？
- [ ] 响应式接口是否保留了 first cache、next 多次和流式订阅语义？
- [ ] `SSE` 场景是否仍然保持多次响应语义，没有被压成一次性请求？
