# 发布库职责收尾六维度清单

本文件是 `aaaaa-xxf-maven-library-release-guard` "职责收尾与强制确认"一节的执行细则。发起强制确认前必须完成本清单自查。

## 总则

1. 库的本质是解决一类问题，不是解决一个问题。库是基础建设：API 建模问题域，不镜像第一个调用方的现场。设计深度决定库能服务多少接入方、活多久。
2. 禁止打补丁式演进：为当前业务方加特判、按某个接入方形态写死行为、用布尔开关和分支堆需求，都是在把库退化成补丁集合。需求必须以抽象或扩展点承接。
3. 对外就是一个沙盒：业务方只管安心接入。对标成熟三方 SDK 的接入体验——一个显式入口、一份稳定契约、同主版本内无感升级；不读源码能接入，不看内部能排障（日志与错误自解释）；库的任何内部失败都在库内兜底降级，不允许 crash 宿主。
4. 接入与维护成本是最终验收标准：业务方接入步骤更少、前提更少、坑更少，才算职责到位。把自己的复杂度转嫁给接入方（隐式初始化顺序、隐藏前提、让接入方绕已知缺陷）都算未做到位。
5. 六个维度按"是否被本次改动触及"裁剪执行：被触及的维度做全量自查；未触及的维度在自查结论表里逐条写明理由，禁止整段跳过不留痕。
6. "触及"按影响面判定，不按改动文件数：只要改动的公共 API、依赖、初始化路径、线程模型、Manifest、资源或发布配置可能影响某维度，该维度即视为触及。纯升版本、纯文档改动允许多数维度"未触及"，但理由必须落在表里。
7. 每个维度分"硬性项"（未通过即未做到位，进入强制确认前必须补齐或列为残留）和"自查问题"（用于发现硬性项是否真的成立）。硬性项要证据（命令输出、产物、文件、行号），不接受"应该没问题"。

## 维度一：契约与 API 设计（设计角度）

对外契约是 SDK 的第一产品。接入方先接触的不是实现，是签名、参数、回调和默认行为。

硬性项：

1. 公共暴露面最小：新增 public/protected 符号逐个确认"接入方必须感知"，能 internal/private 的一律不公开。
2. 公共签名不泄漏实现：返回值、参数、回调不出现内部实现类、内部包类型或三方库具体类型，否则接入方被迫依赖这些细节，升级即碎。
3. nullability 明确：Kotlin 公共 API 不留平台类型裸奔；Java 公共 API 的可空语义明确（注解或文档）。
4. 默认值安全：不传可选参数 = 功能关闭/no-op/空实现，不抛异常、不发请求、不读磁盘。
5. 错误语义一致：失败路径（抛异常 / 返回 null / 回调错误 / 静默降级）全库统一为一种约定并写进文档；不得有的 API 抛异常、有的静默吞掉。
6. 线程契约明确：公共 API 允许在哪个线程调用、回调在哪个线程派发，文档写明且实现一致。
7. 面向一类问题建模：不得为单个业务方的当前场景新增参数、分支或特判；一个参数只为一个调用方服务的，必须重新抽象或移入业务方。

自查问题：

1. 接入方只看签名和文档，能否不读实现就正确使用？最容易误用的参数是哪个？有没有防御或文档提示？
2. 新增回调/监听是否说明一次性还是可多次、是否必须注销、主线程还是后台派发？
3. 同一能力是否存在两套入口（如 suspend 版和回调版）？行为是否一致？
4. 半年后再看，这个 API 还适用于第二、第三个接入方吗，还是只服务于今天这个？

典型反例：

1. 公共方法返回内部 `ResultImpl`，接入方升级时因传递依赖缺类抛 `NoClassDefFoundError`。
2. 必须先 `setDebugMode(true)` 才能避开 crash，默认路径从未被测试。
3. 为 A 业务方加 `enableXxFix` 布尔参数，半年后 API 挂着 8 个无人敢动的开关。

## 维度二：架构与依赖边界（架构角度）

分层与职责边界的完整判定读 `aaaaa-xxf-library-design-rule`；本维度在收尾时核对发布相关的硬性项。

硬性项：

1. 分层与依赖方向不回流：api 不依赖 runtime/core 实现；core 不依赖宿主入口；契约、核心逻辑、运行接入继续混在一个模块且本次改动还在往里堆时，必须提示拆分，不得顺势加码。
2. 依赖声明与暴露一致：出现在公共签名里的类型，其所属依赖必须 `api`；仅内部使用必须 `implementation`；可选集成必须 `compileOnly` 配运行时探测降级。
3. POM 传递树完整且最小：接入方只依赖本坐标即可编译并运行，不缺运行时依赖；也不为省事把重依赖 `api` 透出，强加给所有接入方并锁死其版本。
4. 初始化显式可控：init 入口幂等（重复调用不 crash、不重复副作用）；不强制宿主继承指定 Application；若用 ContentProvider 自动初始化，必须文档声明并给出关闭方式。
5. Manifest 干净合并：新增 authority、FileProvider、permission、resource 前缀不与常见宿主冲突；库内权限必要性按 `aaaaa-xxf-google-play-compliance-gate` 复核。

自查问题：

1. 下游新增这一个坐标后，第一次调用能否直接成功？还缺什么？
2. 哪些依赖是"所有接入方都需要"，哪些是"用到某能力才需要"？后者是否已 optional？
3. 本次新增代码放对了层吗？三个月后再加功能会不会被迫跨层引用？
4. 库内是否存在两个模块对外暴露同名/同义入口，接入方不知道该依赖哪个？

典型反例：

1. POM 缺 runtime-only 依赖，接入方运行时 `NoClassDefFoundError`。
2. 库把 Gson/OkHttp 用 `api` 透出，接入方被迫接受版本并被锁死。
3. 为自动初始化注册 ContentProvider，宿主启动耗时无故增加且无法关闭。

## 维度三：性能与资源（性能角度）

涉及 UI 渲染、启动、主线程、图片、下载/网络、数据库热路径的改动，联动 `aaaaa-xxf-android-performance-gate` 执行其门禁。

硬性项：

1. 初始化路径轻：init 同步路径不做磁盘 IO、网络、大对象反序列化、全量配置解析；能延迟的延迟到首次使用。
2. 增量可知：本次改动对 AAR 体积、方法数、传递依赖的增量已测量或估算；新增重依赖必须说明理由和替代方案。
3. 资源有界：新增缓存有上限与淘汰策略；新增线程/线程池有命名、有界、可关闭。
4. 可注销：新增监听/回调注册必有对应注销；不超出声明周期持有 Activity/View/Context。
5. 热路径干净：高频调用路径无逐次反射、逐次正则编译、逐次重复 JSON 解析、逐次大对象分配。

自查问题：

1. 接入方在 `Application.onCreate` 里同步调 init，冷启动增加多少时间？低端机最坏情况是什么？
2. 弱网或无网时初始化是否阻塞、超时多久？
3. 宿主退后台/进程低内存时，库的后台任务和缓存如何让步？

典型反例：

1. init 里同步读加密配置并全量解密，低端机冷启动卡顿。
2. 网络回调注册后无法注销，Activity 泄漏。
3. 每次调用都 `Pattern.compile` 同一个正则。

## 维度四：宿主解耦（解耦角度）

库的价值在于"任何宿主都能接"。对宿主的每一个假设都是接入成本和事故来源。

硬性项：

1. 不假设宿主：不引用、不反射宿主包名、宿主类、宿主 BuildConfig、宿主资源 id；不假设宿主一定初始化过某个三方库。
2. 宿主能力注入：Context（优先 Application）、logger、executor、图片加载器等宿主能力通过参数/接口/lambda 注入，不抓全局单例，不自造全局状态。
3. 重集成依赖 optional：Gson/Moshi、OkHttp、Coil 等集成依赖用 `compileOnly` + 运行时探测缺省降级；能力不可用时功能关闭或降级，不 crash。
4. 日志走门面：库内日志经注入回调或统一日志门面输出（按 `aaaaa-xxf-coding-style` 使用 `com.xxf.log` 扩展 API），不直接硬编码系统日志或 println 把噪声打进下游发布版。
5. 调试/环境开关来自宿主运行时注入（对应 SKILL"使用宿主运行时事实"一节），不落在库内编译常量。
6. 回调默认 no-op：不强制接入方实现接口才能使用基本能力。
7. 异常不外溢（沙盒边界）：公共入口对内部异常兜底——失败降级、记录、按契约返回错误语义，不把内部异常直接抛进宿主调用栈；异步与回调路径同样不得让未捕获异常落到宿主线程。
8. 不污染宿主环境（沙盒边界）：不向宿主注入未声明的全局状态；线程带库前缀命名且可关；不注册文档未声明的组件；库的存在不给宿主带来可感知的行为变化以外的副作用。

自查问题：

1. 换一个全新空壳工程，只加这一个坐标，几步能跑起来？有没有文档之外的隐式前提？
2. 库的行为是否依赖"宿主也接了我们另一个库"这类隐式顺序？
3. 宿主多进程时，库在每个进程的初始化与状态是否正确、可控？
4. 库内部任何一处失败（磁盘满、解析失败、网络异常、依赖缺失），宿主最坏体验是什么——crash、ANR，还是功能静默降级加可排查日志？

典型反例：

1. 库里 `Class.forName("com.host.app.BuildConfig")` 判断宿主是否 debug。
2. 日志直接 `Log.d` 混入宿主发布版日志，无法关闭。
3. 必须先初始化另一个兄弟库才能用本库，文档没写。
4. 库内 JSON 解析异常直接上抛，宿主在主线程 crash。

## 维度五：设计原则（设计原则角度）

硬性项：

1. 单一职责：一个 Maven 坐标一个能力，一句话能说清本库职责；本次改动没有把第二个不相关职责塞进来。
2. 解决一类问题：公共 API 和内部结构面向问题域通用解，不含按调用方枚举的 `if/else` 特判、写死的业务参数、只服务单个业务的分支。
3. 扩展开闭：预期扩展点以接口/注册器/插件提供，接入方不改库源码、不继承内部类即可完成常见定制。
4. 最小惊讶：API 无隐藏副作用——初始化不偷偷发网络请求、不静默写磁盘、不静默采集上报。
5. 库内一致：新增 API 的命名、风格、错误处理与库内既有约定一致，不出现两套并存。
6. 版本语义：破坏性变更升主版本并写迁移说明；同一主版本内不打破二进制兼容承诺。
7. 不重复造轮子：仓库/团队已有同等公共能力时优先合并复用，不新增平行实现制造选择困难。

自查问题：

1. 这次改动是在扩展一类能力，还是在给库加第二个身份、给某个业务开小灶？
2. 后续同量级需求再来一次，是加扩展点就够，还是又要改核心代码？
3. 新增能力是否应该属于另一个已有库/另一个坐标？
4. 接入方会问"为什么这两个 API 风格不一样"吗？

典型反例：

1. `if (hostPackageName == "com.x.app")` 特判某业务方。
2. "工具库"里出现网络请求和页面跳转，坐标名与内容不符。
3. 同一功能 `init(context)` 与 Builder 两套入口并存且行为不一致。

## 维度六：发布工程（收尾角度）

硬性项对应发布动作本身，缺一即未做到位：

1. API 二进制兼容：新增/变更公共 API 有安全默认值；删除或变更已发布符号有全仓调用方证据，或已加 `@Deprecated` 加迁移说明。
2. 文档同步：README、接入文档、变更记录已更新（结构按 `aaaaa-xxf-readme-docs`）；破坏性变更写明迁移步骤；标准接入步骤数明确。
3. 混淆规则同步：新增注解同步维护 `consumer-rules.pro`，下游 minify 后仍可解析；细则见 [obfuscation.md](obfuscation.md)，涉及反射/序列化时按 `aaaaa-xxf-code-shrinking-guard` 完成 R8 门禁。
4. demo/sample：有接入示例的库，demo 已同步新 API 并编译通过。
5. release 变体验证：release unit-test、release AAR 字节码检查、宿主集成编译至少完成一项且覆盖本次改动。
6. 遗留问题：未解决的 TODO、已知缺陷、临时方案已明确记录在案，不以"应该没问题"沉默发布。
