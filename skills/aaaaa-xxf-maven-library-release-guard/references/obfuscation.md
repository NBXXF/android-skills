# Android 混淆注解与规则

## 适用范围

当目标模块是 Android Library/AAR，且会经过 R8/ProGuard、发布给其他工程消费，或存在反射、序列化、JNI、按字符串查找类名/成员时，必须同时检查：

- 源码中的混淆注解。
- `proguard-rules.pro`。
- `consumer-rules.pro`。
- 发布脚本里注入的额外 `-keep` 规则。

## 核心原则

1. `@Keep` 只是源码标记，不是规则本身。
2. 只有自己的源码可以直接加注解。
3. 第三方库不能改源码时，必须在 pro 规则里显式写 `-keep`。
4. 不能因为补了注解就删掉已有 pro 规则。
5. 对外发布的 AAR，既要保证本模块自身可用，也要保证下游消费后仍然保留需要的符号。

## 常用注解

- `@Keep`：保留类、方法或字段，避免被移除或重命名。
- `@KeepName`：尽量保留名称，但不阻止移除未使用代码。
- `@KeepClassMembers`：保留类内成员，类名可继续混淆。
- `@KeepClassMemberNames`：保留成员名称，允许成员被移除或类名混淆。

## 何时补注解

优先给自己的源码补注解，适合这些场景：

- 反射调用的入口类或成员。
- JSON 序列化/反序列化模型。
- JNI 暴露方法。
- 依赖固定类名或成员名的框架接入点。

如果是可发布 Android Library，还要同步判断是否需要 consumer 规则，因为下游工程只拿到 AAR，不一定能看到你的注解意图。

## 何时补 pro 规则

以下情况必须写规则，而不是只靠注解：

- 第三方依赖的类、方法、字段需要保留。
- 下游工程消费 AAR 时必须保留某些 API。
- 需要保留构造函数、字段、泛型签名、注解或特定成员集合。
- 需要控制 class 名、member 名、或成员是否被裁剪的精确行为。

常见写法示意：

```pro
-keep class com.example.MyClass { *; }
-keepclassmembers class com.example.MyClass { <fields>; }
```

## Android Library 额外要求

- `proguard-rules.pro` 和 `consumer-rules.pro` 都要保留并持续维护。
- 新增注解后，检查对应规则是否仍然覆盖发布路径。
- 如果库里已经有固定规则，先改规则再考虑是否补注解，不要反过来只补注解。
- 字段、构造函数、序列化签名等敏感位置，不能默认认为 `@Keep` 一定足够。

## 检查清单

- 目标符号是否由自己控制源码。
- 是否存在下游 AAR 消费场景。
- 是否需要保留名称、成员、字段、构造函数或签名。
- 注解和 pro 规则是否同时存在且逻辑一致。
- release 产物里关键类是否仍可按预期反射、序列化或初始化。
