# 变体/马甲包上架合规:差异化与触发词治理

> 定位:让每个变体成为**真实差异化的合规产品**,避免被商店/广告平台的自动化系统**误判**
> 为克隆或重复内容。本文不做、也不教任何"向审核隐藏内容"的做法——规避审核(审核期隐藏、
> 过审后切换、加密触发词躲避机审)违反 Google Play「Deceptive Behavior / Repetitive Content」
> 政策与国内应用商店审核规则,结果是全家桶下架、账号连坐。真违规的内容,唯一正确路径是改掉。

## 一、平台如何识别"同一个包的马甲"(公开机制)

理解这些维度不是为了"伪造差异骗过检测",而是知道**真实差异要落在哪些维度上**:

| 维度 | 具体信号 |
|---|---|
| 签名/账号 | 签名证书指纹、证书主体、开发者账号关联 |
| 包身份 | applicationId、版本历史、上架素材(图标/截图/描述)相似度 |
| 代码相似度 | DEX 结构、类/方法签名分布、第三方 SDK 组合清单 |
| 资源相似度 | 图标/主题/启动页/文案资源哈希,strings 内容 |
| 清单特征 | 权限组合、组件声明模式、meta-data、deeplink scheme |
| 行为特征 | (广告平台)设备指纹采集调用组合、网络行为、SDK 初始化序列 |

结论:**真实差异**(品牌、功能集、文案、权限、素材)会自然改变以上全部维度;
**换皮不换魂**(同一产品只改图标文案重复上架)无论怎么处理都会在行为/代码层露馅,
且本身就是政策违规,不要走这条路。

其中最"藏不掉"的一维是**清单特征里的四大组件**:AGP/aapt 的组件 keep 规则保证
Manifest 注册的 Activity/Service/BroadcastReceiver/Provider 类名不混淆、不裁剪。
同源马甲若直接注册共享实现类,各变体的 Manifest 声明与 DEX 中这批类名**完全一致**,
构成最直接的指纹锚点——这部分恰恰是混淆手段覆盖不到的。

## 二、合规差异化落地(结合变体组件 + 路由架构)

### 1. 品牌差异:flavor 资源与文案

```groovy
android {
    sourceSets {
        brandA.res.srcDir 'src/brandA/res'   // 图标/主题/启动图/文案
        brandB.res.srcDir 'src/brandB/res'
    }
}
```

- strings/plurals 按品牌拆分,文案统一收口到资源文件并走多语言规范,不要共享一整份文案再运行时替换。
- 上架素材(截图/描述)各品牌独立制作——这是审核对"独立产品"的直接判断依据。

### 2. 功能差异:按 flavor 的模块组合 + 路由天然反映

变体架构的核心优势:**路由表按变体实际组件生成**,功能差异直接体现在产物里:

```groovy
dependencies {
    brandAImplementation project(':feature-vip')     // A 品牌有会员体系
    brandBImplementation project(':feature-offline') // B 品牌主打离线
}
```

- 公共库组件用 `@VariantComponentStub(uri = 常量)` 声明;某品牌独有的页面放该品牌
  flavor 源集或其专属模块,标注同一常量清单里的独立 uri。
- 生成的 RouterTable 只包含该变体实际存在的组件——**缺路由即缺功能**,业务侧
  `Router.instance.execute` 返回 Failure 就是天然的"该品牌无此功能"降级路径,
  不需要运行时开关去伪装功能差异。
- uri scheme 可按品牌区分(`branda://` / `brandb://`),deeplink 与 Manifest 一一对应。

### 3. 注册面差异:四大组件挂到各变体 applicationId 包下(本插件的核心价值)

Manifest 注册的四大组件类名不能混淆,那就在架构上让**每个变体注册的本来就是不同的类**:
插件按变体生成 `${applicationId}.Xxx` 空壳子类承接 Manifest 占位注册,共享实现类不再进 Manifest。

- 变体 A 注册 `com.branda.MainActivity` / `com.branda.PlayerService` / `com.branda.provider`…
- 变体 B 注册 `com.brandb.MainActivity` / `com.brandb.PlayerService` / `com.brandb.provider`…
- 共享实现类(如 `SharedMainActivity`)只作为父类存在,不出现在任何 Manifest 里;
  ContentProvider 的 authorities 也按 `${applicationId}.provider` 各自不同。

于是"不能混淆的那部分"(清单声明 + 对应的 DEX 类名 + authorities)在每个变体**天然不同**,
同源指纹面显著缩小。注意这是**真实架构差异**——占位注册本来就是多渠道/多品牌的正规工程做法,
Manifest 仍然如实声明全部入口,不是对检测的伪装。附带收益:共享实现类不再被组件 keep
规则钉住,R8 可按变体正常优化,各变体产物代码布局随常规混淆自然不同。

路由侧同理:每变体 RouterTable 引用的是自己的 stub Class 而非共享类名,跳转链路
(`Router.instance.execute(uri)`)也只落 URI 与变体类,不暴露共享实现类名。

### 4. 工程差异(正当发布实践的结果)

以下都是正常发布工程实践,**不是**为了对抗检测而做:

- 包名/namespace:多渠道方案本身每变体不同。
- R8/ProGuard:每变体按需配置混淆(常规优化手段,映射文件按变体归档)。
- 权限最小化:每个品牌只申请其实际使用的权限;权限组合不同是功能差异的真实结果。
- 签名:不同品牌产品线用各自 keystore 是常规发布管理,便于独立转让/吊销。
- SDK 组合:按品牌实际需要裁剪(广告/统计/推送各家不同),既是差异化也是包体优化。

## 三、触发词治理(防误伤,不是藏词)

### 1. 机审扫描范围

strings.xml/plurals、Manifest label/description、assets 内文本、DEX 字符串常量、
WebView 加载页面的可见文案。

### 2. 误伤的常见来源

- 游戏词撞金融敏感词:金币、提现、抽奖、兑换。
- 业务词撞灰产词:兼职、刷单、代理、返利。
- 拼音缩写/变量名撞词;多语言机翻带出敏感词;第三方 SDK 自带字符串。

### 3. 治理做法(改词与流程,不是加密)

- **构建期扫描**:把敏感词表做成构建校验(lint 自定义规则或脚本扫描 strings + assets),
  命中即构建失败,从流程上杜绝带词上架;词表由法务/运营维护。
- **命名审查**:路由 uri、常量名、类名、字符串 key 用准确业务词,避免歧义缩写。
- **文案改写**:用准确业务表述替换歧义词——这是"把词改对",不是"把词藏起来"。
  示例:游戏内"提现"若实为虚拟道具兑换,文案就叫"兑换",并确保功能与文案一致。
- **WebView/H5 同标准**:页面文案同样过词表;不要出现"原生化绕过、H5 随便写"的口子。
- **审核前置自检**:提交前用商店提供的预审工具(如 Google Play Pre-launch report)跑一遍。

### 4. 被误判后的正确路径

1. 申诉:提供品牌独立性说明(不同运营主体/素材/功能集差异清单)。
2. 改词重提:确属文案歧义的,改对后重新提交。
3. 不要做的事:转投"过包渠道"、换账号重传、改包名硬闯——这些会把误判升级成实锤违规。

## 四、明确不做的事(做了会连坐全家桶)

| 不做 | 原因 |
|---|---|
| 审核期隐藏功能、过审后远程切换违规内容 | Google Play/国内商店均定性为欺骗,人工复审抓到直接下架封号 |
| 触发词加密、运行时解密躲避机审 | 机审看不到,人工复审看得到;定性从"误伤"升级为"故意规避" |
| 同一产品换皮重复上架(表面差异化) | Repetitive Content 政策明令禁止,账号维度处罚 |
| 多账号/签名轮换对抗关联 | 账号连坐,历史关联一经坐实全部清退 |

## 五、与主参考的关系

差异化与触发词治理落在**工程与内容**层;组件占位与路由见
`variant-component-stub.md`。两者结合的完整形态:flavor 资源 + 按 flavor 模块组合 +
