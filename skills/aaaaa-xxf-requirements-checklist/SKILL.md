# 需求核查与对齐

维护一份持续收敛的**剩余问题清单**：以证据核对需求，以编号推进对话，多轮逐项解决，完成即删行。清单文件默认 `<需求名>-实现核查问题清单.md`，需要澄清的事项独立成表，不混入确定缺陷。

## 执行顺序

1. 命中触发词进入本 skill；边界判断见下方"边界与授权"与 `triggers.md`。
2. 核查实现前，读 `references/audit-method.md`（核查维度、伪争议消除、证据标准、入表判定决策树）。
3. 建立、更新清单文件前，读 `references/checklist-format.md`（文件名与位置、完整模板、四张表的入表判定与列定义、编号与移除规则）。
4. 进入修复、确认、答复澄清、转表删行等多轮推进前，读 `references/multi-round-loop.md`（轮次模型、条目状态机、澄清提问与答复速记、确认核验分级、回归处理、依赖联动、会话重启恢复）。
5. 按下方"核心铁律"执行，按"交付检查"回复。

- 对齐需求 / 核查需求 / 实现核查 / 核对哪些没做到

- 按编号继续 / 处理第 N 项 / 003 已解决
- 哪些待澄清 / 缺结论 / 缺资源 / 还要验证什么

完整触发表达、反例与边界用例见 `triggers.md`。

## 边界与授权

- 与 `aaaaa-xxf-clarify-question` 分工：本 skill 管理清单中的待澄清项；用户答复后的决策记录按 clarify-question 规则写入主责模块的 `vibe-coding-clarify.md`。
- 纯视觉对稿走 `aaaaa-xxf-ui-design-alignment`；只有"需求是否要求该控件"这类判断回到本 skill。
- 确定问题获授权修复后的构建、测试、审查按项目交付流程（如 `aaaaa-xxf-delivery-loop`）执行；不因纯文档核查无差别要求全量构建或发布。
- "只核查、列问题"不授权修改业务代码；"确定的没做到就补齐"授权继续实现确定项，无需逐条重复确认。授权范围不明时，在首轮回复末尾用一句话确认（直接修确定项 / 只出清单），不默默二选一。
- 未决事项只阻塞依赖该结论的部分，其余已授权工作继续。
- 不借核查扩大重构、补写未知接口或修改需求原文；补充结论与变更依据单独记录。

## 核心铁律

1. 只用四类表格：确定问题 / 待澄清缺结论（独立记录）/ 缺资源外部依赖 / 必要的待验证项；一项只占一行、一张表。可独立修复或独立决策的问题拆行，重复原因造成的表现合并。
2. 编号跨四张表唯一、连续递增（001、002…），跨轮不变；删行不压缩、不复用、不重排；文件头维护"下一个可用编号"。
3. 清单只维护剩余事项，完成并通过必要验证后删行；**已有结论 ≠ 已经完成**。
4. 澄清答复先记录决策，再处理实现。
5. 每轮先读清单恢复上下文，不重新询问已确认项；用户说"第 3 项"即定位 `003`。
6. 表格结论必须带可定位的需求与代码证据；旧审查结论只是线索。区分"用户确认""文档约定""实现现状""助手建议"，不把建议记成需求或用户决策。

## 协作经验（来自 AI 结对实战）

- **验收前置**：没写"修复与验收标准"的行不允许进入修复轮；先补全该行再开工。
- **小步闭环**：修复轮一次推进不超过 3 个编号，修一项验一项，不攒一大批再验。
- **上游优先**：处理顺序按依赖拓扑，行内标"阻塞于 00X"的上游项先行，不按编号大小顺序。
- **时间盒**：单项卡住超过一轮，标暂缓换下一项，不死磕；阻碍写进"未完成原因"。
- **双向追溯**：修复产生的提交 / PR 信息引用清单编号（如 `fix(ads): 003 冷启动广告时序`）；删行时回复带一句依据。
- **决策记原因**：用户快速拍板时顺手问一句原因一并记入决策记录；用户不给原因不阻塞流程。
- **证据外置**：用户提供的截图 / 日志 / 录屏可作为核验证据，注明来源与日期；修复者自己的"我测过了"不构成证据，要贴验证结果。

## 交付检查

1. 表内是否只剩有证据的问题、真实未决事项、具体缺资源和必要待验证项？已实现项是否真正删行？
2. 编号是否唯一、跨轮稳定，跨表移动无重复，下一编号是否正确？
3. 每项是否有明确的处理方向 / 所需答案或资源 / 验证通过条件？
4. 用户已给出的答案是否落入决策记录，且只阻塞相关部分？
5. 回复是否包含：清单路径、本轮处理与移除的编号及原因、各表剩余数量、实际验证结果。未解决项不能用"全部对齐"概括。
