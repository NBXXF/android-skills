# 清单文件格式规范

清单文件是本 skill 跨轮唯一可信的状态源。本文定义它的文件名、位置、模板、四张表的入表判定与列定义、编号与移除规则。

## 1. 文件名与位置

- 默认文件名：`<需求名>-实现核查问题清单.md`，如 `广告优化-实现核查问题清单.md`。`<需求名>` 与需求文档 / plan 主名保持一致，不加日期后缀。
- 默认位置：与需求文档同目录（如 `docs/v2/plans/`）；用户指定路径时从指定。
- 复用优先：同一需求已有清单文件（含历史命名如 `xxx-实现核查.md`、`xxx-核查清单.md`）时，沿用原文件名和编号体系继续更新，**不新建第二份清单**。仅当确认不存在同类清单才创建。
- 唯一状态源：聊天中引用清单路径，不在对话里维护影子清单；每轮结束前把结论落回文件。
- 单会话单清单：一个会话只维护一份活动清单；切换需求时明确说明并切换文件路径，编号不跨清单混用，用户说"第 3 项"默认指当前活动清单。

## 2. 文件模板

```markdown
# <需求名> 实现核查问题清单

- 需求来源：<plan / 需求文档路径或链接>
- 创建日期：YYYY-MM-DD ／ 最近更新：YYYY-MM-DD
- 范围与授权：<只核查 | 允许修复确定项 | 允许修复+验证>
- 下一个可用编号：004

## 1. 确定问题

| 编号 | 优先级 | 需求与依据 | 当前实现与证据 | 确定问题 / 影响 | 修复与验收标准 | 状态 |
|---|---|---|---|---|---|---|

## 2. 待澄清 / 缺结论（独立记录）

| 编号 | 类型 | 需要确定的问题 | 已知事实 / 冲突依据 | 选项与建议 | 答案影响范围 | 状态 |
|---|---|---|---|---|---|---|

## 3. 缺资源 / 外部依赖

| 编号 | 缺少的具体资源 / 契约 | 影响的需求 | 已检查的来源 | 需要谁提供什么 | 解除条件 / 当前可做部分 |
|---|---|---|---|---|---|

## 4. 必要的待验证项

| 编号 | 尚未验证的行为 | 已有实现 / 已做验证 | 未完成原因 | 验证步骤与通过条件 |
|---|---|---|---|---|
```

- 只保留有实际条目的表；空表写"无"或省略整个小节。
- 表内按编号排列；优先级另列一列，不用重编号表达优先级。优先级建议用 P0（阻塞主流程 / 发布）、P1（本期应修）、P2（可延后）。
- 单元格保持简短，详细证据链接到需求与代码来源，不堆完整代码或长段落。

## 3. 文件头元信息

| 字段 | 说明 |
|---|---|
| 需求来源 | plan / 需求文档路径或链接，核查依据的入口 |
| 创建日期 / 最近更新 | 绝对日期（YYYY-MM-DD）；每轮更新"最近更新" |
| 范围与授权 | 只核查 / 允许修复确定项 / 允许修复+验证；范围中途变化在此追加注明 |
| 下一个可用编号 | 每次增删编号后同步更新，防止清空表格后失忆 |

## 4. 四张表的入表判定与列定义

### 4.1 确定问题

入表判定：需求和实际行为均可查明，且存在具体差异。

- 列含义：`编号 / 优先级 / 需求与依据 / 当前实现与证据 / 确定问题与影响 / 修复与验收标准 / 状态`。
- 写清触发条件和实际结果，避免"可能有问题""需要优化"等无法验收的描述。
- 验收标准用微格式：`触发条件 → 期望行为 → 验证方式(A/B/C)`，让"完成"可判定；证据定位格式见 `audit-method.md` §3。
- 状态枚举：待修复、处理中、待验证、暂缓；不保留"已完成"行。
- 修复已写但关键验证尚未完成，不能直接删除；根据剩余阻碍留在本表或移到待验证表，保留原编号。

### 4.2 待澄清 / 缺结论（独立记录）

入表判定：业务取舍、相互冲突的来源或缺少权威结论，且查阅现有证据仍无法确定。不与确定缺陷混表。

- 列含义：`编号 / 类型 / 需要确定的问题 / 已知事实与冲突依据 / 选项与建议 / 答案影响范围 / 状态`。
- 类型标记：需求不明确、来源冲突、缺业务结论、范围待定等，说明到底缺哪个答案。
- 状态枚举：待答复、暂缓；不保留"已答复"行。
- 选项应互斥、能直接回答；建议注明理由，不能冒充用户已经选择。
- 提问携带编号；优先问当前阻塞且影响最大的少量问题，已经确认过的不重问。提问模板、答复速记与决策记录流程见 `multi-round-loop.md` §3。
- 用户未回复、继续别的工作或仅说"继续"不等于选择某个未决方案。
- 用户明确答复后，**先记录决策再处理实现**：按项目已有 `aaaaa-xxf-clarify-question` 的记录规则，将决策、日期、来源、影响范围和原编号写入主责模块的 `vibe-coding-clarify.md`；无该约定时复用项目既有决策记录。已决事项移出本表；尚需实现则按原编号转入确定问题表，并在行内携带决策依据。

### 4.3 缺资源 / 外部依赖

入表判定：先搜索现有仓库、附件、设计工具或已连接资料源，能直接取得的自行取得；确实缺失才列入。

- 列含义：`编号 / 缺少的具体资源或契约 / 影响的需求 / 已检查的来源 / 需要谁提供什么 / 解除条件与当前可做部分`。
- 区分缺设计源文件、图标、文案、接口字段、错误码定义、配置样本、访问权限或设备能力，不能笼统写"缺资料"。
- 原图、真实接口、业务参数缺失时，不用近似图、模拟数据或猜测字段伪装完成。
- 收到资源只解除依赖；还需接入或验证的，按原编号转入对应表，不能仅因"资料到了"就删除整个问题。

### 4.4 必要的待验证项

入表判定：实现已存在但关键行为尚未验证；不把每个缺少单测的方法都列成新需求问题。

- 列含义：`编号 / 尚未验证的行为 / 已有实现与已做验证 / 未完成原因 / 验证步骤与通过条件`。
- 编译通过不等于真机、后端或线上配置验收通过；只有源码证据时准确标明。
- 同一正式链路的多个观察点可合并为一次端到端验收，避免重复列成多个"未实现"。
- 不具备验证条件时保留具体阻碍；不能为了让表格清零把未知结果写成通过。
- 验证步骤标注执行方：`助手可执行`（构建 / 单测 / 脚本 / 读码）或 `需用户配合`（真机 / 账号 / 线上配置），避免两边互相等。

## 5. 编号规则

- 新清单使用跨四张表唯一、连续递增的编号，例如 `001`、`002`、`003`；用户说"第 3 项"即定位 `003`。已有清单保留原编号体系。
- 删除行后不压缩剩余编号、不复用旧编号；跨表移动保持编号。
- 拆分条目：保留原号作为其中一项，其余用新号并注明来源；合并条目：保留最早编号，聊天说明合并关系。
- 用户指定编号时优先处理对应项及必要依赖，不顺带修改无关项；用户引用旧号时先查决策或文档历史，不能让旧号指向新的问题。

## 6. 移除规则

| 情况 | 对活动表格的处理 |
|---|---|
| 核实已实现，或按本次范围完成修复并通过必要验证 | 删除该行 |
| 新证据证明问题不成立或已被明确决策覆盖 | 删除该行；在本轮回复简述撤销依据 |
| 澄清已回答，但实现尚未完成 | 保留编号，移入确定问题表 |
| 缺失资源已补，但接入或验收尚未完成 | 保留编号，移入确定问题表或待验证表 |
| 用户仅说暂缓，未明确取消 | 保留行并注明暂缓，不能记为完成 |
| 用户明确取消、移出本期或要求从清单删除 | 删除该行；必要时在清单头"范围与授权"注明，不宣称已实现 |

## 7. 内容纪律

- 清单只维护剩余事项：不追加"已完成问题表"、删除线历史行或越来越长的修复流水账；验证证据留在测试报告 / 提交记录，用户决策留在决策记录。
- 更新已有行时，"需求与依据"列保持稳定，只更新证据、状态等列；确需修正表述时在本轮回复说明，避免下一轮认不出该行对应哪个问题。
- 每轮先核对实际改动和新答案，再更新表格；不要将上一轮全部结论机械复制回来。
- 用户要求保留全量追踪台账时，按其要求执行；不能把默认消项规则强加到指定台账上。
