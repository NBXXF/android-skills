# 核查方法（如何查出真问题）

清单管"记录"，本文管"怎么核"。目标：每个入表的行都有可定位证据，每个不入表的疑点都有不成立的理由。核查轮开始时通读本文再动手。

## 1. 核查维度（按序过一遍，防漏检）

1. **入口**：每个需求点对应的界面入口 / 路由 / 触发时机是否存在。
2. **状态**：初始态、中间态、终态、异常态是否都处理；前后台切换、弱网、重试后的表现。
3. **业务逻辑**：条件分支、边界值、优先级与互斥规则、计数 / 频控 / 防重。
4. **配置**：远端开关、默认值、灰度、多品牌 / 多渠道差异。
5. **失败恢复**：超时、错误码、降级路径、兜底 UI。
6. **验证证据**：有没有能证明行为正确的测试、日志或验收记录。

## 2. 伪争议消除（入表前先过这四关）

1. **决策时效**：用户后续明确决策覆盖被取代的旧描述；严格区分"用户确认 / 文档约定 / 实现现状 / 助手建议"四种来源。
2. **截图 ≠ 源设计**：原始文档截图与用户指定的源设计不同时，优先完整源设计和后续指示，不能仅凭旧截图断言某控件是多做的。
3. **强化 ≠ 缺陷**：需求未要求的强化条件、额外兜底、假设场景不是缺陷；"要不要扩展需求"与"漏实现"是两件事，前者走待澄清。
4. **服务端契约**：职责已有明确契约且客户端已接入时，不因本仓库没有服务端源码就认定未实现；真实结果未知只保留必要的联调验收项。

来源冲突过完这四关仍无法消除的才入待澄清表，写明冲突点，不自行选更顺手的口径。

## 3. 证据标准

- 每个结论给出 `文件:行号`、提交号或文档段落定位；只有聊天记忆支撑的结论标注"待复核"。
- 旧审查结论、历史文档只是线索，必须重新对照当前代码后才能引用。
- "没搜到" ≠ "不存在"：换关键词、换入口、沿调用链再查一轮，仍无才可作为"未实现"的证据。
- 编译通过、代码存在都不等于行为正确；行为结论要能指出验证证据在哪。

## 4. 入表判定（分类决策树）

| 事实组合 | 去处 |
|---|---|
| 需求要求，实现缺失或有差异 | 确定问题表 |
| 需求要求，实现已做，关键行为未验证 | 待验证表 |
| 无法判断需求是否要求（业务取舍 / 来源冲突 / 缺口径） | 待澄清表 |
| 实现被外部资源卡住（设计源文件 / 接口字段 / 权限） | 缺资源表 |
| 需求没要求，实现也没有 | 不入表（不是缺口） |
| 需求没要求，实现做了 | 不是缺陷；确有风险在回复中提一句，用户认可才入表 |
