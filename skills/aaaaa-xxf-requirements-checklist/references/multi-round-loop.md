# 多轮修复与确认工作流

清单文件是跨轮唯一可信的状态源。本文定义条目如何跨轮流转、澄清如何提问与记录、用户确认如何核验、回归与依赖如何处理、会话重启如何恢复。每一轮都落在"恢复 → 对照 → 处理 → 收敛"的骨架上。

## 1. 轮次模型

| 轮次类型 | 触发 | 本轮动作 | 退出标准 |
|---|---|---|---|
| 核查轮 | 首次对齐、需求更新、大改动后复核 | 建清单或全面复核，产出/更新四表 | 每行有证据、分类正确、编号连续 |
| 修复轮 | 用户指定编号或授权修复确定项 | 实现该编号及必要依赖 + 针对性验证 | 状态更新为待验证或验证通过后删行 |
| 确认轮 | 用户答复澄清、声称完成、给新证据 | 先记录决策或先核验，再删行/转表 | 结论落回清单文件 |
| 收敛轮 | 提测/上线前 | 复核剩余项的证据、分类、解除条件；对近期删行的 P0 / 主流程项做读代码级抽查复检 | 只剩真实未决事项，抽查无复活项 |

混合轮常见（先答复再修复）：**先落决策记录，再动代码**；不要把"用户确认了"直接当成"已经做完了"。

每轮固定骨架：

1. **恢复**：读清单文件、决策记录（`vibe-coding-clarify.md`）、原始需求与上一轮改动。
2. **对照**：核对本轮新信息（用户新答复、新资源、新代码改动）影响哪些编号。
3. **处理**：只处理用户指定的编号及必要依赖，不顺带修改无关项。
4. **收敛**：更新清单文件、移除已关闭行、同步"下一个可用编号"和"最近更新"，回复剩余数量。

## 2. 条目状态机

跨表移动一律保留原编号。

### 确定问题

```
待修复 → 处理中 → 待验证 → （验证通过）删行
           ↑         │
           └─────────┘（验证失败：回到处理中，保留编号）
任意状态可 → 暂缓（保留行并注明）
```

### 待澄清 / 缺结论

```
待答复 →（用户明确答复）记录决策
            ├─ 需要实现 → 按原编号转入确定问题表
            └─ 纯结论 / 不再适用 → 删行
任意状态可 → 暂缓（保留行并注明）
```

### 缺资源 / 外部依赖

```
缺失 →（资源到位）
            ├─ 还需接入或验证 → 按原编号转入确定问题表或待验证表
            └─ 仅为等资料即可关闭 → 删行
```

### 必要的待验证项

```
待验证 →（通过）删行
            └─（失败）按原编号转入确定问题表，描述实际缺陷
```

## 3. 澄清的提问与答复

### 3.1 提问格式

1. 按阻塞优先，每轮最多 3 个问题；已确认过的不重问。
2. 每个问题携带清单编号，使用统一模板，让用户能用"编号 + 选项"速记答复：

   ```
   【待澄清 002】<问题一句话>
   - A. <选项> → <影响>
   - B. <选项> → <影响>
   建议：A（<一句理由>）
   ```

3. 选项互斥、可直接回答；建议必须注明理由，不能冒充用户已经选择。
4. 运行环境提供结构化提问组件时优先使用，问题、选项与清单编号保持一致。

### 3.2 答复速记解析

| 用户说 | 处理 |
|---|---|
| "002 A" / "第 2 项选 B" | 选定对应选项，记录决策并联动影响范围 |
| "都按建议来" / "按你说的办" | 该批问题全部采用建议项；决策记录注明"用户采用助手建议" |
| "002 不做了 / 砍了" | 明确取消：删行并在清单头"范围与授权"注明 |
| "002 先放着 / 以后再说" | 暂缓：保留行标暂缓 |
| "002 好了 / 修完了" | 进入核验（见 §4），核验通过才删行 |
| "继续" / 沉默 / 转做别的事 | 不是答复；未决项保持未决，其余已授权工作继续 |
| 一轮批量答复（"002 A，005 砍了"） | 逐项解析、逐项记录决策、逐项转表或删行 |

### 3.3 决策的记录与携带

1. 用户明确答复后，**先记录决策再处理实现**：按 `aaaaa-xxf-clarify-question` 的规则，将决策、日期、来源（提问编号）、影响范围写入主责模块的 `vibe-coding-clarify.md`；项目无该约定且无既有决策记录文件时，在需求文档同目录创建一份 `vibe-coding-clarify.md` 沿用相同字段，不把决策散落在聊天里。
2. 决策记录只追加不覆盖：后续新决策取代旧决策时，旧记录保留并在新记录注明"取代 <日期> 关于 <问题> 的决策"，避免回溯时只剩最后一份口径。
3. 用户快速拍板时顺手问一句原因一并记入；用户不给原因不阻塞流程，决策来源标注"口头拍板"。
4. 已决事项移出待澄清表；尚需实现的按原编号转入确定问题表，并在该行"需求与依据"末尾追加决策来源，格式如 `（依据：003 决策 2026-10-23，见 vibe-coding-clarify.md）`——保证下一轮只读清单也能理解"为什么这样做"。
5. 决策只影响"答案影响范围"列出的条目：扫描该列联动更新，可能一次关闭或激活多行，不能只改提问的那一行。

## 4. 确认的核验规则

1. **口头完成不直接删行**。用户说"第 N 项好了 / 已经修了"，先按该行"修复与验收标准 / 验证步骤与通过条件"做最小核验；通过才删行，不通过保留并在状态列写核验结论。
2. **决策确认 ≠ 完成确认**。用户确认"就这么做"只关闭待澄清行；实现部分按原编号入确定问题表。
3. **批量声明逐项核验**。用户说"确定问题都修了吧"，逐项核验，只删通过项，未通过项列出原因；不整表清空。
4. **沉默 / "继续" ≠ 答复**。存在未决方案时，用户继续别的工作不等于选定任何方案。
5. **口头结论与代码矛盾**。以可定位证据为准，回贴证据请用户裁决；矛盾本身可入待澄清表，不自行选更顺手的口径。
6. **证据的来源分级**。用户提供的截图 / 日志 / 录屏是有效核验证据，在行内注明来源与日期；修复者自己的"我测过了"不构成证据，必须贴验证结果或命令输出。
7. **核验强度分级**：
   - A 静态核验（读代码 / 读配置）
   - B 构建 + 相关单测
   - C 真机 / 联调 / 线上配置验收

   每条的验收标准应写明需要哪级；未达级别的只能转待验证表，不能删行。编译通过不属于 C。

## 5. 回归与复活

不复用已删除的编号。

| 情况 | 处理 |
|---|---|
| 本轮内发现删错了（其实没修好） | 恢复原编号原行，状态注明"复检未过" |
| 相隔一轮以上再次出现（被其他改动改坏） | 新编号重新立项，描述注明"回归自 00X" |
| 用户质疑已删行 | 先复检；不成立则解释依据并回贴证据；成立按上两行处理 |

- 修复引出的新缺陷用新编号立项，不塞进旧行、不扩大旧行描述。
- 删行时在本轮回复中给出一句依据（验证结果 / 决策来源），便于事后追溯。

## 6. 依赖与联动

- 修复或决策依赖另一项时，在行内显式写"阻塞于 00X"；被阻塞项不重复提问、不重复修复。
- 一项资源到位后，同步检查"影响的需求"列里其他条目是否随之解锁。

## 7. 会话重启与上下文压缩

- 新会话 / 记忆截断后的第一动作：读清单文件 + 决策记录，再读需求文档；**禁止重新询问清单里已有结论的问题**。
- 清单头元信息（需求来源、范围与授权、最近更新、下一个可用编号）必须随时可续接。
- 发现清单过期（"最近更新"早于已知改动，或代码现状与清单描述明显不符）时，先对该部分做一轮快速复核再继续，不盲推旧结论。

## 8. 范围中途变化

- 扩需求：新条目用新编号；已删行不因范围扩大自动复活。
- 缩范围：明确"本期不做 / 砍掉"→ 删行并在清单头"范围与授权"注明；"暂缓"→ 保留行标暂缓。
- 用户要求重开已取消项：新编号立项并注明来源；仍在同一轮内的可恢复原行。
- 需求原文修订后：受影响条目重新对照新版需求，结论被取代的删行并注明依据。

## 9. 每轮回复格式

回复按序号列点，保持简短：

1. 本轮处理了哪些编号、各自结果（修复 / 记录决策 / 转表 / 删行 + 依据）。
2. 四表剩余数量。核查轮或用户要求看清单时，在聊天里完整展示四表；推进轮只展示本轮变动的行，避免整表刷屏。
3. 当前阻塞点，格式固定：`待答复：002、007 ／ 待资源：005 ／ 无阻塞`。
4. 实际验证结果（做了哪级核验）；未解决项不能用"全部对齐"概括。
5. 修复类回复附一句影响面与回归风险；项目有提交规范（如 `[risk:] [test:] [impact:]`）时按其格式声明。
6. 讨论任何条目时先报编号再陈述，保证对话与清单可互相定位。
