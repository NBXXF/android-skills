# README / Docs 文档规范

## 目标

为 Android、Kotlin、KMP、SDK、Library、组件库和工程文档建立统一结构，让读者能按“先理解、再接入、再深入、再排错、再迁移”的顺序使用文档，也让 AI Agent 编写规范文档时有清晰约束。

## 触发场景 / 适用范围

- 用户要求写、改、补全或审查 README、Docs、接入文档、SDK 文档、Library 文档、开发规范、规则文档、AGENTS.md、CLAUDE.md、SKILL.md、`.mdc` 文档。
- 用户提到“快速开始、逐步进阶、API 说明、最佳实践、排错、故障排查、迁移、版本记录、示例、核心概念”等文档结构。
- Android / KMP / SDK / Library 文档需要面对第三方开发者、业务接入方、团队开发者或 AI Agent。

## 强制规则

- 先读目标仓库源码、Gradle 配置、公开 API、示例、测试和既有文档，再写结论；禁止凭记忆补 API、版本号、包名、参数或行为。
- 文档结构优先使用“概览、快速开始、核心概念、接入指南、使用指南、示例、API 参考、最佳实践、故障排查、迁移指南、版本记录”这套完整体系。
- 将“逐步进阶”规范为“使用指南 / Guides”，将“API 说明”规范为“API 参考 / API Reference”，将“排错”规范为“故障排查 / Troubleshooting”。
- Quick Start 必须让用户能在最短路径跑通最小示例；Reference 用于查询，不承担教程职责。
- 每篇指南或规范文档必须尽量包含：目标、触发场景 / 适用范围、强制规则、禁止事项、执行流程、验证 / 审查清单、输出要求。
- 面向 AI Agent 的规则型文档必须把“什么时候触发、必须做什么、禁止做什么、怎么验证、最终输出什么”写清楚。
- 文档必须格式友好，优先用表格、树状结构、流程图、步骤清单和 Demo 呈现；避免长篇大论堆段落。
- 表格列优先使用 `What`、`Why`、`How`，其次才是差异、限制、风险、示例等补充列。
- Android SDK / Library 接入文档必须覆盖 Gradle、初始化、Manifest、权限、ProGuard / R8、版本兼容、错误处理和可验证示例，除非该库确实不涉及。
- 涉及用户可见文案、公共 API、发布库、R8、Google Play 合规、性能或测试时，继续按对应项目 skill 做专项门禁。

## 禁止事项

- 禁止把 README 写成只有安装命令和 API 列表的片段。
- 禁止在没有源码证据时编造类名、方法签名、Gradle 坐标、版本号、Manifest 节点、权限、错误码或配置项。
- 禁止把教程型内容、API 查询内容和排错内容混在同一个无层次长文里。
- 禁止只写“建议”“可以”，却不写强制规则、禁止事项和验证方式。
- 禁止为了完整而堆砌空章节；确实不适用的章节要说明“不涉及”的原因。
- 禁止在共享 Android skills 仓库中写入具体业务 App 私有 API 或私有接入细节。

## 执行流程

1. 明确文档类型：教程型、API 型、规则 / Skill 型，或完整 SDK 文档体系。
2. 读取事实来源：源码、Gradle、Manifest、公开 API、示例、测试、Release Notes、既有 README。
3. 判断读者：第三方开发者、业务接入方、库维护者、团队成员或 AI Agent。
4. 先设计一级目录，再补每篇文档内部结构。
5. 将快速开始压缩到最短可运行路径，把概念、进阶、API、排错和迁移拆到独立章节。
6. 给代码示例补齐文件路径、依赖、初始化位置、调用顺序、异常处理和验证方式。
7. 把解释性段落尽量改成 `What / Why / How` 表格、目录树、流程图、Do / Don't、Demo 或排错表。
8. 用审查清单检查是否可运行、可查询、可排错、可迁移、可维护。

## 需要读取的 references

- 编写正式 README、SDK 文档、Library 文档、文档站结构、规则型文档或需要完整模板时，读取 `references/readme-docs-reference.md`。
- 只做很小的标题、错别字或链接修复时，可以不读取 reference，但仍要遵守本文件的强制规则和禁止事项。

## 三类文档模板

### 教程型

```text
目标
前置条件
核心概念
执行流程
示例
最佳实践
故障排查
```

用于 Quick Start、接入教程、功能指南。重点是让读者按顺序完成任务。

### API 型

```text
概述
API
参数
返回值
异常
示例
注意事项
```

用于 API Reference。重点是准确、可查、可复制，不要把大量教程内容塞入 API 条目。

### 规则 / Skill 型

```text
目标
触发场景 / 适用范围
前置条件
强制规则
禁止事项
执行流程
边界情况 / 异常处理

```

用于 AGENTS.md、CLAUDE.md、SKILL.md、`.mdc`、团队规范和 AI Agent 规则。推荐顺序是：先告诉它什么时候做，再告诉它必须怎么做、不能怎么做、怎么确认做对了。

## API / 配置说明写法

- API 条目必须包含签名、参数、返回值、异常、线程要求、生命周期要求和示例。
- Gradle 配置必须写清插件、dependency、version catalog、repository、consumer rules、minSdk / compileSdk / targetSdk 影响。
- Android 接入必须写清初始化位置、Context 要求、Activity / Fragment / Application 生命周期、权限、Manifest、R8 和多进程影响。
- KMP 接入必须区分 commonMain、androidMain、iosMain 等平台差异。
- Deprecated API 必须写替代方案和迁移步骤。

## 示例写法

- 最小示例只保留跑通所需代码。
- 推荐示例展示生产环境更合理的封装方式。
- 完整示例给出文件路径、依赖、初始化、调用、异常处理和验证方式。
- Kotlin 示例优先；只有项目仍需 Java 接入方时才补 Java 示例。

## 边界情况 / 异常处理

文档必须按实际能力覆盖相关边界：

- 空值、重复调用、并发调用、初始化失败。
- 生命周期异常、配置变更、进程重启。
- 网络异常、IO 异常、权限拒绝、版本兼容问题。
- 线程切换、取消、超时、资源释放和内存泄漏。

## 最佳实践

- 使用 Do / Don't 呈现推荐与反模式。
- 写明推荐架构、模块划分、生命周期管理、线程与并发、性能、内存、网络、缓存、错误处理、安全和可测试性。
- 解释关键约束背后的原因，避免只有结论没有上下文。

## 验证 / 审查清单

完成文档后检查：

- 是否说明“这是什么、解决什么问题、适合谁”。
- Quick Start 是否能在 5 分钟内跑通最小示例。
- 是否优先使用表格、树状结构、流程图、步骤清单和 Demo，避免长篇段落。
- 关键解释是否用 `What / Why / How` 表格表达，差异、限制、风险是否作为后续列补充。
- Gradle、Manifest、权限、初始化、R8、版本兼容是否覆盖。
- API 签名、参数、返回值、异常和示例是否来自真实源码。
- 是否区分教程、指南、Reference、Troubleshooting 和 Migration 的职责。
- 是否包含核心概念，避免用户只会复制代码但不理解原理。
- 示例是否可编译，是否标明文件路径和必要 import。
- Demo 是否体现真实接入路径、核心效果、验证方式和常见场景。
- 是否覆盖常见错误、日志排查、错误码和 FAQ。
- 是否列出 Breaking Changes、Deprecated API 替换和迁移检查清单。
- 是否写清输出要求，尤其是 AI Agent 最终应该交付什么。

- 新增或调整了哪些文档章节。

- 哪些章节因项目不涉及而省略。
- 是否存在无法确认的 API、版本、平台兼容或行为细节。
- 对规则 / Skill 型文档，必须保留强制规则、禁止事项、执行流程、验证 / 审查清单和输出要求。
