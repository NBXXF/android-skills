# 结构与职责清晰专项

> 目标：每个类、函数、文件一眼看得出"它负责什么"，职责边界清晰、放代码的位置可预测。依据 Ousterhout《A Philosophy of Software Design》（深模块/信息隐藏/复杂度三症状）与 Sandi Metz 规则。模块间依赖方向、包结构、分层归属归 `aaaaa-xxf-coding-arch` / `aaaaa-xxf-multi-module-structure` / `aaaaa-xxf-class-declaration-guidelines`；本文件管"单个类型/函数/文件内部的职责与结构清晰"。

## 1. 职责声明测试

- **一句话测试**：能否用一句话（一个动词短语）说清这个类/函数的唯一职责？说不清、句子出现"和/以及/还有"就是多职责，拆。
- **名字难起 = 设计有问题**：给某个类/函数起名卡壳、起出来的名字不带信息量（`DataProcessor`、`InfoHelper`），说明切分边界本身错了，先调边界再补名字（Ousterhout 红旗）。
- **改完像一开始就这么设计的**：修完 bug / 加完功能后，周边代码应看起来"该变更本来就在设计内"，而不是补丁摞补丁；最小 diff 不等于最小改动质量。

## 2. 复杂度三症状（结构层视角）

- **变更放大**：一个简单概念变更要改多处——说明该概念没有唯一属主。
- **认知负担**：开发者要知道/记住的太多——接口面过宽、约定过多。
- **未知的未知**：不明显哪些东西重要、改这里会牵连哪里——命名含糊、依赖隐藏。
- 复杂度是增量累积的：每次"就这么先写着"都在付利息，小事也要较真。

## 3. 深模块 vs 浅模块

- **深模块 = 接口窄、功能深**：公共方法少而每个干得多，调用方一行代码换来大量工作。
- **浅模块 = 接口几乎和实现一样复杂**：公共方法多而每个都很薄，调用方承担大部分编排负担。数公共方法：多而薄即浅。
- **编排归属测试**：调用方是否必须按正确顺序调用本模块多个方法才能完成一件事？是——把编排拉进模块内部，调用方只留一个高层入口。
- **复杂度下压**：无法避免的复杂实现收进模块内部，接口保持简单；模块自己能定合理默认值时，就不要加配置参数把决策推给调用方。
- 少而强的操作胜过多而窄的操作。

## 4. 信息隐藏：按知识分组，不按执行顺序分组

- 每个模块封装"别的模块不需要知道的决策"（文件格式、协议、数据结构、算法）。
- **同一决策只允许一个模块知道**：同一个格式/协议知识出现在多个文件里就是信息泄漏，变更会放大。
- **时序分解反模式（Temporal Decomposition）**：按"读取→解析→校验→转换→写入"的执行步骤切类/切方法，而不是按"谁知道什么"切。特征：调用方必须按特定顺序调用一组方法才正确——这是隐式时序耦合，正确性靠约定不靠类型。
- 修正：把"知道文件格式"的所有代码归一个类型，"知道校验规则"的归一个类型；顺序由编排层显式表达。

## 5. 相邻层不同抽象

- 两个相邻层接口高度相似 = 分解错了：每层应工作在明显不同的抽象层级。
- 纯转发（Pass-Through/Middle Man）：方法体基本只是调用另一个相似签名的方法，加了一层却没加抽象——内联（跨模块防腐层/二进制兼容包装除外）。
- **连体方法（Conjoined Methods）**：两个方法必须一起读才能懂（共享隐式状态/隐式契约）——合并，或把共享契约显式化成类型/参数。

## 6. 合与分的判断

- **长度从来不是拆分的理由**，共享信息、简化接口、消除重复才是；同样，"太长了"不是合并的理由，职责完整才是。
- 特殊目的代码与通用机制混杂（Special-General Mixture）时分离：通用机制留在通用层，特化逻辑留在使用它的地方。
- 拆分后每个单元仍要"做一件事且做完整"——拆成半成品（每片都离不开别的片）比不拆更糟。

## 7. 一致性优先（对 AI 尤其重要）

- **类似的问题用类似的解法**：同一文件/模块里，同类场景（重试、缓存、错误映射、线程切换）用同一种既有写法，不引入第二种风格。
- "我有个更好的想法"不是引入不一致的充分理由；确有全局改进时单独开重构任务统一迁移，不在功能 diff 里夹带。
- 新代码落位前先看邻居：同类问题邻居怎么写，就怎么写。

## 9. 状态与依赖信号

- **状态唯一属主（Single Source of Truth）**：每份可变状态只有一个属主类型，修改入口唯一；同一个事实存在两份（两个 LiveData/字段/缓存）必然漂移。
- UI 状态集中建模（一个 UiState/sealed 状态），不散落多个可变流让阅读者自行拼装真相。
- 副作用集中：同类副作用（埋点、日志、导航）在同一层处理，不散落每个函数里。
- 构造注入依赖 7+：类职责扩散或在做编排之外的事，重新划职责。
- 函数间用成员 `var` 传状态 = 隐式信道，改为参数/返回值或状态对象。

## 10. 文件内布局与视觉清晰

看起来乱经常只是布局乱。统一约定（与 `aaaaa-xxf-class-declaration-guidelines` 的文件组织规则叠加）：

- **成员排序模板**：属性/字段 → init → override（生命周期在上）→ 公共 API → 私有 helper（按被使用顺序）→ companion。全库统一，读者形成位置直觉。
- **空行分组**：一段空行一个想法；同类语句聚成一组，不同意图之间空行分隔。连续多段无空行平铺 = 想法没分组。
- **相似结构相似排版**：连续的同构调用（多个 `put`/多个 builder 语句）按同样缩进/字段顺序排列；参数列表超行宽时每参数一行。
- **行宽**：遵守项目 ktlint/format 配置；无配置时 ~120 列，链式调用在操作符前换行。
- **diff 友好**：不重排无关行、不改无关键缩进；让 review 者看到的每一行变更都有意义。

## 11. 实现前：Design it twice

对非平凡的类型/API/重构：实现前用几句话对比至少两个根本不同的方案——接口简洁度、实现复杂度、未来变更的承受力。哪怕第一眼方案"显然对"，对比一遍也会暴露盲点；产出的结论让评审有据可依。与 `aaaaa-xxf-agent-high-quality-operation` 的方案先行要求衔接。
