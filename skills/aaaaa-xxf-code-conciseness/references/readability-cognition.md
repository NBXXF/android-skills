# 认知负担与上手速度专项

> 目标：新接手的人（或下次的你、 reviewing 的 agent）以最小认知负担看懂并安全改出第一行代码。本文件管"读得快"，`kotlin-idioms.md` 管"写得对"，`code-smell-catalog.md` 管"哪里烂"，`structure-responsibility.md` 管"放哪里、归谁管"。阈值依据 Miller 定律（工作记忆 7±2 组块）与 The Art of Readable Code，认知复杂度口径参考 Sonar。

## 1. 认知阈值表（Miller 系）

人类工作记忆一次持住约 7 个组块，代码各项指标超出即"读着费劲"：

| 维度 | 目标值 | 超过即信号 |
|---|---|---|
| 函数参数 | ≤5 | 调用方记不住顺序，开始靠猜 |
| 类的公共方法数 | ≤7 | 类职责开始膨胀（配合 God Object 检测） |
| 单函数分支数 | ≤5 | if/when/loop/catch 合计 |
| 单函数逻辑行 | ≤15（不含空行注释） | 本 skill 的 50 行是拆分评估上限，15 行是理想值 |
| 嵌套层级 | ≤3 | 第 4 层嵌套里读者已丢失外层上下文 |
| 连续布尔条件 | ≤3 个操作数 | `a && b \|\| !c && d` 要在脑内建栈 |

超过任一阈值：先拆函数/提取谓词/参数对象，确实无法拆（如长 when 映射表）时允许保留，但要在交付说明里讲清为什么。

## 2. 认知复杂度 ≠ 圈复杂度

圈复杂度数分支数量；认知复杂度额外惩罚**嵌套**与**思维栈**。同样 3 个 if：

```kotlin
// 便宜：平铺，读者线性扫过，各条件独立
if (!user.isActive) return ...
if (user.isBanned) return ...
if (user.age < 18) return ...

// 昂贵：嵌套，读者必须维持外层上下文的思维栈
if (user.isActive) {
    if (!user.isBanned) {
        if (user.age >= 18) { ... }   // 读到这里还得记得前两个条件
    }
}
```

Kotlin 口径的简化记分：

- 嵌套结构内每个控制流语句按**当前嵌套深度**计分——第 3 层里的一个 if ≈ 顶层的三个 if。
- 连续布尔操作数序列递增：`a && b && c || d` 比拆成命名谓词贵。
- 递归、非线性跳转（带标签的 break/continue）额外加负担。

实操结论：**平铺永远优于嵌套**（guard clause）；深嵌套优先消灭，其次才考虑函数提取。

## 3. 阅读流：自上而下、高层到细节

- **报纸隐喻**：文件像报纸——标题（类 KDoc 一句话）→ 摘要（公共编排入口）→ 正文（私有实现细节）。读者从上往下读，理解逐步加深，不需要跳读。
- 类内排序：公共 API 与编排入口在上；私有 helper 按被使用顺序跟在调用者下方；companion 常量最底部（或顶层）。
- **主编排函数读作大纲**：读一个编排函数应该像读目录，每行一个意图，具体怎么做在下一层函数里。一个函数里同时出现"编排语句"和"实现细节语句"就是抽象层级混杂，是"读起来乱"的直接原因。
- **声明就近**：变量在使用点前最近处声明，禁止文件头/函数头声明区；读者不该向下扫 50 行找某变量定义。
- **相似代码相似外观**：同一文件里同一模式用同一种写法（都用 `?.let` 或都用 if-null-check，不混用）；参数列表、链式调用按语义分组换行对齐。

## 4. 词汇一致性：一概念一名

新人上手慢的最大隐藏成本是**同一概念多个名字**：

- 同一领域概念全库唯一名字：`user`/`account`/`member` 不许混用指同一物；`callback`/`listener`/`handler` 选一个体系。
- 命名映射可预测：DTO/VO/Entity 之间字段名要么完全一致，要么全部走显式映射函数；类型名稳定可推断（`UserVo` ↔ `UserDto` ↔ `user` 表）。
- **改名边界即转换边界**：跨层词汇统一发生在 DTO 转换处，边界内部不许出现同义词漂移。
- 引入新概念前先 Grep 既有词汇表，复用已有命名；确实要造新词时确认没有近义旧词在用。
- 反向也成立：一个名字只允许指一个概念。`context` 既指 Activity 又指协程上下文又指解析上下文时，读者每次都要现场消歧。

## 5. 可搜索性与名字信息量

- **名字必须可 grep**：单字母/双字母命名只允许在几行的作用域内（短 lambda、紧跟其后的循环体）；跨行跨层出现的变量必须全名。`e` 在 catch 里可以，`d` 作为长链中间变量不行。
- 名字携带关键消歧属性：
  - 时间值带单位：`retryDelayMs`，不是 `retryDelay`
  - 大小带单位：`cacheSizeBytes` / `fileSizeMb`
  - ID 带类型：`userId` / `trackId`，裸 `id` 只允许在持有者类型内部
  - 可空/默认语义显式：`displayNameOrDefault` 这类不如类型建模，但至少别让名字撒谎
- 名字不许与外层作用域遮蔽（shadowing）框架/标准库符号；`it` 嵌套时必须改命名参数。
- **语法角色规则**：类/接口/对象 = 名词（`DownloadQueue`）；方法/函数 = 动词或动宾（`cancelAll`、`parseHeader`）；布尔 = 形容词系（`isXxx`/`hasXxx`/`shouldXxx`）；返回集合 = 复数（`activeUsers`）；名字带介词短语时注意语义（`byId` 做后缀表示索引键）。
- **无信息量名字黑名单**：脱离上下文站不住的 `data`、`info`、`temp`、`val`、`obj`、`result`、`item`、`handle` 一律改名（`parseResult`、`firstItem` 这类有上下文的保留）；`data` 只在 `data class` 声明处出现。
- **匈牙利残留禁令**：`m`/`s`/`k` 成员前缀、`I` 接口前缀（`IUserRepository` → `UserRepository`）、类型缩写后缀（`strName`、`intCount`）全部清除——类型信息由类型系统承载。
- **计算属性 vs 函数**：无参数、无副作用、O(1) 或廉价计算的用 `val x get()` / `fun x()` 属性形态；耗时、有副作用、可能失败的必须用函数且名字体现代价（`loadX`/`computeX`/`fetchX`）。
- **名字难起 = 设计有问题**：起名卡壳或起出来不带信息量，先怀疑切分边界错了（详见 `structure-responsibility.md` §1），不要硬起一个 DataProcessor/InfoHelper 蒙混。

## 6. 变量与作用域最小化

- 一次性中间变量删除：只用一次、名字不新增信息的那层变量直接内联。
- 作用域最小化：能局部不成员、能 private 不 public、能 internal 不 public；`var` 局部化，禁止成员级 `var` 充当函数间隐式信道。
- 结果尽早聚合：不留"半成品状态"跨段流转（先建空 list、三个 if 各塞一点、最后再加工——加工动作离数据源头越远越难读）。
- 布尔标志变量只在条件复杂到值得命名时引入；能用枚举/sealed 表达的状态不要用多个布尔拼。

## 7. 上手路径（新人 15 分钟测试）

- 新人 15 分钟能否定位"改这个功能动哪个文件"：入口点（路由表/导航图/Manifest/模块 README）清晰、模块名与业务名对应。
- 每个文件顶部一句话说明它是什么、和谁协作（KDoc 规范归 `aaaaa-xxf-comment-guidelines`，此处只要求存在目的句）。
- **最小惊讶**：函数行为与名字严格一致——名字带 `get` 就不许有副作用，`load` 不许悄悄缓存写穿，`check` 不许返回结果。行为超出名字范围时要么改名要么拆函数。
- 错误消息可自助定位：异常/日志带够上下文（哪个 id、什么状态、什么输入），新人靠报错就能找到现场，不需要打断别人。

## 8. 新读者模拟检验

交付前随机挑改动文件做一次：

1. 只读 diff 上下文 ±30 行，能否向同事说清这段代码"做什么、为什么"？
2. 编排函数逐行读，每行能否读出一个意图？
3. 有没有哪一行需要"停顿反推"？（回看上文、数括号、脑内展开嵌套——都算）停顿处就是重构点：命名、拆函数或加中间变量。
4. Grep 文中新出现的概念名，是否与库内既有词汇冲突或同义？
