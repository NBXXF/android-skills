# UI 设计稿对齐

## 核心目标

实现 Compose UI 时同时满足两件事：默认机型上尽量贴近设计稿像素效果，多窗口尺寸和动态内容下不崩、不挤、不遮挡、不写死。不要为了单张截图对齐而牺牲真实设备适配。

## 先取设计真值

1. 明确设计来源：Figma/Figama、MasterGo、蓝湖、摹客、截图或产品口述。
2. 记录设计稿基准画板宽高、关键节点尺寸、间距、字号、颜色、圆角、阴影、图片比例、状态栏/导航栏处理。
3. 有设计工具数据时，以节点坐标、尺寸、文本、颜色、资源为准；不要凭视觉大概估。
4. 只有截图或口述时，先声明哪些值是推断值，并优先使用现有项目样式、dimens、主题 token 和邻近页面规范。
5. 存在 Figma/MasterGo 工具能力时，优先获取节点截图或 DSL/metadata，并在实现后用运行截图对照。
6. 编写 Compose UI 前，先按下方“图标与图片资源导出”规则获取设计稿原始资源；节点截图只用于对照，不能代替资源导出。

## 像素对齐规则

- 以设计稿基准宽度换算 Android `dp`，不要直接把设计稿 px 当成代码常量；确认设计稿是否是 1x、2x、3x 或 Android dp 画板。
- 关键视觉锚点必须对齐：页面左右边距、顶部起点、卡片宽高、头像/封面比例、按钮高度、分割线、图标尺寸、文本 baseline、列表 item 间距。
- 颜色、字号、圆角、间距优先复用资源：Compose theme、typography、spacing token、`colors.xml`、`dimens.xml` 或项目既有 modifier/组件参数；不要在多个 composable 中散落魔法数字。
- 图标和图片必须使用设计稿导出的原始资源，按下方规则选择 SVG 转 VectorDrawable XML 或 3x PNG；禁止擅自使用 Material Icons、其他内置图标、手绘近似图标或占位资源替代。
- 允许 1dp 级别的 Android 渲染差异；超过这个范围要么修正，要么在最终说明里解释原因。

## 图标与图片资源导出

### 强制规则与资源选型

编写 Android Compose UI 时，必须优先从设计稿下载原始图标和图片资源。具备设计工具或导出接口能力时，自动从对应设计节点导出并落入目标模块资源目录，不把可自动完成的导出工作转交给用户。

| 资源类型 | 导出与转换 | 存放目录 |
| --- | --- | --- |
| 简单矢量图标 | 优先导出 SVG，转换为 Android VectorDrawable XML，核对转换后的视觉效果 | `res/drawable/` |
| 复杂渐变、阴影、模糊、滤镜等转换后无法准确还原的图标或图片 | 从原设计节点导出 3x PNG；SVG 转换不兼容或视觉失真时也使用此方案 | `res/drawable-xxhdpi/` |

- 资源选型优先 SVG 转 XML；不能仅因转换麻烦而改用内置图标，也不能为了保留矢量格式而删减原稿效果。
- 必须保持设计稿的颜色、尺寸、形状、透明度、渐变、阴影及其他视觉效果，不允许自行绘制近似路径、用字符或 emoji 代替图标、使用 AI 生成的近似图标或占位资源完成设计还原。
- 3x 以目标逻辑尺寸为基准：例如 24dp 的资源对应 72 × 72px PNG。先核对画板倍率，避免将已有 2x/3x 稿重复放大；不得把低清截图放大后冒充 3x 原始导出。

### 执行流程

1. 根据设计节点列出本页图标和图片，确认节点标识、目标逻辑尺寸、颜色及效果；项目已有资源只有经核对与设计原稿一致时才可复用。
2. 自动导出适用资源的 SVG，并转换为 VectorDrawable XML；保留路径、填充、描边、透明度、viewport 与宽高比。不能只改文件扩展名，也不能直接把 SVG 放入 `res/drawable/` 当作 VectorDrawable 使用。
3. 对照设计节点预览转换结果。发现不支持的 SVG 特性、效果丢失或视觉失真时，从同一原始节点重新导出 3x PNG，保留透明背景和阴影/模糊所需边界，避免裁切效果。
4. 将 XML 放入目标模块 `res/drawable/`，将 3x PNG 放入 `res/drawable-xxhdpi/`，按项目资源命名规范接入 Compose。多色或原色资源不得被默认 tint 覆盖，使用 `Icon` 时应按需设置 `tint = Color.Unspecified`；图片缩放与裁剪不得改变原稿比例或截断效果。
5. 在目标尺寸下对照设计稿与运行截图，检查颜色、尺寸、形状、边缘、透明度、渐变和阴影。编译通过不代表资源转换或视觉还原通过。

### 资源缺失或导出受阻

- 只有页面截图、缺少源设计权限、导出接口不可用或原始资源缺失时，明确报告受阻节点和所缺资源，并请求原始资源或可访问的设计来源；可以继续不依赖这些资源的布局工作。
- 原始图标或图片缺失、无法导出时，必须在生成代码中对应的 Compose 资源引用或待接入位置紧邻添加 `// TODO: ...` 注释，注明缺失资源用途、设计节点（未知则注明待确认）、预期资源名/路径和待完成的导出接入事项；不能只在最终回复或文档中记录。TODO 使用注释，不向产品界面展示，也不能引用尚不存在的资源导致编译失败。
- 禁止静默回退到 Material Icons、其他内置图标、手工近似绘制或占位资源，也不能把未完成资源还原的页面报告为已对齐。
- 加载态、空态和失败态中的占位策略仅用于产品状态表达，不能替代设计稿中应交付的真实图标与图片。

## 不要写死

- 不要写死屏幕宽高、状态栏高度、导航栏高度、刘海高度、列表数量、文案长度、图片真实尺寸或接口返回顺序。
- 不要用 `screenWidth - 37`、固定 `offset` 堆坐标、固定 item 总数来模拟设计稿。
- 不要让列表 item 依赖父页面某个固定高度；列表应能处理 0/1/少量/大量数据。
- 不要把服务端文案、用户名、价格、标签、按钮文案当成固定长度；长文本必须有换行、截断或自适应策略。
- 不要把标题、平台名、用户名、页面主标题这类单行文本的可视宽度写成常量上限（`widthIn(max = 166.dp)`、固定 `width`）。除设计稿明确标注了文本框宽度外，单行文本宽度必须由父容器剩余空间决定；常量上限等于提前截断，本可完整显示的内容会被省略。
- 不要为了某个机型截图好看而破坏小屏、横屏、折叠屏、平板或字体放大后的布局。

## 多机型适配

- 窗口尺寸断点、canonical layouts、导航容器选型、折叠屏铰链、edge-to-edge 强制行为和 manifest 大屏配置，按 `references/compose-adaptive-window-standards.md` 的官方口径执行。
- 优先使用 `Modifier.fillMaxWidth`、`weight`、`widthIn/heightIn`、`requiredSize`、`aspectRatio`、`BoxWithConstraints`、adaptive grid、window size class 和 `WindowInsets` 表达布局关系。
- "按比例适配"类需求先定缩放作用域：默认只缩放被点名的那层容器盒子（如卡片 `aspectRatio` 随宽度定高），子组件的字号、字距、图标尺寸、功能性行高与内边距保持设计稿原值；整组件 ×scale 仅限装饰性整组、固定栅格宽度对、装饰图等明确类别，不得从一句"这个 XX 按比例"扩展到全部子组件，也不得把仓库既有 ×scale 先例当通用许可。
- 容器按宽高比锁高后内容必须有让位方案，这是产品决策：动手前按编号列方案（整组等比 / 指定弹性件自动收缩 / 间距动态压缩 / 容器放宽可滚动）让开发者选择并记录；禁止默认任一方案（细则见 `references/compose-adaptation-scenarios.md` 的「比例缩放的作用域边界」与「宽高比容器的内容让位方案」）。
- 小屏至少检查 320dp/360dp 宽；主流机型检查 390dp/411dp 宽；有横屏、平板、折叠屏入口时按官方测试窗口基准检查更宽断点。
- 页面容器要处理系统 inset：状态栏、导航栏、沉浸式、刘海、水滴屏、手势导航、软键盘；Compose 中优先用 `Modifier.windowInsetsPadding`、`statusBarsPadding`、`navigationBarsPadding`、`imePadding` 或项目既有 inset 封装。
- 字号用 `sp`，但紧凑控件要验证 font scale 1.15/1.3；触及通用组件或有无障碍要求时按官方口径加测 200% 最大字号（Android 14+ 系统上限）；重要按钮、`TextField` 和输入框不能因为字体放大而文字被裁。
- 图片区域用明确比例或约束，不用只在一个设备上看起来刚好的固定高度；头像、封面、banner、瀑布流图片要明确 `ContentScale` 和裁剪策略。
- 深色模式、多语言、RTL 不是默认必做，但改动触及通用组件或公开库时要确认是否已有要求。

## Compose 动态布局原则

实现任何文本、图片或内容卡片时，先判断组件尺寸来自哪里：设计稿固定值、父容器约束、内容自然尺寸、窗口尺寸、服务端数据或图片真实比例。不要只按当前样例文案和当前截图写一个固定宽高。

- 组合外层优先接收父级约束并向内传递：用 `Modifier.fillMaxWidth`、`widthIn/heightIn`、`wrapContentHeight`、`aspectRatio`、`weight` 和 padding 表达关系，避免到处读取屏幕宽度后手算。
- `Row` 中的动态文本要明确压缩顺序：固定图标/按钮先占位，文本用 `weight` 承接剩余空间，用 `maxLines`、`overflow` 定义溢出策略；不要让长文本把右侧按钮、价格、角标挤出屏幕，也不要用常量 `widthIn` 提前限制文本宽度。
- `Column` 中的动态内容要允许父容器增高、滚动或折叠；不要用固定高度裁掉多行文本、错误提示、输入框 helper text 或状态区。
- `Text` 必须明确 `maxLines`、`overflow`、`softWrap`、`lineHeight` 和对齐方式；长文、富文本、emoji、数字、价格、日期要用最长合理样例验证。
- 图片用 `Modifier.aspectRatio`、稳定占位和明确 `ContentScale`；远程图不能依赖原图比例刚好符合设计稿。
- Lazy 列表 item 要按内容独立自适配，使用稳定 key，避免 item 高度变化导致状态错乱、滚动跳动或重组成本失控。

### 文字适配是写 UI 的默认步骤（组件优先，不做页面级补丁）

任何涉及文本的 UI 任务，动手前先回答三件事，结论要体现在实现或注释里：

1. **这段文本是什么语义**：只读读数（金额/账号/手机号/时间/数量/按钮文案）、多行说明，还是可交互富文本。
2. **放不下时怎么办**：吃满宽度 → 缩字号 → 省略/换行，按本文「单行」「多行限行」两节的三级策略走，不临时发明第四种。
3. **这是第几次遇到**：同一类语义文本在第 2 处出现、或明显会复现时，必须收口到组件，不能在调用点再写一遍 `BasicText + TextAutoSize`。

**默认动作**：只读单行文本一律用 `AutoFitText`；不要手写 `TextAutoSize.StepBased`，不要把缩字/省略策略复制进业务文件。

**判断"一类问题"还是"个例"**：

- **一类问题**（同一语义文本多处出现、同一套"先吃满→缩字→兜底"策略反复出现、同一类定高容器裁字）→ 抽/扩组件，放到共享 UI 层（`xxf_android/core/lib_compose` 或 feature 的公共 ui 包），一次性替换所有同类调用点，并在变更说明里列出被替换的位置。
- **个例**（只影响单页的排版关系：间距、层级、一次性背景/定位）→ 就页面改，不抽组件；在注释里写明"为什么不成类"，避免下次被误当模式复制。

**组件不够用时按这个顺序扩，不要绕开组件另起一套**：

1. 先用现有参数表达：`maxLines`（行数）、`overflow`（省略/裁剪）、`minFontSize`（下限）、`em` 行高/字距。
2. 参数确实缺失 → 给组件加**"不传即旧行为"的增量开关**（如 `textStyle` 承接 `fontFamily`/`drawStyle`/`shadow`，`autoSize` 承接双层描边共享测量），默认值一律不动。
3. 语义上已是另一类组件（描边艺术字、带图标或富文本的金额、格宽由内容反推的网格）→ 抽新组件放共享层，复用同一套策略，不要复制粘贴后各改各的。

**反模式（评审直接打回）**：业务代码里出现 `TextAutoSize.StepBased`；同一套策略在 2 个以上文件各写一份；用固定高度 + `clip` 裁字；用常量 `widthIn(max = …)` 提前截断；为单页问题复制一个组件副本。审查时先跑 `grep -rn "TextAutoSize" --include=*.kt <模块>`，业务模块命中且不在组件内部，基本就是没收口。

### 单行标题与名称的宽度适配（默认策略）

设计稿把标题、平台名、用户名、弹窗主标题画成单行，且没有说明放不下时怎么办，默认按下面三级顺序处理，不自创第四种，也不跳级：

1. **先吃满可用宽度**：标题行用父容器剩余空间承接（`Modifier.fillMaxWidth()` + 文本 `Modifier.weight(1f, fill = false)`），短文本仍按原对齐方式居中/紧跟，不加常量 `widthIn(max = …)` 提前收窄。固定元素（图标/Logo/箭头/按钮）保持设计尺寸，不参与压缩。
2. **再缩字号**：用 `AutoFitText`（内部即 `TextAutoSize.StepBased(minFontSize, maxFontSize = 设计字号, stepSize = 0.5.sp)`，业务代码不手写）。`maxFontSize` 就是设计值，默认不改；`minFontSize` 取设计字号的约 60%~75%，且不低于可读下限 —— 读数类（金额/账号/名称/时间）一律给到 8sp（`AutoFitText` 的内置下限，再低没有意义），宁可缩字也不提前省略；只有纯装饰大标题才可自行抬高。
3. **最后兜底**：缩到下限仍放不下才 `maxLines = 1` + `softWrap = false` + `overflow = TextOverflow.Ellipsis`；业务明确允许折行时，兜底改为换行并同步放宽行高与父容器节奏。

例外与澄清：设计稿明确标注了标题文本框宽度时按标注实现，但仍要说明放不下时的策略；省略会丢失关键信息（平台名、账号、金额、地名）或需从单行改多行时，列方案让开发者选，不默认拍板。代码模板、最小字号口径、`BasicText` 与 material3 `Text` 的差异坑见 `references/compose-adaptation-scenarios.md` 的「文字超长的适配策略」。

自查信号：截断后的省略号两侧还有明显空白，或可用宽度远大于文本实际宽度，几乎都是先被常量宽度上限截掉了，先查宽度而不是先改字号。审查已实现页面时，先跑 `grep -rn "widthIn(max" --include=*.kt <模块>` 逐个确认该常量的出处：有设计标注则保留并在注释写明节点，没有则按上述三级策略改造。

自适应文本组件 `AutoFitText`（手机号、邮箱、昵称、金额/余额、数量、时间/时长、按钮/标签、说明文案）：同一类文本在多个位置出现时一律用它承接上面的策略，业务只传设计字号、颜色、字重、字距，不再各自 `BasicText + TextAutoSize`。**默认策略是契约**：`maxLines = 1` + `softWrap = false`（单行不折行）→ `autoShrink = true` 按 0.5sp 步进缩字号（只缩不放）→ 缩到 `minFontSize`（不传时设计字号 60%，且不低于 8sp 可读下限）→ 仍放不下才 `overflow = Ellipsis`；扩展时不许改这些默认值，只能加"不传即旧行为"的开关。**金额、账号、时间/时长、按钮这类"必须一行读完"的字段必须用默认值**，只有说明/条款/2~3 行标题才允许 `maxLines = 2~3`，且正文下限给到设计字号 80% 以上。放宽后要保证父容器给出有界宽度（否则不会折行），组件按 `maxLines > 1` 自动打开 `softWrap`——`softWrap = false` 在 Compose 内部会把行数强制压回 1。默认整份继承 `LocalTextStyle`（字号/字重/字距/行高/对齐，颜色按 `LocalTextStyle` → `LocalContentColor` 回落）：`BasicText` 不读主题，漏字体家族会静默退回系统字体，漏行高会让行盒变矮、纵向节奏错位。两个扩展口：`textStyle`（最后 merge、同名字段优先，承接 `fontFamily` / `drawStyle` 描边 / `shadow` / `platformStyle`）；`autoSize`（外部 `TextAutoSize`，传了就不再按 `minFontSize`/`autoShrink` 自建，用于描边+填充双层共用一次测量——两层除颜色/`drawStyle` 外的参数必须一致）。下限要防无效配置：`minFontSize` 大于等于设计字号时按 60% 回落，否则 `floor == fontSize` 会让 autoSize 静默关闭、长文本直接省略。缩字号后仍需成立的度量（行高、负字距）必须用 `em`；行高明显小于字号（`< 1em` 或固定 sp 小于字号）会被组件当无效配置丢弃、回落自然行高。自动缩放只按"末行是否被省略"判定，**不看高度**：固定 dp 高的容器要用 `dp.toSp()` 给字号物理封顶，不能指望组件按高度缩字。金额要扫全：`formatLocalizedAmount()` 直出的纯读数（余额、列表金额、播报金额、待打款）走组件；`+%s` 模板或整句拼接的按拼接文本处理，但要确认它所在容器不会裁字。

已落地的共享实现：`xxf_android/core/lib_compose` 的 `com.xxf.compose.ui.text.AutoFitText`（`BasicText` + `TextAutoSize`，需 Compose UI ≥ 1.8，对应 `compose-bom` 2025.05.00），发布为 `com.NBXXF.xxf_android:lib_compose`（经 `lib_view` 传递依赖）。跨 App 复用直接依赖该产物，**不要再复制副本**；Reels 已删除本地副本、统一走 maven 版本。改组件前先读它 KDoc 的「默认策略（契约，扩展时不许改默认值）」一节。

### 多行限行文本（maxLines = N）的适配（默认策略）

设计稿给了行数上限（"最多 3 行""超出省略"）时，目标从"塞进一行"变成"塞进 N 行"，顺序随之变化，不能照抄单行：

1. **先吃满宽度**：同单行规则。宽度被常量上限收窄时，多行更容易多出一行、提前触顶。
2. **让行数在 1..N 内自由伸缩**：`maxLines = N` + `softWrap = true` + 显式 `lineHeight`，容器高度跟随行数。限行只能用 `maxLines`，不能用固定高度 + `clip` 裁剪——那是裁字不是省略，字体放大后裁得更多且没有省略提示。
3. **超 N 行再降级，按语义二选一**：内容要尽量完整（标题/说明/状态提示）→ `TextAutoSize` + `maxLines = N`，下限取设计字号 60%~85%，到下限仍超才末行省略；内容可截断或可交互（列表副标题/简介/评论/地址）→ 保字号不缩，`maxLines = N` + 末行省略，业务允许时用"展开/收起"替代省略。
4. **等高要求**用 `minLines = N` 或固定 item 高 + `maxLines = N`，并验证 fontScale 1.3 不裁字。

与单行的关键差异：单行只有"缩到 1 行"一条路，省略即丢全部信息；多行本身能用行数吸收溢出，末行省略只丢尾部，所以缩字号的优先级更低、对省略的容忍度更高。另注意 `autoSize` 必须与 `maxLines = N` 同时给（否则只按宽度收缩、行数无界），`overflow` 必须显式 `Ellipsis`（默认 `Clip` 没有省略提示）。共享层直接用 `AutoFitText(maxLines = N, minFontSize = …)` 即可承接第 2~3 步。细则与代码见 `references/compose-adaptation-scenarios.md` 的「多行限行文本（maxLines = N）」。

### 单行文本在有界容器内的垂直居中（默认策略）

同时满足以下条件时，文本**必须垂直居中**，不允许靠上下 padding 目测凑：

1. 内容单行（含单行输入框、单行标签）；
2. 直接父容器有确定高度或最小高度（`height`/`heightIn`/`minHeight`），高度不是由文本自身撑出来的；
3. 容器有可见边界：背景色、渐变、描边、圆角、分割线；
4. 容器以文本为主体，可能附带固定尺寸的前缀/图标/箭头（如 "+1" 区号框 + 手机号、带背景的标题栏、标签胶囊、只读字段）。

做法：

- 用容器自身对齐：`Box(contentAlignment = Alignment.Center/CenterStart)`、`Row(verticalAlignment = Alignment.CenterVertically)`、`Column(verticalArrangement = Center)`；不要写 `padding(top = 4.dp, bottom = 2.dp)` 这类补偿。
- 高度与内边距要写在**同一个**有界容器上：`Box(Modifier.heightIn(min = 42.dp).padding(h, v), contentAlignment = CenterStart)`，而不是把 `heightIn` + `padding` 挂在更外层、让内层文本顶格。
- `BasicTextField` 必须走 `decorationBox`：内层文本默认贴内容区顶部，最小高与内边距写在外层 modifier 上对居中无效。
- 居中前先消除字体度量的不对称：显式 `lineHeight` + `PlatformTextStyle(includeFontPadding = false)`；否则 ascent/descent 自带的上大下小会让几何居中看起来仍偏 1~2dp。

例外：设计稿明确画成非居中（下划线输入框文字贴基线、底部对齐角标、多行文本首行对齐）时按标注实现，并在注释写明节点与对齐依据；多行文本是"整块居中"还是"首行固定"属口径歧义，按澄清处理。

自查信号：文本 ink 到容器上下边缘的留白肉眼不等（尤其上方明显更紧），几乎都是"把高度和内边距加在外层、内层文本却顶格"。验收要量这个差值，两侧差 ≤1dp 才算通过——只核组件总高是否等于设计值会漏掉这类 bug（高度全对、文字就是偏上）。

## 列表和动态内容

- Lazy item 必须按内容独立自适配，不依赖屏幕上固定出现几个 item。
- `LazyVerticalGrid`、瀑布流、横滑列表要根据可用宽度、最小 item 宽度和设计间距计算列数/跨度；不要固定只适配一个设备。
- 使用稳定 key、项目既有分页/局部刷新方案和稳定状态持有方式，避免为了 UI 对齐牺牲列表性能或造成状态串位。
- 覆盖加载态、空态、错误态、骨架屏、分页尾部、无更多、刷新中、图片加载失败、权限缺失等状态。
- item 文案、标签、角标、按钮、头像、封面缺失时要有占位或隐藏策略，不能留下错位空洞。


## 文字内边距问题
- compose Text组件默认带内边距,会导致实际间距和其他组件有问题,尤其是figma/master-go 设计图读取的dsl, 建议都先去出内边距之后再计算核对
- 去除内边距的代码如下:
```kotlin
   style = TextStyle(
                        platformStyle = PlatformTextStyle(
                            includeFontPadding = false
                        )
                    )
```


## 实现优先级

1. 先复用项目已有 Compose 组件、theme、typography、spacing token、颜色和图片加载封装。
2. 再新增局部 composable、modifier 或资源，命名跟随邻近模块。
3. 最后才新增自定义 Layout、`SubcomposeLayout` 或复杂测量逻辑；新增时必须考虑测量次数、重组成本、主线程开销和生命周期。
4. 优先用 `Row`、`Column`、`Box`、`Lazy*`、`FlowRow`（Compose ≥ 1.11 可经用户同意换 `FlexBox`）、`ConstraintLayout` 和 modifier 表达静态结构；运行时只计算真正依赖 constraints、数据或 inset 的值。
5. 复杂页面先对齐布局骨架，再补资源、动效和状态，不要一开始堆 magic number。

## 复核清单

实现后至少做以下检查，并在最终说明里报告结果或阻塞原因：

- 设计稿基准尺寸和目标机型宽度是否明确。
- 默认机型截图与设计稿关键间距、尺寸、颜色、字号是否对齐。
- 图标和图片是否来自原始设计节点，是否记录 SVG 转 XML 或 3x PNG 的选型及资源路径，目录与密度是否正确。
- 缺失或无法导出的资源是否在对应代码位置添加了说明用途、设计节点、预期资源路径和待办事项的 TODO，且未引入不存在的资源引用。
- 转换后颜色、尺寸、形状及视觉效果是否与原稿一致，是否避免默认 tint、裁切和错误缩放造成失真，是否不存在擅自替换的内置图标、近似绘制或占位资源。
- 小屏、主流屏、字体放大下是否无重叠、无遮挡、无裁字。
- "按比例适配"类改动是否只落在被点名的作用域（容器盒子），子组件字号/字距/间距没有被顺手 ×scale；等比容器的内容让位方案（整组等比/弹性件/间距压缩/容器放宽）是否经过开发者选择并记录，而不是默认。
- 文本组件是否明确单行/多行/截断/换行/动态高度策略，外层容器是否能承接宽高变化。
- 单行标题/名称是否先吃满父容器宽度（无设计标注却存在常量 `widthIn(max = …)` 或固定 `width` 即为未通过）；缩字号是否设了可读下限并写明取值依据；兜底是省略还是换行是否明确，且与设计稿单行口径一致。
- 多行限行是否用 `maxLines = N` 表达（用固定高度裁剪即为未通过），`autoSize` 是否与 `maxLines` 配套（只缩字不限行会让行数无界），`overflow` 是否显式 `Ellipsis`，容器高度是否随 1..N 行变化或按需 `minLines` 等高。
- 单行文本（手机号/邮箱/昵称/金额/数量/时长/按钮文案）是否复用一个公共策略组件（业务只传样式）；金额类要扫全：列表/播报里的纯金额字段（如 `record.amount`）同样要走组件，不要只改主视觉上的大金额；带 `+%s` 模板或整句拼接的金额按拼接文本处理，不算纯读数；金额/账号/时长/按钮是否仍用 `maxLines = 1` + `Ellipsis` 默认值，多行用例是否由父容器给出有界宽度；默认样式是否整份继承 `LocalTextStyle`（含字体家族、行高、对齐与颜色回落顺序）；`minFontSize` 是否确实小于设计字号（等于或大于会让 `autoSize` 静默失效）；缩字号后仍需成立的负字距是否用 `em`；定高容器是否用 `dp.toSp()` 做了字号封顶。
- 是否收口到组件：业务模块里是否残留手写 `TextAutoSize.StepBased` 或第二份缩字/省略逻辑（`grep -rn "TextAutoSize" --include=*.kt <模块>`，命中且不在组件内部即未收口）；`AutoFitText` 不够用时是加"不传即旧行为"的参数或抽新组件，还是在调用点另起一套；为单页问题复制的组件副本是否已合并回共享层；新组件是否有"默认策略"KDoc 契约，避免后续被逐个改默认值。
- 单行文本在有界容器（定高/最小高 + 背景/描边/圆角/分割线）内是否垂直居中：文本 ink 到容器上下边缘的留白差是否 ≤1dp；靠 `padding(top/bottom)` 手调、或 `BasicTextField` 内层文本顶格（`heightIn`/`padding` 挂在外层而非 `decorationBox`）即为未通过。
- 图片组件是否明确比例、占位、失败态、裁剪和远程图片极端尺寸策略。
- 横屏、分屏、多窗口、平板、折叠屏或更宽窗口下是否有合理布局，不依赖设备型号硬判断。
- 旋转、折叠开合、窗口 resize 后滚动位置、输入内容、选中态、播放进度是否保留；是否未用 configChanges/screenOrientation 掩盖状态丢失（状态保持细则见 `references/compose-adaptive-window-standards.md`）。
- 本地化、RTL、资源限定符、深色模式和默认资源兜底是否在触及范围内处理或说明不适用。
- 交互态、禁用态、选中态、弹窗/浮层、键盘弹起、返回恢复后是否保持布局稳定。
- 列表 0/1/多条、长文案、缺图、加载失败、分页态是否可用。
- 状态栏、导航栏、软键盘、沉浸式区域是否正确处理。
- UI 资源或 Compose 代码改动是否执行对应模块 `assembleDebug` 或更窄可行验证。
- 触及 Lazy 列表、图片、自定义 Layout/绘制、动画时，同时按 `aaaaa-xxf-android-performance-gate` 做性能门禁。

## 输出要求

最终回复要说明：对齐了哪些设计要点、哪些尺寸/资源没有写死、验证过哪些机型或状态、是否有设计稿缺失或 Android 渲染导致的残余偏差。图标和图片还需说明设计来源/节点、导出格式、最终资源路径、SVG 转 XML 或回退 3x PNG 的原因，以及视觉复核结果；无法导出的资源必须列为未完成项，并提供对应代码 TODO 的文件路径和位置。
