# 多来源冲突裁决：产品需求 / 设计图 / bug 单 / 产品口述 / 现有实现

> 本文解决一件事：**同一件事（一个 UI 属性、一条业务规则、一个文案口径）在同一范围内，只能有一个生效值或生效行为，且这个值不能由 AI 推断出来。**

## 适用范围

产品需求（PRD）、设计图、bug 单、产品口述、现有实现这五类来源，对同一件事给出不同答案时，一律走本文流程。三类对象共用同一套判定，只是"条目"的建模方式不同：

| 对象 | 条目单位 | 权威基准 `D` | 画像 |
|---|---|---|---|
| UI 取值 | 组件/区域 + 属性 + variant/状态 | 设计稿节点取值 | 附录 A |
| 业务规则 | 规则场景 + 四要素（触发条件 / 判定条件 / 预期行为 / 适用范围） | 需求文档对应章节 | 附录 B |
| 文案口径 | 文案 key + 语言 + 场景 | 需求/文案表条目 | 附录 B.6 |

**三方矛盾是常态，不是异常**：PRD 写了一套、设计图画了另一套、bug 单按线上表现又提了第三套，三者都不会互相回改。所以判断依据不能是"哪份文档更权威"，只能是"这条有没有已登记裁决"。

> 本文件放在 `aaaaa-xxf-ui-design-alignment` 下是因为最初只服务 UI 对稿，但内容不依赖 Compose/设计稿知识，业务规则任务可以直接读，不必先加载 UI 规范。

## 速查（6 条）

1. 只改本次点名的问题条目；没点名的，文档里看见也不改，只写进交付差异。
2. 不在本次范围内 → 保持现状；在范围内且无冲突 → 有登记用登记值、无登记用基准值、都没有保留现状；有冲突看第 3 条。
3. 登记值与基准值冲突，而本次没给出该条目的明确目标值 → **停下来问**，不许任选一方。
4. 要问就一次问完，每条给出基准值、生效值、范围、来源、影响面。
5. 判断依据只有三种：登记表、带条目 ID 的代码注释、权威基准（设计节点/需求章节）；登记表与证据统一落在 `<module>/docs/vibe-coding-clarify/`，聊天里的结论不算数。
6. 交付必须分四类：改了 / 按裁决保留 / 有差异未处理 / 待裁决。

## 0. 不解决的问题与失效表述

这不是"产品需求和设计图谁更大""bug 和 PRD 谁更大"的排序题。**本文件不定义任何全局优先级。**

以下表述一律视为违规，无论出现在文档、注释还是对话里：

1. "设计稿是唯一真值" —— 忽略了已登记的产品变更和 PRD。
2. "PRD 是唯一真值" —— 忽略了 PRD 不更新、bug 单与产品口述已经改了口径。
3. "以最新 bug 单为准" —— 忽略了 bug 可能只覆盖一条规则、一个场景。
4. "以代码现状为准" —— 现状可能是历史遗留错误。
5. "bug 只是复现，以 PRD 为准" —— 忽略了大量需求变更只经 bug 单或口述下发。
6. "bug 优先于 PRD / PRD 优先于 bug" / "PRD 优先于设计图 / 设计图优先于 PRD" —— 都没有这个规则。
7. "先按某一方改，有意见再说" —— 静默回改已裁决值。
8. "PRD 没写就是没要求" —— 缺失同样是未决，不是允许自由发挥。

正确的表述只有一种：**该条目不在本次写入范围时保持现状；在范围内时，本次给了目标值就用目标值，没给但存在生效裁决且与基准值冲突就停下来问，两者都没有才按基准值。**

## 1. 三条铁律

### 铁律一：写入集合 = 本次点名范围（最小写入）

一次任务能改的**条目**（UI 属性 / 业务规则 / 文案），等于本次请求**明确要求的范围**；默认这个范围只含**点名的条目**。PRD、设计图、bug 单里看得见但没点名的条目，即使与代码不一致，也**不许改**。

只有两种情况会扩大范围，且都必须由请求文字明确表达：

1. 首次实现（base 分支不存在该页面/该规则）→ 全量按基准值实现；
2. 明确说"整块按新稿重做"或"这块需求整体对齐一下" → 范围为整块，但**每个与生效裁决冲突的条目仍需单独裁决**（§2.3），范围扩大不等于授权覆盖裁决值。

这条铁律针对的真实事故：用户只问"这个 spacer 是不是缩放了"，AI 顺手把金额字号从 16sp 改成 21sp；反过来，用户只让改间距，AI 把整块按设计稿重排，把已裁决的字号改回设计值。业务侧同型事故：用户只让改"退出提现页是否弹窗"，AI 顺手把整条"未绑账号能否提现"的规则按 PRD 原文改回去，推翻了上一轮的裁决。

判定见 §2。

### 铁律二：生效值只能来自"已登记裁决"，不能来自推断

一个值或一条行为成为生效值，只有两条路径：

1. 本次请求中用户/产品**明确给出该条目的目标值或目标行为**；
2. 该条目在裁决登记表中存在**状态为生效、范围匹配**的记录。

除此之外的任何来源——代码现状、git 历史、相邻页面、截图目测、PRD 原文、服务端当前表现、AI 认为"这样更合理"——都不产生生效值。

**禁止事后合法化**：不允许先改代码，再补一条"裁决记录"来证明改动正确。裁决必须是用户/产品已经做出的表态，AI 只能记录，不能发明。

### 铁律三：无记录的不一致 = 未决冲突 = 必须问

发现"代码行为 ≠ 基准行为"且查不到任何裁决记录时，不默认任何一方：不默认按 PRD 改，也不默认保留代码值。停下来问来源，再决定。

例外只有一种：该条目**不在本次写入集合内**——这时不改，也不打断任务，只在交付时报告（§13）。

## 2. 什么算"点名"

### 2.1 按任务类型决定范围

| 任务类型 | 判定 | 写入集合 |
|---|---|---|
| 首次实现页面/组件（base 分支不存在） | 无历史值，无冲突可能 | 设计稿覆盖的全部属性 |
| 增量改稿（已存在且已合入/上线） | 有历史值，可能已有裁决 | **仅点名属性**；明确说“整块重做”则扩到整块，冲突属性仍逐个裁决 |
| 新增一条业务规则（需求有、代码无） | 无历史行为，无冲突可能 | 该规则的全部分支与边界 |
| 修改已有业务规则（已上线） | 有历史行为，可能已有裁决 | **仅点名的条件/场景**；未被点名的分支保持现状 |

“有历史行为”不等于“有裁决”：没有登记的就是未决，按 §5.3 问。

### 2.2 UI 的点名判定

| 算点名 | 说明 |
|---|---|
| 请求文字里出现的属性名（"间距""字号""高度""颜色""圆角""图标"） | 中文/英文/口语均可，只要属性可识别 |
| 请求里被红框、箭头、标注圈出的属性 | 需能在截图上确认圈选范围 |
| Dev Mode 中被测量、被选中、被标数值的属性 | 以标注面板实际显示的属性为准 |
| 请求文字写明的具体值（"改成 12dp"） | 值本身即点名，且构成目标值 |

| 不算点名 | 说明 |
|---|---|
| 设计稿画面上可见、但请求没提的属性 | 最常见的事故来源，一律不动 |
| "整体看一下""对一下稿""有没有问题" | 这是审查请求，不是写入请求；输出差异报告 + 建议改动清单，确认后再改 |
| "按新稿重做这一块" | 范围=整块（§2.3），但**每个冲突属性仍需单独裁决**，不等于授权覆盖裁决值 |
| 相邻元素新增/删除/位移 | 属于新需求，需确认是否本次做 |
| 用户只描述了现象（"看起来怪"）没指属性 | 先定位属性，再按点名处理 |

### 2.3 范围指令不等于值指令

"整块按设计稿重做""这块需求整体对齐"给出的是**范围**，不是**目标值**。它不是点名，因此不构成 `P`；但它把写入集合扩到整块。此时：

- 基准值与裁决一致的条目 → 照做；
- 基准值与裁决不一致的条目 → 收集起来，**批量问一次**（§11），不能因为"用户说了按设计稿/按 PRD"就整块覆盖。

### 2.4 业务规则的点名判定

| 算点名 | 说明 |
|---|---|
| 请求文字里出现的规则要素：触发条件、判定条件、状态、结果、上报时机、去重维度、有效期 | 只要该要素可识别 |
| 请求里明确写的目标行为（"退出时不要推进进度""未绑也要允许提现"） | 行为本身即点名，且构成 `P` |
| 请求指向的代码位置（类/方法/页面）但没说行为 | 需先定位该位置承担哪几条规则，再把规则名念给用户确认，不能默认整类都改 |
| 缺陷单的复现步骤 | 复现步骤圈定的场景即点名范围，不扩散到相邻场景 |

| 不算点名 | 说明 |
|---|---|
| PRD 里写了、但请求没提的规则 | 一律不动，写进交付差异 |
| "把这块逻辑理一下""看看还有没有问题" | 审查请求，输出"规则 × 现状 × 依据"报告 + 建议，确认后再改 |
| "按 PRD 全量对齐" | 范围=整块，冲突规则仍需逐条裁决（§2.3） |
| 用户只描述现象（"这里不对""数据不对"） | 先定位到具体规则与条件，再按点名处理 |

## 3. 每个条目取四个输入

对写入集合内的每个条目（UI 属性 / 业务规则 / 文案），先把四个值摆出来，再判定：

| 记号 | 含义 | UI 取值任务 | 业务规则任务 | 可为空 |
|---|---|---|---|---|
| `P` | 本次请求的目标值/目标行为 | 对话或单据里写明的值 | 对话或单据里写明的要求行为 | 是（只给范围/只说现象） |
| `R` | 已登记的生效值/生效行为 | 登记表中状态=生效且范围匹配 | 同左 | 是 |
| `D` | 权威基准 | 设计节点标注 | 需求文档对应章节 | 是（可能根本没写） |
| `C` | 代码现状 | 源码中的实现值 | 源码/接口实际行为 | 是（首次实现） |

`D` 是"基准"而不是"真理"：它是无裁决时的默认来源，不是最高优先级（§0）。

### 3.1 证据等级（决定 D 能不能直接用）

本分级只用于判断"这条能不能当基准值"，与 `aaaaa-xxf-agent-high-quality-operation` 的 A~E 证据等级不是同一套；用甲乙丙丁避免与输入记号 `D` 混淆。

| 等级 | 来源 | 能否作为 D | 要求 |
|---|---|---|---|
| 甲 | 设计工具节点标注（MasterGo / Figma Dev Mode 等） | 可以 | 记录节点 id + 获取日期 |
| 乙 | 带标注的设计稿截图 | 可以 | 记录截图文件 + 获取日期 |
| 丙 | 聊天截图、自然语言、飞书/缺陷单链接 | **不可以** | 只能作为 `P` 的来源 |
| 丁 | AI 从截图目测/按比例估算 | **不可以** | 只能作为推断值，须标注并让用户确认 |

业务规则的同口径：

- **甲**：带版本号/发布日期的需求文档章节、正式评审结论；
- **乙**：需求文档截图、会议纪要里明确写下的条款；
- **丙**：聊天、口述、缺陷单里的转述（包括"PRD 里就是这么写的"这类无出处的断言）；
- **丁**：AI 从现有代码反推出的"应该就是需求"。

丙、丁级来源不能写成"需求文档/设计值"。把聊天里说的"21"写成"设计值 21sp"、把口述的"应该这样"写成"PRD 规定"，是后续所有对稿混乱的起点。

### 3.2 基准值必须带版本信息

设计稿会改，节点 id 会复用；需求文档会改版，章节号会挪。登记 `D` 时必须同时记版本信息：

- UI：节点 id + 获取日期；
- 业务规则：文档名 + 版本号或发布日期 + 章节号（如 `《网赚逻辑》v2.3 §5.3`）。

下次发现同一来源取值变化，即为"基准已更新"，按 §6 形态 5/6 处理，不能当作没发生。

## 4. 判定表（逐条目执行，确定性）

```text
条目是否在写入集合内？
  ├─ 否 → 不动；若 D≠C，列入交付报告的“未处理差异”（有裁决的附 ID）
  └─ 是 ↓（在范围内 = 本次要处理这个条目）

P 是否有明确值（本次请求直接给出了目标值/目标行为）？
  ├─ 是 → 用 P
  │        ├─ P == R          → 值不变，确认记录仍在生效
  │        ├─ P ≠ R 且 R 存在 → 用户新裁决推翻旧裁决：先追加补充决策、更新条目状态，再改代码
  │        └─ P ≠ D 且 D 存在 → 必须登记覆盖（否则下次对齐会回改）
  │        注：后两条可同时命中（P 既不等于旧裁决、也不等于基准值），两个动作都要做
  └─ 否 ↓（只给了范围、只说了“改一下”、或只描述现象）

R 是否存在且状态=生效、范围匹配？
  ├─ 是 → D 是否也有值且 D ≠ R？
  │        ├─ 是 → 待裁决（§5.1）：无法判断“按基准改”还是“保留裁决”，禁止落代码
  │        └─ 否 → D 有值时用 D（此时 D == R，值不变）；D 无值时保持 R 不变
  └─ 否 ↓

D 是否存在？
  ├─ 是 → 用 D（正常对齐）
  └─ 否 → 保留 C；C 也没有则视为未定义，向用户要值

过程中命中 §5 任一条件 → 该条目置为“待裁决”，禁止落代码
```

### 4.1 判定结果只有六种

| 结果 | 含义 | 是否改代码 | 是否记录 |
|---|---|---|---|
| 按基准改 | 无 P、无冲突裁决，采用 D（D 与 C 不同）。UI 即按设计稿改，业务即按需求改 | 是 | 否 |
| 按本次要求改 | P 明确 | 是 | P≠D 时必须记录 |
| 按记录保留 | 存在生效裁决且本次不动（未点名，或基准值已与裁决一致） | 否 | 否（已有记录） |
| 仅报告不改 | 不在写入集合，或差异需用户知晓 | 否 | 否 |
| 无需改动 | 在集合内，但与基准值/裁决值已一致，无变更 | 否 | 否 |
| 待裁决 | 命中 §5 | 否，先问 | 裁决后记录 |

**没有第七种结果。** 不允许出现"先按某一方改，等用户反馈再调"。

## 5. 必须问的 8 种情况

只有以下情况需要打断用户，其余一律不问，避免把对齐变成连环问答。

1. **条目被点名，但只给了范围没给目标值，且 R 生效、D ≠ R。**
   例：UI——用户说"这个间距不对，按设计调一下"，而该间距有生效裁决 8dp、设计值 12dp；业务——用户说"提现这块规则理一下"，而该规则有生效裁决、PRD 又是另一套口径。
2. **同一条目存在多条互相矛盾的记录**（不同日期、不同来源、值/行为不同）。
3. **代码行为与基准不同，且查不到任何记录与来源注释**（来源不明）。
4. **基准更新导致已有裁决的前提失效。**
   例：UI——原裁决是"宽度不够时缩字号"，新稿把文字区加宽了；业务——原裁决是"接口返回 A 才走 B 流程"，新需求把 A 的判定条件整体改了。
5. **本次要求与已有裁决语义对立。**
   例：已有裁决"超长必须省略"，本次要求"标题要显示完整"；已有裁决"未绑账号也可以提现"，本次要求"必须绑卡"。
6. **共用实现被多处复用，只有一处需求更新。**
   例：Header 被 TAB 与播放页复用只改了播放页；公共 `Service`/`Manager` 被多条业务线调用，只有一条线的规则变了。改共用实现会让其他调用方跟着变，必须确认是否加参数分叉。
7. **PRD 与接口/服务端实际行为不一致。**
   例：需求写"达到 S3 才推进"，接口却已提前下发 `progress=100`。不能默认"以接口为准"，也不能默认"以 PRD 为准"——要看是否有裁决，没有就问。
8. **规则以服务端下发为准，但客户端又写了兜底/默认值。**
   例：字段缺失时客户端默认按 0 处理。兜底值本身就是一条隐形规则，必须确认缺省语义（跳过 / 阻塞 / 上报默认值）。

提问必须**一次问完**（§11），不能一项一项挤牙膏。

## 6. 冲突形态与处置

### 6.1 UI 取值特有形态

| # | 形态 | 典型表现 | 处置 |
|---|---|---|---|
| 1 | 设计变更型 bug | bug 要求的值 ≠ 当前设计值，设计稿不会同步 | 修复后**必须**登记覆盖，否则下次对稿必回改 |
| 2 | 缺陷型 bug | 实现写错，修完等于设计值 | 只修不登记；修完顺带检查同组件是否有未登记差异 |
| 3 | 同组件后续改其他属性 | 贴图只改间距，字号有旧裁决 | 只改点名属性；旧裁决保留；不得整块重排 |
| 4 | 同属性新设计值 ≠ 裁决值 | 设计更新了，值却和 bug 要求不同 | 转形态 6，必须裁决 |
| 5 | 基准已并入裁决值 | D == R | 记录状态改为 `已并入基准`，保留历史，不再阻止对齐 |
| 6 | 设计稿更新但值不同 | D ≠ R 且设计节点已改版 | 必须裁决：采用新设计 / 保留裁决 / 分状态并存 |
| 7 | 裁决只作用于某 variant / 状态 / 语言 | 仅播放页、仅 terminal、仅葡语 | 按范围建条目；范围外按设计，不推广 |
| 8 | 两个来源对同属性给出不同值 | 两个 bug 单、bug 与产品口述 | 只有"一方明确写出值、另一方含糊"时才按明确方；两方都明确或都含糊 → 必须问，禁止按日期或"哪个更新"取胜 |
| 9 | 裁决是临时兜底 | 等接口、等设计定稿 | 状态记"临时生效"并写失效条件；到期即视为待复核 |
| 10 | 设计稿只标注了部分属性 | 只标了间距，没标字号 | 未标注属性 D 为空，保留 C；不得从邻近页面推断 |
| 11 | 设计值非整数 | 28.5dp、45.2dp | 照抄设计值，不做"取整美化"，取整即偏差需说明 |
| 12 | 大字体/无障碍导致的值变化 | 系统 fontScale 下的缩放 | 属于适配策略，不是设计值覆盖；若需求明确"间距不许随字号变""禁止用省略号代替缩字"，登记为 `行为约束`（设计值 = 生效值，但取值规则被限定） |
| 13 | 整块重做 + 多条旧裁决 | 新稿重绘整个卡片 | 批量冲突，一次问完（§11） |
| 14 | 代码值与设计不同、无注释但 git 有历史 | 历史改动没留痕 | 先 `git log -S` 找来源；找到明确单据则补登记，找不到按 §5.3 问来源 |
| 15 | 共用组件只有一处设计更新 | 组件被多个页面复用，新稿只改了其中一个入口 | **必须问**：是接受所有复用处一起变，还是加参数分叉；不能默认"一起改"或"只改一处" |

### 6.2 业务规则特有形态

| # | 形态 | 典型表现 | 处置 |
|---|---|---|---|
| B1 | 需求变更型 bug | bug 要求的行为与 PRD 不同，PRD 不回改 | 修复后**必须**登记 `规则覆盖`，写清改了哪条判定条件 |
| B2 | 实现缺陷型 bug | 实现写错，修完等于 PRD | 只修不登记覆盖；补一条用例锁定行为，用例即证据 |
| B3 | PRD 改版只改了一处 | 新版本更新了 §5.3，§5.1/§5.2 的相邻规则没同步 | **不能只改被引用的那条**：列受影响的规则清单，逐条问是否联动 |
| B4 | PRD 自相矛盾 | §A 说"必须绑卡"，§B 说"未绑也可提现" | **必须问**，AI 不得择一执行；裁决后登记并注明冲突章节 |
| B5 | PRD 未定义 | 没写缺省值、边界、异常分支 | 属未决，问；**不得从现有代码反推成"需求如此"**（那是丁级证据） |
| B6 | 服务端与客户端重复实现同一规则 | 接口返回 `canWithdraw`，客户端又自己算一遍 | 必须问谁为准；裁决后把另一侧标为"仅展示/仅兜底"，并登记 |
| B7 | 规则跨端只改一端 | iOS/Android/服务端只有一端按新规则改了 | 必须问是否需要同步；不同步要写清差异与生效范围（端） |
| B8 | 埋点口径与业务规则脱节 | 业务规则改了，事件名/上报时机没改 | 一起裁决；登记时把"上报时机"作为该规则的连带项 |
| B9 | 灰度/开关导致线上与 PRD 不同 | 新规则只在实验组生效 | 登记 `临时生效` + 失效条件（全量或下线日期），到期复核 |
| B10 | 历史数据没有新字段，走兜底 | 老数据 `null`，客户端按 0 处理 | 兜底本身是一条隐形规则：必须登记缺省语义（跳过/阻塞/上报默认值），不能留在代码里没人知道 |
| B11 | 改动影响不可回溯的数据 | 已经结算的金额、已上报的埋点 | **必须问是否回溯**；不回溯要写"仅对新数据生效 + 生效时间点" |

## 7. 改 bug / 接产品要求时的落地五件套

只要存在**需要防回改的决定**，五件必须同时完成，缺一不可。触发条件有四类，对应登记表的 `类型`：

| 类型 | 触发条件 | 典型场景 |
|---|---|---|
| `值覆盖` | UI 生效值 ≠ 设计值 | bug 把字号从 16sp 改成 21sp |
| `规则覆盖` | 业务生效行为 ≠ 需求定义 | bug/口述改了判定条件，PRD 不回改 |
| `口径澄清` | 需求没写或写不清，裁决补了具体口径 | "退出提现页要不要推进进度"PRD 没定义 |
| `行为约束` | 等于基准，但取值规则/实现方式被限定 | "间距不许随 fontScale 变""上报必须幂等" |

纯缺陷修复（修完等于基准且无额外约束）不登记，但要有用例或截图锁住行为。

1. **判定类型**：按上表选一个。判据是"修完后与基准的关系"，不是主观意图。
2. **拆条目**：UI——组件/区域、属性、设计值、生效值、范围（页面/variant/状态/语言/字倍/主题）；业务——规则名、触发条件、判定条件、预期行为、范围（端/版本/用户状态/开关）、连带项（埋点、其他端）。
3. **证据落库**：UI 存截图；业务存需求章节截图、缺陷单、接口响应样本、用例或单测路径。外部链接只作补充，仓库内必须有副本。没有单号的口述，记录原话摘要 + 提出人 + 日期。含手机号、账号、金额的截图打码，但不能遮住被裁决的区域。
4. **写代码注释**：紧邻取值处或规则分支，标明类型与 ID（§9）。
5. **写登记表**：在 `<module>/docs/vibe-coding-clarify/REGISTRY.md` 增加一行（§8），并在同目录 `vibe-coding-clarify.md` 写决策背景并引用 ID。模块尚未迁移时先把旧记录并进来再登记，**不允许新旧两处各写一份**。

连带调整（如字号变大导致容器高度必须变；规则改了导致埋点时机必须跟着变）也必须写进同一条目，注明"连带项 + 原因"，不能悄悄改。

## 8. 裁决资料归档（docs/vibe-coding-clarify/）

### 8.1 位置与唯一性

**一个模块一个目录，所有裁决资料集中放在 `docs/vibe-coding-clarify/` 下。**

```text
<module>/docs/vibe-coding-clarify/
├── REGISTRY.md                  # 唯一权威表，一行一条，给 grep 用（UI 取值 + 业务规则两节）
├── vibe-coding-clarify.md       # 决策背景与时间线，引用条目 ID
└── evidence/<component|rule>/*  # 证据：UI 截图、需求章节截图、接口样本、用例说明
```

规则：

1. 仓库级问题（构建、发布、Gradle、聚合库）放 `<repo>/docs/vibe-coding-clarify/`，不散落到各模块。
2. 不要放在模块根目录，也不要另建 `ui-adjudications/` 之类的第二套目录；已经存在的旧目录要合并进来。
3. 模块根目录若有历史 `vibe-coding-clarify.md`，搬进 `docs/vibe-coding-clarify/` 并同步所有指向它的路径（代码注释、计划文档、其他 md），**不留两份**；迁移单独提交，不与业务改动混在一起。
4. 表是给 grep 用的，不要写成散文；`REGISTRY.md` 在出现第一条裁决时创建，只有普通决策（无取值/行为裁决）的模块可以只有 `vibe-coding-clarify.md`。

### 8.2 表结构

一个 `REGISTRY.md` 分两节，节内一行一条。UI 用 `ADJ-`，业务规则用 `RULE-`，互不串号。

**A. UI 取值**

```markdown
| ID | 组件/区域 | 属性 | 类型 | 设计值(节点/日期) | 生效值 | 生效范围 | 来源类型 | 来源与日期 | 证据 | 状态 | 最后复核 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| ADJ-XXX-001 | 金额文本 | 字号 | 值覆盖 | 16sp (NODE-XXXX / 2026-11-24) | 21sp | 全部页面、全部语言 | bug单 | 《默认字号调整》缺-1234 / 2026-11-26 | `.../2026-11-26-font21.png` | 生效 | 2026-11-26 |
| ADJ-XXX-002 | 图标-金额 | 间距 | 行为约束 | 9.04dp (同上) | 9.04dp，禁止随 fontScale 分支 | 全部页面 | bug单 | 《间距固定》缺-1235 / 2026-11-26 | 同上 | 生效 | 2026-11-26 |
```

**B. 业务规则**

```markdown
| ID | 规则/场景 | 触发与判定条件 | 需求定义(文档/版本/章节) | 生效行为 | 生效范围 | 类型 | 来源类型 | 来源与日期 | 证据 | 状态 | 最后复核 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| RULE-XXX-001 | 未绑账号退出提现页 | 进任务 + 未绑 + 点退出 | 《网赚逻辑》v2.3 §5.3：退出即解除蒙层，流程不推进 | 同需求 | 进任务阶段；全部端、全部语言 | 口径澄清 | 产品裁决 | 评审会 2026-11-24 / 提出人 Z | `.../2026-11-24-exit-flow.png`、`WithdrawBalanceServiceTest#exit` | 生效 | 2026-11-26 |
```

字段要求：

1. **ID**：UI `ADJ-<模块短名>-<三位序号>`，业务 `RULE-<模块短名>-<三位序号>`；只增不改，不复用，不因撤销而回收。
2. **粒度**：UI 一个条目只写一个属性；业务一个条目只写**一条可分叉的规则**（一个触发条件 + 一个预期行为），不要把"提现整条链路"写成一行。
3. **类型**：四种，见 §7 表。
   - `值覆盖`：UI 生效值 ≠ 设计值。
   - `规则覆盖`：业务生效行为 ≠ 需求定义。
   - `口径澄清`：需求没写或写不清，裁决补了具体口径；此时"需求定义"列必须写清缺口（如"§5.3 未定义退出行为"），不能编一个需求原文。
   - `行为约束`：等于基准，但取值规则/实现方式被限定（如"间距不许随字体缩放""上报必须幂等"）。这类不是"值不同"，不登记就会被下一次适配改动静默推翻。
4. **基准值**：UI 必须带节点 id 与获取日期；业务必须带文档名 + 版本/发布日期 + 章节号。没有基准就写 `无`，不写"待定"。
5. **生效范围**：UI 写页面/variant/状态/语言/字倍/主题；业务写端（Android/iOS/服务端）、版本、用户状态、开关/灰度。默认写"全部"，**禁止留空**。
6. **状态**：`生效` / `临时生效` / `已并入基准` / `已撤销`。
   - `临时生效` 必须在范围列写失效条件（如"接口下发后失效""全量后失效"）。
   - `已并入基准`：基准已等于生效值，保留历史但不再阻止对齐（仅对 `值覆盖`/`规则覆盖` 有意义）。
   - `已撤销`：保留行，写撤销来源与日期，禁止删行。
7. **最后复核**：每次对齐检查过该条目就更新日期；超过基准改版日期未复核的，视为待复核。

### 8.3 一个组件/一条链路多条裁决时

按属性或规则分行，不合并；同一属性不同范围也分行。业务规则尤其禁止把"整条链路"写成一行——链路里的每个分支要能单独裁决、单独撤销。行长控制在可读范围，证据用相对路径。

### 8.4 追溯链路（必须闭环）

每一个取值/行为决定都要能从代码走回原始诉求，四跳缺一不可：

```text
代码处注释（ADJ-ID / RULE-ID）
        ↓
REGISTRY.md 行（基准 / 生效值或行为 / 范围 / 来源 / 日期）
        ↓
vibe-coding-clarify.md 条目（为什么改、谁裁决、影响面）
        ↓
evidence：截图 / 需求章节 / 接口样本 / 用例或单测
```

规则：

1. 任一跳缺失即视为记录不完整，不能标记为"已登记"。
2. 代码注释只写 ID、来源、基准 → 生效值、对齐约束，**不复制整段背景**；详细背景只存 `vibe-coding-clarify.md`，避免三处内容各自漂移。
3. `REGISTRY.md` 与 `vibe-coding-clarify.md` 的取值必须一致；不一致时以 `REGISTRY.md` 为准，并修正另一处。
4. 业务规则的第四跳优先用**可执行证据**：单测/用例名（能跑）、接口响应样本（能复现）；只放一张需求截图不足以证明行为已生效。
5. 证据必须是仓库内相对路径，能直接打开；只给外部链接视为没有证据。
6. 交付说明至少给出一个可直接定位的路径（`REGISTRY.md` 行或 clarify 条目标题），不能只说"已记录"。

## 9. 代码注释格式

四种注释，不能混用。**覆盖值/规则缺 ID 等于没有记录**；基准值注释只要求来源与版本。

```kotlin
// ── 覆盖设计稿（ADJ-XXX-001）───────────────────────────────
// 来源：bug 单《<标题>》（<单号/链接>，YYYY-MM-DD）
// 设计值：16sp（节点 NODE-XXXX，YYYY-MM-DD）→ 生效值：21sp
// 范围：全部页面、全部语言；连带项：无
// 对稿：未获产品确认前不得回改 21sp；裁决见 docs/vibe-coding-clarify/REGISTRY.md
fontSize = 21.sp,
```

```kotlin
// 来自设计稿：8dp / 14dp，节点 NODE-XXXX（YYYY-MM-DD）。未被任何 bug 单覆盖。
padding(start = 8.dp, end = 14.dp),
```

```kotlin
// 推断值：设计稿未标注，按 1x 截图目测约 6dp，待设计确认（未登记，不构成裁决）。
Spacer(Modifier.width(6.dp))
```

```kotlin
// ── 口径澄清（RULE-XXX-001）────────────────────────────────
// 需求缺口：《<需求文档>》v2.3 §5.3 未定义"未绑账号退出提现页"的行为
// 裁决：进任务 + 未绑 + 退出 → 只解除蒙层，流程不推进、进度仍显示 100%（评审 YYYY-MM-DD）
// 范围：进任务阶段；Android / iOS / 服务端一致；连带：埋点 page_state 仍上报 blocked
// 对齐：未获产品确认前不得改回"绑定前不往下走"；裁决见 docs/vibe-coding-clarify/REGISTRY.md
// 用例：<TestClass>#<method>
if (gate.requiresAccount && !account.isBound) {
    dismissMaskOnly()
}
```

规则：

1. 覆盖值/规则禁止写"设计值""需求要求"来掩盖 bug/产品裁决，必须写来源类型。
2. 覆盖值必须带条目 ID（`ADJ-` 或 `RULE-`）；基准值不带 ID，但必须带版本信息（节点+日期 / 文档+版本+章节）。
3. 同一处多个属性或分支来自不同来源时，按属性/分支分组注释，不写一段笼统说明。
4. 推断值必须显式写"推断"，且不得被后续代码当作基准传播。
5. 业务规则的注释要写**需求缺口在哪**（章节+缺什么），否则下次会被当成"需求没要求"而删掉。

## 10. 后续对齐的执行顺序

改任何 UI 值或业务规则之前，按顺序做，不可跳步：

```bash
# 1. 找登记表：新路径优先，历史路径同样算记录
ls <module>/docs/vibe-coding-clarify/REGISTRY.md
ls <module>/docs/ui-adjudications/REGISTRY.md            # 历史目录（未迁移的模块）
ls <module>/docs/vibe-coding-clarify/vibe-coding-clarify.md
ls <module>/vibe-coding-clarify.md                       # 历史位置（模块根目录）

# 2. 按组件名/规则关键词/属性名/文件路径检索（对上面命中的每个文件都搜一遍）
grep -n "<组件名>\|<规则关键词>\|<属性名>" <命中的登记表>

# 3. 找代码里的来源注释（含无 ID 的历史注释）
grep -rn "来源：\|覆盖：\|对稿：\|对齐：\|ADJ-\|RULE-" <module>/src/main/java/<package>

# 4. 找需求出处（业务规则必做：确认基准是哪一版、哪一节）
grep -rn "<规则关键词>" <module>/docs <repo>/docs 2>/dev/null

# 5. 找历史改动来源（注释缺失时）
git log -S "<该值或该判断条件>" -- <file>
```

**关键：查不到 ≠ 没有记录。** 只有在上面所有位置都搜过仍为空时，才能按"无记录"处理；否则会把已裁决值当成未决冲突，或者更糟——当成无约束直接按基准改。

命中历史路径时：本次仍按记录判定，并在交付说明里提出迁移（把文件并入 `docs/vibe-coding-clarify/`，同步引用路径）。迁移本身单独提交，不与本次改动混在一起。

检索结果的处理：

| 结果 | 动作 |
|---|---|
| 有生效条目且条目在写入集合内，P 明确 | 按 P 改，追加补充决策，更新条目 |
| 有生效条目，条目不在写入集合内 | 不动，交付报告列出 |
| 有生效条目，条目在集合内但 P 不明确 | 问（§5.1） |
| 有 `已并入基准` 条目 | 按普通基准值处理 |
| 有条目但状态 `已撤销` | 按普通基准值处理 |
| 无条目但有 `来源：bug单/产品裁决` 注释 | 先补登记（可能是漏登记），再判定 |
| 无条目、无注释，C 与 D 不一致 | 问（§5.3） |
| 记录只在历史路径（`ui-adjudications/`、模块根目录） | 按记录判定，不视为无记录；交付时提出迁移 |

## 11. 批量冲突：一次问完

命中 §5 多项时，合并成一次提问，逐条给选项，不要逐项追问。

```text
这块有 4 个条目需要你一次确认（有裁决冲突，也有来源不明）：

| # | 对象 | 条目 | 基准 | 当前生效 | 裁决来源 | 本次请求 |
|---|---|---|---|---|---|---|
| 1 | UI | 金额字号 | 16sp | 21sp | bug 单 #123（11-26） | 只说"对一下稿" |
| 2 | UI | 图标-金额间距 | 12dp | 8dp | bug 单 #123（11-26） | 只说"对一下稿" |
| 3 | UI | 卡片高度 | 57dp | 62dp | 无记录 | 只说"对一下稿" |
| 4 | 规则 | 未绑账号退出提现页 | §5.3 未定义 | 仅解除蒙层 | RULE-XXX-001 | 只说"这块理一下" |

选项（可对每条分别选）：
A 全部保留现状，本次只改你点名的 <属性>
B 全部采用新设计，登记表对应条目标记撤销
C 逐条指定（回复 1B 2A 3A 这种即可）
D 按状态拆分（例如仅播放页采用新设计）

确认后我先更新 REGISTRY.md 与代码注释，再改代码。
```

提问必须包含：设计值、生效值、范围、来源、影响面。**缺少任一项就是在让用户猜。**

不提供"默认选项"：用户不选 → 保持现状，该条目不落代码，下次继续按未决处理。禁止替用户预选 A 或 B。

## 12. 改动清单（动手前必须输出）

对齐类任务（UI 对稿、业务规则核对）在落代码前，先在对话里给出清单，让用户能一眼看出 AI 打算改什么、为什么。小任务 1~3 行也算。

```text
本次改动清单
| # | 对象 | 条目 | 基准值/需求 | 代码现状 | 生效记录 | 处理 | 依据 |
|---|---|---|---|---|---|---|---|
| 1 | UI | 组件 A · 项间距 | 6dp | 8dp | 无 | 按基准改 | 本次点名 |
| 2 | UI | 组件 A · 标题字号 | 14sp | 14sp | 无 | 无需改动 | 已与设计一致 |
| 3 | UI | 组件 B · 金额字号 | 16sp | 21sp | ADJ-XXX-001 | 按记录保留 | 未点名 + 生效裁决 |
| 4 | 规则 | 未绑账号退出提现页 | §5.3 未定义 | 仅解除蒙层 | RULE-XXX-001 | 按记录保留 | 未点名 + 口径澄清 |
```

规则：

1. 清单里"无需改动 / 仅报告不改"的行也要写，尤其是 D ≠ C 的行——这是让用户知道差异存在、但 AI 没动。
2. 处理列只能取 §4.1 六种结果之一。
3. 清单没列出的条目，本次不得改；临时发现要改的，先补进清单再改。
4. 业务规则清单要写到**分支粒度**（"未绑 + 进任务 + 退出"），不要写成"提现流程"。

## 13. 交付输出契约

交付必须按下面**四类**逐项交代，缺任一类视为没做完：

1. **改了哪些条目**，各自依据（基准值 / 本次明确要求 / 裁决 ID）。
2. **按裁决保留的条目**，写明裁决 ID 与本次为何没动。
3. **有差异但未处理的条目**，列出"基准值 vs 当前值 vs 未改原因"。这一项是防止"用户以为你按需求改了，其实没改"和"用户以为你保留了裁决，其实被你回改了"。
4. **仍未裁决的条目**，以及它们阻塞了什么；没有就写"无"。

推荐格式：

```text
改动：<属性> 按设计稿 X→Y；<规则> 按本次要求改为 <行为>（已登记 RULE-XXX-002）
保留：<属性> 保持 21sp（ADJ-XXX-001 生效，本次未点名）
差异未处理：<属性> 设计 16sp / 当前 14sp，不在本次范围，未改
待裁决：<规则> §5.3 与接口行为不一致，阻塞 <场景> 的实现
```

业务规则额外要求：写明**验证方式**（单测名 / 用例路径 / 真机场景），只写"已按需求实现"不算交付。

## 14. 反模式（逐条对应真实事故）

1. **越界写入**：用户只问间距，AI 顺手把字号改成"设计值"。→ 违反铁律一。
2. **整块重排**：贴一张整组件设计图，AI 按图纸重写整块，裁决值被静默回改。→ 违反铁律一。
3. **把 bug 值写成设计值**：注释写"设计值 21sp"，下次对稿查不到来源，直接回改。→ 违反 §9。
4. **"设计稿没标" = 随便定**：自行目测一个值写进代码。→ 违反 §3.1，应标推断并确认。
5. **一条记录推全组件**：某金额文本的字号 21sp 被推广到整个 Header。→ 违反 §8.2 按属性建条目。
6. **先改后说**：冲突在交付说明里提一句，代码已经改完。→ 违反 §5，必须先问。
7. **"最新即优先"**：不判断范围和明确性，按日期排序取胜。→ 违反 §6 形态 8。
8. **自我授权**：AI 自己写一条 clarify 记录证明改动合理，用户从未表态。→ 违反铁律二。
9. **默认跟随设计稿**：因为"这次是设计对稿"就整块按 D 覆盖。→ 违反 §4。
10. **默认保留现状**：因为"有 bug 单"就拒绝本次明确的产品新指令。→ 违反 §4 的 P 分支。
11. **双向沉默**：发现差异既不问也不报告，交付说明只写"已按设计稿对齐"。→ 违反 §13。
12. **按 PRD 原文改回去**：把已登记的 `口径澄清`／`规则覆盖` 当成"需求没写"或"实现走样"，恢复成 PRD 字面。→ 违反铁律二。
13. **从代码反推需求**：看到实现是 A，就写注释"需求规定 A"。这是丁级证据冒充甲级。→ 违反 §3.1。
14. **只改被引用的那一条**：PRD 改版只动了 §5.3，没检查 §5.1/§5.2 与埋点口径，改完自相矛盾。→ 违反形态 B3。
15. **以接口为准**：PRD 与接口不一致时默认相信接口，"反正线上就是这样"。→ 违反 §5.7，先问。
16. **兜底值不算规则**：字段为空时按 0 处理，代码里没人知道这等于一条业务规则。→ 违反形态 B10。
17. **验证只写在嘴上**：业务规则改完没有单测/用例，交付写"已按需求实现"。→ 违反 §13。

## 附录 A：UI 取值画像

正文即以 UI 为主线，这里只列易漏点：

1. **粒度**：组件/区域 + 属性 + variant/状态。字号与间距是两个条目，不能合并。
2. **范围维度**：页面、variant、状态、语言、字倍、主题。留空视为"全部"，这是最危险的默认。
3. **证据**：设计节点（甲）或带标注截图（乙）。聊天里的"这里改成 12"只能作 `P`，不能作 `D`。
4. **验收**：默认机型真机截图对照，逐项写"设计 X / 实现 Y"。
5. **特有形态**：见 §6.1（非整数不取整、共用组件单点更新、大字体适配不算覆盖等）。

## 附录 B：业务规则画像

### B.1 一条规则的四个要素

拆条目时四要素必须齐全，缺一项就无法判定"改没改到点上"：

| 要素 | 说明 | 缺失后果 |
|---|---|---|
| 触发条件 | 什么事件/状态下生效（进入页面、点击、接口返回、定时） | 规则会被套用到不该生效的场景 |
| 判定条件 | 生效所需的判断（是否绑定、阶段、开关、灰度、端） | 边界场景被漏掉或误伤 |
| 预期行为 | 系统应该做什么（推进/不推进、弹窗/不弹、上报什么） | 无法验证，只能靠感觉 |
| 适用范围 | 端、版本、用户状态、开关 | 改动外溢到其他业务线 |

### B.2 拆分原则

1. **一个分支一行**：同一规则的不同条件分支（已绑 / 未绑、S3 前 / 后）分开登记，便于单独撤销。
2. **不要把链路写成一条**："提现整条链路"不是一个条目，它是十几条规则的组合。
3. **连带项写同行**：规则改了导致埋点时机、接口字段、其他端要跟着变的，在同一条目的"连带项"里写清，不要另开条目却互不引用。

### B.3 需求取证

1. 必须记 **文档名 + 版本/发布日期 + 章节号**；只写"PRD 里说了"等于丙级证据。
2. **正文与批注可能冲突**：评审批注、流程图批注常常比正文新，也可能互相矛盾。冲突时按 §5.2 问，不要默认正文优先。
3. **需求文档不更新是常态**：bug 单、评审口头结论、接口文档都可能比 PRD 新。这正是要登记的原因，不是"不按需求做"。

### B.4 来源类型

`bug单` / `产品裁决` / `需求评审` / `口述`。写清是哪一种 + 提出人 + 日期；`需求评审` 要带会议日期与结论原文摘要。

### B.5 验收

1. 优先**可执行证据**：单测/用例名、接口响应样本、可复现的真机步骤。
2. 跨端规则必须说明其他端是否同步；不同步要写差异与生效范围。
3. 涉及金额、结算、上报等不可回溯数据时，必须写明生效时间点与是否回溯（形态 B11）。
4. 只写"已按需求实现"不算验收。

### B.6 文案口径

文案 key + 语言 + 场景三者缺一不可。三类来源要分清：需求给的正式文案（甲/乙）、设计稿里的占位文案（不能当正式文案）、翻译/本地化给出的调整（可能反过来覆盖需求）。文案与 UI 取值一样会冲突，走同一套判定。

### B.7 业务侧常见坑

1. **PRD 没写 ≠ 没要求**：缺失是未决，要问，不能自由发挥（§0 第 8 条）。
2. **代码注释写"按需求"但没出处**：等同于没有记录，下次对账会被当成实现走样改掉。
3. **只改客户端**：规则由服务端下发时，客户端改了也不生效；反之服务端改了客户端可能覆盖。
4. **规则改动没有用例**：下一次重构会静默改回去，而且没人发现。
5. **临时开关没有失效条件**：半年后没人知道这个分支为什么存在。
