# Compose 适配场景矩阵

## 读取时机

当任务涉及 Compose 页面实现、页面修复、复杂列表、弹窗、横屏/平板/折叠屏、多窗口、键盘、RTL、深色模式、字体放大或无障碍时，读取本文件。目标是把适配风险转成具体 Compose 布局决策，而不是只对齐一张默认设备截图。

## AI 与开发者的适配协作约定

适配的第一问永远是"这个尺寸/位置从哪来"：设计稿固定值、父容器比例、内容自然尺寸、窗口尺寸还是服务端数据。来源不同策略不同。协作分工：

- AI 可自主执行：下文五类场景的"默认策略"，以及在设计稿与代码事实一致时的等比换算与实现；等比换算只作用于已确认的缩放作用域（见下节「比例缩放的作用域边界」）。
- AI 必须澄清：命中"澄清触发"条目时，按编号列出备选方案（含代价：等比缩放 / 固定尺寸+文本自适应 / 换行 / 省略 / 隐藏低优元素）让开发者选择，并按 `aaaaa-xxf-clarify-question` 记录决策；不要替业务在"省略丢信息 / 换行破构图"之间拍板。
- AI 必须验证：布局类改动要在真机或预览宿主截图核对，且做"部位级"检查（逐个确认关键交界的间隙/裁切，如"Only 文案与按钮是否分离""金额每个字符是否完整"），禁止整图扫一眼就报通过；声称"字体放大已验证"前先确认测试路径真的生效（pixel-diff 对比，见文末防坑）。

### 比例缩放的作用域边界（先定边界再动手）

- "按比例适配/等比适配"类需求默认只作用于**被点名的那一层容器盒子**：宽度优先、高度随比例（如卡片 `fillMaxWidth + heightIn(min=设计高) + aspectRatio(设计宽/设计高)`），解决的是底图 FillBounds 拉伸、构图比例失真这类盒子级问题。
- 子组件默认**不**随比例缩放：字号（sp）、字距、图标尺寸、功能性行高与内边距保持设计稿原值，各自走既有适配策略（控件标签省略、单 token 数据 TextAutoSize、段落换行）；字体放大仍由 fontScale 路径自然撑高容器。
- 整组件 ×scale（所有尺寸含字号同乘系数）只适用于本文件明确归类的场景：固定栅格宽度对、装饰性整组（营销弹窗/插画组合）、装饰图本体；且必须有明确需求、设计稿标注或**该组件自身**的既有决策支撑，不得从一句"这个 XX 按比例适配"推断到它的全部子组件。
- 仓库/项目里已有的 ×scale 实现只是那个组件的决策记录，不是通用先例许可；动手前先回到本次需求文本核对作用域，先例只能参考不能扩权。
- 需求只说"按比例"、缩放边界不明时，按"澄清触发"处理，方案清单见下节「宽高比容器的内容让位方案」，不要默认最宽的整组缩放。

### 宽高比容器的内容让位方案（必须让开发者选）

容器高度随宽度等比锁定后，内容栈与容器的差值必须有人让位。**让位方式是产品决策，不是实现细节**：凡给容器加 `aspectRatio` 等比锁定、且内部是固定节奏内容栈（行高/间距/字号累加出卡高）时，动手前必须按编号列方案让开发者选，并按 `aaaaa-xxf-clarify-question` 记录决策：

1. 整组等比：全部子组件（含字号、字距、间距、图标）随容器 ×scale。适用装饰性整组（营销弹窗/插画组合）；含功能文本的组件慎用，小屏可读性下降。
2. 指定弹性件：点名单个子组件（通常是主体内容，如金额/标题）吃剩余空间并自动收缩——`weight(1f)` 给出有界高度 + `TextAutoSize` 同时按宽高缩字号，其余子组件保持设计原值。需求出现"XX 动态变小/自动收缩"类表述时即此方案。
3. 间距压缩：padding/spacer 随可用空间动态压缩（弹性 Spacer、动态 spacedBy、比例化 padding），子组件尺寸与字号不动。文字优先保字号时用。
4. 容器放宽（兜底）：不锁比例，允许内容撑高或滚动（即上文"内容超高向下长高 + 整列滚动"）。

- 禁止不问就默认任一方案：整组 ×scale 越权（见防坑）、擅自指定让位件、静默压缩间距，都算替产品拍板。
- 弹性件方案的前提是**有界高度约束**：`TextAutoSize` 只在 maxHeight 有界（`weight` 或固定 max）时才为高度收缩；只有 `heightIn(min=…)` 时它只按宽度收缩，高度永远不让步。
- 选定的让位方案要写进代码注释（KDoc 标明"谁让位、怎么让"），防止后人把让位件改回固定尺寸或误扩到全部子组件。

### 横向排列的组件（非横向滚动容器内）

- 判断维度：同行元素是否要保持设计稿的相对宽度关系；内容是否会随数据/语言/字体放大变宽；同行放不下时谁让位。
- 默认策略：
    - 宽度来自内容：固定元素（图标/按钮）先占位，动态文本用 `weight(1f)` + 截断/缩字承接剩余空间，不允许把固定元素挤出屏幕。
    - 设计稿固定栅格（双金额对、双按钮对）：宽度按设计基准（如 380）随容器比例缩放 `scale = 可用宽/设计宽`（可设上限），既不写死 px 也不无条件写死 dp；×scale 只作用于栅格宽度对本身，不外溢到其他子组件（见「比例缩放的作用域边界」）。
    - 同行放不下必须定义压缩顺序：谁缩字号、谁省略、谁换行、谁隐藏；没有顺序就会互相挤压或裁切。
- 禁止：只在一个机型上"刚好"的固定 dp 堆叠；假设"内容永远不会超宽"。
- 澄清触发：设计稿未说明放不下时谁让位、能否换行/缩小时，列备选让开发者选。

### 纵向排列的组件（非纵向滚动容器内）

- 判断维度：整组高度是设计稿固定，还是允许随内容（行数/字体放大）自然长高；窗口不够高时滚动还是压缩。
- 默认策略：
    - 内容驱动的纵向流用 Column + 自然高度：文本换行、卡片随内容长高，不写死整组高度。
    - 装饰性整组（营销弹窗、插画组合）可按设计基准随宽度比例缩放，但必须保留"内容超高向下长高 + 整列滚动"兜底，不切换第二套简化视觉；整组 ×scale 属于该场景的明确类别，不得当作通用方案套到含功能文本的普通组件（见「比例缩放的作用域边界」）。
    - 固定高度只给纯装饰带（图标行、插图区）；含文本区域禁止写死高度裁字。
- 澄清触发：设计高度与内容自然高度冲突（小屏/大字体放不下）时，问开发者：允许滚动、压缩间距、还是隐藏某段。

### 相对位置与叠层排列（写死尺寸 vs 相对定位）

- 判断维度：设计稿表达的是"定位关系"（A 在 B 上方 12dp、A 压住 B 下沿 95）还是"绝对坐标"（x=163,y=171）。优先把定位关系翻译成结构（对齐 + padding + 绘制顺序），而不是平铺 offset。
- 默认策略：
    - 能用对齐关系表达的用 `align`/`Arrangement`/`padding`；叠层用"先绘制在底、后绘制在上"+ Top/Bottom 锚定表达。
    - 需要精确对稿的装饰组合可用 `offset × scale`，但 offset 只做视觉位移、**不参与父容器测量**：该位置若影响兄弟排布，必须用 padding/alignment 表达，否则兄弟会按未含溢出的尺寸接着排（实测踩坑：弹窗卡片用 offset 下沉，底部链接压到按钮上）。
    - 相对定位要随内容增长保持关系稳定：如"卡片增高向下长、与上方元素重叠量恒定"，不让叠层量随字体缩放漂移。
- 禁止：在含交互元素的容器里用 offset 表达"参与布局"的位置；绝对坐标定位交互控件（按钮/输入框）。
- 澄清触发：内容放大后叠层关系无法同时满足（不遮按钮就不遮插图）时，截图对比两个方案让开发者选。

### 文字超长的适配策略

- 判断维度：文本是控件标签、单 token 数据还是段落；可用空间是否有限；行数上限是 1 还是 N>1；业务是否允许省略。按类型给默认，不逐案发明：
    - 控件标签（button/tab/导航栏标题/输入框 label）：默认**单行 + 省略号**（`maxLines=1` + `overflow=Ellipsis`），不换行撑高控件；除非业务明确要多行。
    - 单 token 数据（金额/城市/电话/账号/编号）：默认**单行 + 自动缩放字号**（`TextAutoSize.StepBased`，设可读下限如 9sp）；这类内容不可能合理换行、通常也不允许省略。禁止"硬宽度约束 + 手算估宽"——估不足会在约束边缘裁半个字符（实测踩坑：金额数字显示半边）。
    - 段落/说明/消息：默认**多行自适应**（softWrap）+ 容器自然增高或滚动，不裁字；设计给了行数上限时按「多行限行文本（maxLines = N）」处理，不套用单行策略。
    - 数字/价格注意 fallback 字体测量差异（如 ¥ 在某些字体走回退变宽），用最长合理样例验证。
- 单行空间也有限时的降级顺序（前提：已按下一节做完"吃满可用宽度"）：缩字号（至可读下限）→ 省略号（业务允许）→ 换行（布局允许）；任一降级在代码注释标明业务口径。
- 澄清触发：省略会丢关键信息（金额/账号/地址），或控件既不允许换行也不允许缩字号时，让开发者指定策略，不要默认省略。

#### 标题/名称类单行文本：三级宽度策略（默认）

适用于设计稿画成单行的标题、平台名、用户名、弹窗主标题、列表主标题，且设计未说明放不下时怎么办。顺序固定，不许跳级，也不许自创第四种（行数上限 N>1 的多行场景见下一小节，降级顺序不同）：

| 级别 | 做法 | 判定"该进入下一步"的条件 |
| --- | --- | --- |
| 1 先吃满空间 | 行容器 `fillMaxWidth()`，文本 `weight(1f, fill = false)`；固定元素（图标/Logo/箭头/按钮）保持设计尺寸 | 文本在设计字号下的自然宽度 > 可用宽度 |
| 2 再缩字号 | `TextAutoSize.StepBased(minFontSize, maxFontSize = 设计字号, .5.sp)` | 已到 `minFontSize` 仍超宽 |
| 3 最后兜底 | `maxLines = 1` + `softWrap = false` + `overflow = Ellipsis`；业务允许折行时改为换行并放宽行高节奏 | — |

- **第 1 级的唯一敌人是常量宽度上限**：`widthIn(max = 166.dp)`、固定 `Modifier.width(...)`、"按比例留白"的 `widthIn(max = 250.dp * scale)` 都属于把设计稿里某个盒子的宽度当成了文本的可视宽度。除设计稿明确标注文本框宽度外，这类常量一律删掉，宽度交给父容器——
    - 短文本不会因此变宽：行仍 `Arrangement.Center`/Start，`weight(1f, fill = false)` 让文本只占自身宽度，箭头、按钮继续紧跟文字。
    - 长文本才有收益：省下的空白直接变成可显示字符。
- **第 2 级的取值口径**：`maxFontSize` 就是设计字号，不作为"建议上限"另调；`minFontSize` 取设计字号的约 60%~75%，同时不低于可读下限（名称/正文类 ≥12sp）。字号带 `scale` 的整组缩放场景，下限按同一比例或封顶（如 `12.sp * scale.coerceAtMost(16f / 12f)`），避免宽屏时下限被 scale 抬得缩不动。
- **第 3 级必须先定义**：省略号是"降到下限后仍放不下"的结果，不是首选策略；单行口径下它就是默认兜底，但要在 KDoc 写明"到下限才省略"，防止后人把 `overflow` 当主策略、把宽度常量加回来。

```kotlin
// 标题行：宽度来自父容器，短标题仍整体居中，长标题先吃满再缩字，最后才省略
Row(
    modifier = Modifier.fillMaxWidth(),            // 不写 widthIn(max = …)
    verticalAlignment = Alignment.CenterVertically,
    horizontalArrangement = Arrangement.Center,
) {
    Image(painterResource(iconRes), null, Modifier.size(44.dp))   // 固定元素不参与压缩
    Spacer(Modifier.width(18.dp))
    BasicText(
        text = platformName,
        modifier = Modifier.weight(1f, fill = false),  // 短文本只占自身宽度
        style = TextStyle(
            color = Color.White,
            fontSize = 24.sp,                        // 设计字号 = autoSize 上限
            lineHeight = 34.sp,                      // 用 sp 声明，随字号等比缩放
            fontWeight = FontWeight.SemiBold,
        ),
        autoSize = TextAutoSize.StepBased(
            minFontSize = 16.sp,                     // ≈设计字号 2/3，且 ≥12sp 可读下限
            maxFontSize = 24.sp,
            stepSize = 0.5.sp,
        ),
        maxLines = 1,
        softWrap = false,
        overflow = TextOverflow.Ellipsis,            // 到下限才省略
    )
}
```

- material3 `Text` 目前没有 `autoSize` 参数（截至 compose BOM 2025.05 / material3 1.3.x），缩字必须换 `androidx.compose.foundation.text.BasicText`；后续升级 material3 后先确认是否已提供同名参数，有则优先用 `Text` 以减少不继承 `LocalTextStyle` 的差异。替换时注意两点：
    - `BasicText` 的 `style` 不合并 `LocalTextStyle`，主题或所在位置若有自定义 `fontFamily`/`letterSpacing`，必须显式写进 `style`，否则字体回退、字距丢失（`FontFamily.Default` 的主题无影响）。
    - 定高行（如 35dp 渠道行）替换后保持与原 `Text` 相同的 `includeFontPadding` 取舍，度量一变就可能顶破定高盒子。
- 例外与澄清：设计稿明确标注了文本框宽度 → 按标注实现，但仍需说明放不下时的策略；业务要求"必须两行"或"名称必须完整不得省略" → 折行会破单行构图/定高，需列方案（放宽行高与纵向节奏 / 保底省略 / 降级为两行）让开发者选。
- 自查信号：省略号两侧还有明显空白、或可用宽度远大于文本实际宽度，说明第 1 级没做，先查宽度常量而不是先调字号；反过来，缩字号却看不到变化，先确认 `maxWidth` 是否真由父容器给出（`widthIn`/固定 `width` 会让 autoSize 在错误约束里循环）。

#### 多行限行文本（maxLines = N）：与单行的差异（默认）

设计稿给了行数上限（"最多 3 行""两行截断""超出省略"）时，目标不是"塞进一行"，而是"让内容在 1..N 行内排下"。降级顺序与单行**不同**，不能照抄：

| 维度 | 单行 `maxLines = 1` | 多行限行 `maxLines = N > 1` |
| --- | --- | --- |
| 溢出表现 | 整句在末尾被截断，信息几乎全丢 | 只截末行，前 N−1 行信息保留 |
| 缩字号目标 | 塞进 1 行，收益直接 | 塞进 N 行；缩 10% 常常不足以减少一行，收益递减 |
| 行数本身 | 恒为 1，只能靠缩字号/省略 | 1..N 自由伸缩，本身是第一层弹性 |
| 默认降级 | 吃满宽度 → 缩字号 → 省略 | 吃满宽度 → 行数自适应 → 缩字号（按语义）→ 末行省略 / 展开 |
| 高度 | 单行定高安全 | 随 1..N 行变化；需要等高时才用 `minLines = N` |

1. **先吃满宽度**：与单行同规则（`fillMaxWidth()`，无设计标注就删掉常量 `widthIn`）。多行场景下宽度上限的伤害更大——宽度少 20% 常常意味着多出一行，直接提前触顶被省略。
2. **让行数在上限内自由伸缩**：`maxLines = N` + `softWrap = true` + 显式 `lineHeight`，容器高度跟随 1..N 行。**限行只能用 `maxLines`，不能用固定高度 + `clip` 裁剪**——后者是裁字不是省略，字体放大后裁得更多，且不显示省略号。
3. **超 N 行再降级，按业务语义二选一**（单行没有这个分叉）：
    - **内容要尽量完整**（标题、说明、状态提示、协议摘要）：缩字号 `TextAutoSize.StepBased(下限, 设计字号, .5.sp)` + `maxLines = N`，autoSize 会在 N 行内选最大可容纳字号；下限取设计字号 60%~85%（短标题取 80% 以上、状态/提示类可到 60%，实测先例 15sp→9sp），到下限仍超才末行省略。
    - **内容可截断或可交互**（列表副标题、用户简介、评论、地址）：不缩字号，直接 `maxLines = N` + `overflow = Ellipsis`；业务允许时优先"展开/收起"交互替代省略，比缩小正文更可读。
4. **等高场景**：列表 item 要求整齐时用 `minLines = N`（1 行内容也占 N 行高）或固定 item 高度 + `maxLines = N`，并验证 fontScale 1.3 下不裁字；只为"看起来整齐"而用固定高度裁字属未通过。

```kotlin
// 3 行限制的状态提示：宽度吃满 → 3 行内自适应 → 缩字到下限 → 末行省略
BasicText(
    text = statusTip,
    style = TextStyle(fontSize = 15.sp, lineHeight = 21.sp, fontWeight = FontWeight.SemiBold),
    autoSize = TextAutoSize.StepBased(minFontSize = 9.sp, maxFontSize = 15.sp, stepSize = 0.5.sp),
    softWrap = true,                 // 多行必须为 true
    maxLines = 3,                    // 行数上限只由 maxLines 表达
    overflow = TextOverflow.Ellipsis, // 末行省略，不静默裁字
)
```

- 坑：`autoSize` 不配 `maxLines` 时只按宽度收缩、行数无界——内容越长行数越多，等于放弃行数约束；`maxLines = N` 必须一起给。
- 坑：`maxLines = N` 但 `overflow` 用默认 `Clip` 时不显示省略号，用户不知道还有内容；限行场景必须显式 `Ellipsis`（仅设计明确不要省略号时才用 `Visible`）。
- 末端省略丢的若是关键信息（金额、日期、结论），优先"展开"或调整排版把关键信息前置，不默认截断。
- 澄清触发：省略会丢关键信息、业务要求"必须完整显示"、或列表需要等高但 1 行 item 被拉高时，列方案（缩字 / 展开 / 改两行布局 / 放宽高度）让开发者选。

### 图片的适配策略

- 判断维度：图片是内容（用户头像/远程封面，尺寸不可控）还是装饰（插画/图标，尺寸已知）；容器比例是否固定；裁切是否伤害主体。
- 默认策略：
    - 内容图：容器固定比例或固定尺寸 + 明确 `ContentScale`（允许裁切的封面用 Crop/FillBounds，不允许裁切的整图用 Fit），带占位与失败兜底，加载前后不跳尺寸。
    - 装饰图：按设计稿尺寸随容器比例缩放（×scale），仅限装饰图本体；组合插画用 Fit 保持原始比例，禁止拉伸变形；只有允许变形的底板/渐变才可用 FillBounds。
    - 远程图不假设原图比例恰好等于设计稿比例，必须有 `aspectRatio` 或固定容器兜底。
- 澄清触发：裁切会切掉主体（人脸/文字/二维码）或设计稿与数据图比例不一致时，让开发者选裁切还是留白。

## 窗口和设备形态

- 官方断点数值、window size class 获取 API、canonical layouts、折叠屏铰链与多窗口验证矩阵见 `compose-adaptive-window-standards.md`；本节只列场景风险。
- 窗口尺寸：手机小屏、常规屏、大屏、横屏、平板、ChromeOS、外接显示器、分屏、多窗口、自由窗口都会改变可用宽高；布局分支优先基于实际 constraints、window size class 或项目封装，不基于设备型号。
- 折叠屏：折痕、铰链、半折叠姿态、双屏区域和展开/折叠切换会改变内容连续性；关键按钮、输入框、弹窗、底部栏不能跨不可用区域或被折痕切开。
- 方向切换：横竖屏切换后要验证 `rememberSaveable` 状态、Lazy 滚动位置、分页状态、输入焦点、弹窗和底部栏位置。
- 大屏布局：宽屏不要简单拉伸手机布局；必要时改为双栏、列表详情、导航 rail、网格列数增加或内容最大宽度居中。
- 小屏布局：320dp/360dp 宽下优先保证主任务可完成，低优先级标签、辅助按钮、说明文可折叠、换行或隐藏。

## WindowInsets 和系统区域

- target 35+ edge-to-edge 强制行为、失效 API 清单与 `enableEdgeToEdge()` 标准用法见 `compose-adaptive-window-standards.md`。
- edge-to-edge：状态栏、导航栏、手势区域、刘海/挖孔、透明系统栏要用 `WindowInsets` 明确处理；可点击元素必须避开系统栏和手势热区。
- Compose API：优先用项目既有 inset 封装；没有封装时再使用 `Modifier.windowInsetsPadding`、`statusBarsPadding`、`navigationBarsPadding`、`imePadding`、`safeDrawingPadding` 等。
- 底部固定元素：吸底按钮、底部操作栏、FAB、Snackbar、BottomSheet 要同时处理导航栏、手势区域和键盘。
- 顶部固定元素：沉浸式标题栏、吸顶 tab、搜索栏、banner 顶图要明确是绘制到状态栏下面，还是延伸到状态栏背后。
- 弹层：Dialog、Popup、DropdownMenu、Tooltip、引导浮层、BottomSheet 要处理锚点越界、小屏超高、横屏、键盘和系统栏遮挡。

## 键盘和输入

- 表单、搜索、评论、登录、弹窗输入、底部输入栏要验证键盘弹起后的可见区域、焦点滚动、提交按钮、错误提示、候选词栏和系统导航栏。
- 输入框要明确单行/多行、最大高度、内部滚动、计数器、清除按钮、密码可见按钮、helper text 和 error text 的占位策略。
- Compose 中不要只依赖初始布局；键盘出现会改变 insets，`imePadding`、滚动容器和焦点 bring-into-view 要配合使用。

## 字体、显示大小和文本系统

- 验证 font scale 1.15/1.3，触及通用组件时考虑更大字体；按钮、标签、输入框、顶部栏和底部栏不能裁字。
- 限行文本（`maxLines = N`）在 fontScale 1.3 下常常从 2 行变 3 行、或从 3 行溢出：验证时要同时看行数上限是否被顶破、容器高度策略（自适应 / `minLines` 等高）是否仍成立、省略是否发生在可接受的位置。
- 系统显示大小、粗体文本、不同系统字体、fallback font、emoji、数字等宽/非等宽都会影响测量；不要用固定高度假设文本永远一行。
- `Text` 的 `maxLines`、`overflow`、`softWrap`、`lineHeight`、`includeFontPadding` 相关项目约定要明确。
- 富文本、可点击 span、混排图标、价格、小数、倒计时、日期、单位要用最长合理样例验证。

## 本地化、RTL 和资源

- 本地化会影响字符串长度、断行、货币、日期、复数、单位和图片文字；按钮和标签尤其要预留文本扩展空间。
- RTL 下要检查返回箭头、方向图标、进度、列表滑动方向、Row 排列、padding start/end、文本对齐和动画方向是否需要镜像。
- 资源必须有默认兜底：`drawable`、`mipmap`、`values`、`font`、`night`、`sw<N>dp`、`land`、语言资源不能只存在限定目录。
- 带文字图片要确认是否需要本地化替换；如果不替换，至少保证布局不会因不同语言资源缺失而崩溃。

## 主题、颜色和渲染

- 深色模式、高对比度、省电模式、动态主题色、透明系统栏、品牌换肤会影响颜色、阴影、分割线和系统栏图标明暗。
- ldpi 到 xxxhdpi、不同 GPU/系统版本、圆角抗锯齿、阴影、1dp/1px 分割线、矢量 viewport、图片采样可能产生视觉偏差。
- Compose 中 `clip`、`background`、`border`、`shadow`、`drawBehind`、`graphicsLayer` 的顺序会影响圆角、阴影和裁剪结果；按设计稿顺序实现。

## 内容和状态

- 覆盖加载中、空态、错误态、无权限、未登录、审核中、禁用、过期、下架、删除、弱网、分页无更多、局部刷新失败。
- 数据极值包括 0、1、多条、超长列表、重复数据、缺字段、空字符串、emoji、换行符、富文本、超大数字、负数、极短/极长昵称、图片宽高缺失。
- 交互状态包括按下、选中、禁用、加载、倒计时、防重复点击、滑动、拖拽、吸顶、展开收起、动画中断、返回恢复。
- 可访问性要检查 TalkBack 焦点顺序、触控热区、contentDescription、合并朗读、禁用态可理解、颜色对比度和可缩放内容。

## Lazy、滚动和分页

- `LazyColumn`、`LazyRow`、`LazyVerticalGrid`、瀑布流、Pager、FlowRow、吸顶 header、下拉刷新、分页 footer 叠加时，要确认滚动范围、嵌套滚动和边缘留白。
- Lazy item 使用稳定 key；动态高度、图片加载、展开收起、局部刷新不能导致错误复用、状态串位或明显滚动跳动。
- 网格列数基于可用宽度和最小 item 宽度计算；`GridCells.Adaptive` 优先于固定列数，除非设计明确固定。
- 分页列表要覆盖首屏不足一屏、加载更多失败、无更多、刷新中、删除 item、插入 item、图片迟到后的高度变化。

## 媒体和裁剪

- 静态图、动图、视频封面、直播流、透明 PNG、长图、宽图、二维码、头像、带文字图片要分别确认比例、裁剪、圆角、背景和加载失败。
- 圆角卡片、阴影、描边、父子裁剪、列表首尾 item、瀑布流边缘要检查是否误裁、露底或阴影被裁。
- 图片加载前后容器尺寸必须稳定；占位图、失败图、真实图使用同一比例和裁剪策略，避免视觉跳动。

## 性能边界

- 动态测量、`onSizeChanged`、`SubcomposeLayout`、`TextMeasurer`、富文本、图片圆角/模糊、瀑布流和复杂约束不要为了适配引入明显卡顿。
- 能用父级 constraints 和标准布局表达时，不要在 composition 阶段读取屏幕宽度后手算所有尺寸。
- 避免在 Lazy item 中创建不稳定对象、重复执行重计算或因图片状态变化触发整屏重组。

## 适配验证防坑（实测结论）

- `Dialog`/`Popup` 是独立 window：外层 `CompositionLocalProvider(LocalDensity provides …, fontScale=…)` 不会传入弹窗内容（弹窗用自己的配置派生密度）。预览宿主里"xx-font 场景"对弹窗类组件可能根本没生效——用 `settings put system font_scale` 改系统字体做真实验证，测完恢复原值；用 pixel-diff（`ImageChops.difference` 的 bbox 只落在状态栏 = 场景没生效）确认测试路径有效。
- offset 与 padding 的测量语义差异是相对定位第一大坑：offset 不改变父容器对子项的测量结果，padding 会。涉及兄弟排布的位置用 padding/alignment，纯装饰微调用 offset。
- 文本放进硬宽度约束的盒子时，`maxLines=1` 会在约束边缘直接裁字（不是溢出显示）；单 token 内容要么给足空间，要么 TextAutoSize。
- 部位级核对：整图视觉检查容易漏"小字压在按钮上"级别的缺陷；按关键交界裁剪放大（PIL crop + resize）逐项确认，"金额每个字符完整""链接与按钮有明确间隙"这类可判定的问法比"布局正常吗"可靠。
- 比例适配的作用域越权是高频返工点：需求说"这个 card 按比例适配"，实现却把卡内字号、字距、图标、内边距全部 ×scale——把仓库里弹窗族的整组缩放先例当成了需求范围（实测踩坑：2026-11 提现余额卡，整卡缩放被全部还原，只保留容器 `aspectRatio`）。动手前先按「比例缩放的作用域边界」确认哪一层缩放、哪一层不动；等比容器的内容让位方案按「宽高比容器的内容让位方案」列选项让开发者选。
- 弹性件没有有界高度就不会让位：`TextAutoSize` 在 maxHeight 无界（只给了 `heightIn(min=…)`）时只按宽度收缩，容器等比锁高后内容栈超高会把上下行挤出卡片；必须 `weight(1f)` 或固定 max 给出有界高度（实测踩坑：2026-11 提现余额卡金额行把渠道/账号行挤出卡外，加 weight 后按剩余高度缩字号解决）。
- 常量宽度上限会伪装成"字号太大"：2026-11 提现流程弹窗平台头写死 `widthIn(max = 166.dp)`，24sp 名称在 103dp 内被截成 `Master...`，而卡片内还有约 160dp 空白；同页余额卡渠道行 `widthIn(max = 250.dp * scale)` 同类问题。两者去掉上限 + `TextAutoSize(16→24sp / 12→19sp×scale)` 后完整显示，短名称的箭头位置不变（`Row` Start 排列 + `weight(fill = false)`）。排查顺序永远是"先量可用宽度，再怀疑字号"，否则会一路把字号调小却仍然被截断。
- "限 N 行"用固定高度 + `clip` 实现是裁字不是省略：字体放大后裁得更多、不显示省略号，且中文/英文断词位置一变就会半行残缺。行数上限只交给 `maxLines`，需要等高再用 `minLines = N` 或固定 item 高 + `maxLines = N`；`autoSize` 必须与 `maxLines` 成对出现，单独用只按宽度收缩、行数无界。
