# Compose 适配场景矩阵

## 读取时机

当任务涉及 Compose 页面实现、页面修复、复杂列表、弹窗、横屏/平板/折叠屏、多窗口、键盘、RTL、深色模式、字体放大或无障碍时，读取本文件。目标是把适配风险转成具体 Compose 布局决策，而不是只对齐一张默认设备截图。

## AI 与开发者的适配协作约定

适配的第一问永远是"这个尺寸/位置从哪来"：设计稿固定值、父容器比例、内容自然尺寸、窗口尺寸还是服务端数据。来源不同策略不同。协作分工：

- AI 可自主执行：下文五类场景的"默认策略"，以及在设计稿与代码事实一致时的等比换算与实现。
- AI 必须澄清：命中"澄清触发"条目时，按编号列出备选方案（含代价：等比缩放 / 固定尺寸+文本自适应 / 换行 / 省略 / 隐藏低优元素）让开发者选择，并按 `aaaaa-xxf-clarify-question` 记录决策；不要替业务在"省略丢信息 / 换行破构图"之间拍板。
- AI 必须验证：布局类改动要在真机或预览宿主截图核对，且做"部位级"检查（逐个确认关键交界的间隙/裁切，如"Only 文案与按钮是否分离""金额每个字符是否完整"），禁止整图扫一眼就报通过；声称"字体放大已验证"前先确认测试路径真的生效（pixel-diff 对比，见文末防坑）。

### 横向排列的组件（非横向滚动容器内）

- 判断维度：同行元素是否要保持设计稿的相对宽度关系；内容是否会随数据/语言/字体放大变宽；同行放不下时谁让位。
- 默认策略：
    - 宽度来自内容：固定元素（图标/按钮）先占位，动态文本用 `weight(1f)` + 截断/缩字承接剩余空间，不允许把固定元素挤出屏幕。
    - 设计稿固定栅格（双金额对、双按钮对）：宽度按设计基准（如 380）随容器比例缩放 `scale = 可用宽/设计宽`（可设上限），既不写死 px 也不无条件写死 dp。
    - 同行放不下必须定义压缩顺序：谁缩字号、谁省略、谁换行、谁隐藏；没有顺序就会互相挤压或裁切。
- 禁止：只在一个机型上"刚好"的固定 dp 堆叠；假设"内容永远不会超宽"。
- 澄清触发：设计稿未说明放不下时谁让位、能否换行/缩小时，列备选让开发者选。

### 纵向排列的组件（非纵向滚动容器内）

- 判断维度：整组高度是设计稿固定，还是允许随内容（行数/字体放大）自然长高；窗口不够高时滚动还是压缩。
- 默认策略：
    - 内容驱动的纵向流用 Column + 自然高度：文本换行、卡片随内容长高，不写死整组高度。
    - 装饰性整组（营销弹窗、插画组合）可按设计基准随宽度比例缩放，但必须保留"内容超高向下长高 + 整列滚动"兜底，不切换第二套简化视觉。
    - 固定高度只给纯装饰带（图标行、插图区）；含文本区域禁止写死高度裁字。
- 澄清触发：设计高度与内容自然高度冲突（小屏/大字体放不下）时，问开发者：允许滚动、压缩间距、还是隐藏某段。

### 相对位置与叠层排列（写死尺寸 vs 相对定位）

- 判断维度：设计稿表达的是"定位关系"（A 在 B 上方 12dp、A 压住 B 下沿 95）还是"绝对坐标"（x=163,y=171）。优先把定位关系翻译成结构（对齐 + padding + 绘制顺序），而不是平铺 offset。
- 默认策略：
    - 能用对齐关系表达的用 `align`/`Arrangement`/`padding`；叠层用"先绘制在底、后绘制在上"+ Top/Bottom 锚定表达。
    - 需要精确对稿的装饰组合可用 `offset × scale`，但 offset 只做视觉位移、**不参与父容器测量**：该位置若影响兄弟排布，必须用 padding/alignment 表达，否则兄弟会按未含溢出的尺寸接着排（实测踩坑：弹窗卡片用 offset 下沉，底部链接压到按钮上）。
    - 相对定位要随内容增长保持关系稳定：如"卡片增高向下长、与上方元素重叠量恒定"，不让叠层量随字体缩放漂移。
- 禁止：在含交互元素的容器里用 offset 表达"参与布局"的位置；绝对坐标定位交互控件（按钮/输入框）。
- 澄清触发：内容放大后叠层关系无法同时满足（不遮按钮就不遮插图）时，截图对比两个方案让开发者选。

### 文字超长的适配策略

- 判断维度：文本是控件标签、单 token 数据还是段落；可用空间是否有限；业务是否允许省略。按类型给默认，不逐案发明：
    - 控件标签（button/tab/导航栏标题/输入框 label）：默认**单行 + 省略号**（`maxLines=1` + `overflow=Ellipsis`），不换行撑高控件；除非业务明确要多行。
    - 单 token 数据（金额/城市/电话/账号/编号）：默认**单行 + 自动缩放字号**（`TextAutoSize.StepBased`，设可读下限如 9sp）；这类内容不可能合理换行、通常也不允许省略。禁止"硬宽度约束 + 手算估宽"——估不足会在约束边缘裁半个字符（实测踩坑：金额数字显示半边）。
    - 段落/说明/消息：默认**多行自适应**（softWrap）+ 容器自然增高或滚动，不裁字。
    - 数字/价格注意 fallback 字体测量差异（如 ¥ 在某些字体走回退变宽），用最长合理样例验证。
- 单行空间也有限时的降级顺序：缩字号（至可读下限）→ 省略号（业务允许）→ 换行（布局允许）；任一降级在代码注释标明业务口径。
- 澄清触发：省略会丢关键信息（金额/账号/地址），或控件既不允许换行也不允许缩字号时，让开发者指定策略，不要默认省略。

### 图片的适配策略

- 判断维度：图片是内容（用户头像/远程封面，尺寸不可控）还是装饰（插画/图标，尺寸已知）；容器比例是否固定；裁切是否伤害主体。
- 默认策略：
    - 内容图：容器固定比例或固定尺寸 + 明确 `ContentScale`（允许裁切的封面用 Crop/FillBounds，不允许裁切的整图用 Fit），带占位与失败兜底，加载前后不跳尺寸。
    - 装饰图：按设计稿尺寸随容器比例缩放（×scale）；组合插画用 Fit 保持原始比例，禁止拉伸变形；只有允许变形的底板/渐变才可用 FillBounds。
    - 远程图不假设原图比例恰好等于设计稿比例，必须有 `aspectRatio` 或固定容器兜底。
- 澄清触发：裁切会切掉主体（人脸/文字/二维码）或设计稿与数据图比例不一致时，让开发者选裁切还是留白。

## 窗口和设备形态

- 窗口尺寸：手机小屏、常规屏、大屏、横屏、平板、ChromeOS、外接显示器、分屏、多窗口、自由窗口都会改变可用宽高；布局分支优先基于实际 constraints、window size class 或项目封装，不基于设备型号。
- 折叠屏：折痕、铰链、半折叠姿态、双屏区域和展开/折叠切换会改变内容连续性；关键按钮、输入框、弹窗、底部栏不能跨不可用区域或被折痕切开。
- 方向切换：横竖屏切换后要验证 `rememberSaveable` 状态、Lazy 滚动位置、分页状态、输入焦点、弹窗和底部栏位置。
- 大屏布局：宽屏不要简单拉伸手机布局；必要时改为双栏、列表详情、导航 rail、网格列数增加或内容最大宽度居中。
- 小屏布局：320dp/360dp 宽下优先保证主任务可完成，低优先级标签、辅助按钮、说明文可折叠、换行或隐藏。

## WindowInsets 和系统区域

- edge-to-edge：状态栏、导航栏、手势区域、刘海/挖孔、透明系统栏要用 `WindowInsets` 明确处理；可点击元素必须避开系统栏和手势热区。
- Compose API：优先用项目既有 inset 封装；没有封装时再使用 `Modifier.windowInsetsPadding`、`statusBarsPadding`、`navigationBarsPadding`、`imePadding`、`safeDrawingPadding` 等。
- 底部固定元素：吸底按钮、底部操作栏、FAB、Snackbar、BottomSheet 要同时处理导航栏、手势区域和键盘。
- 顶部固定元素：沉浸式标题栏、吸顶 tab、搜索栏、banner 顶图要明确是绘制到状态栏下面，还是延伸到状态栏背后。
- 弹层：Dialog、Popup、DropdownMenu、Tooltip、引导浮层、BottomSheet 要处理锚点越界、小屏超高、横屏、键盘和系统栏遮挡。

## 键盘和输入

- 表单、搜索、评论、登录、弹窗输入、底部输入栏要验证键盘弹起后的可见区域、焦点滚动、提交按钮、错误提示、候选词栏和系统导航栏。
- 输入框要明确单行/多行、最大高度、内部滚动、计数器、清除按钮、密码可见按钮、helper text 和 error text 的占位策略。
- Compose 中不要只依赖初始布局；键盘出现会改变 insets，`imePadding`、滚动容器和焦点 bring-into-view 要配合使用。

## 字体、显示大小和文本系统

- 验证 font scale 1.15/1.3，触及通用组件时考虑更大字体；按钮、标签、输入框、顶部栏和底部栏不能裁字。
- 系统显示大小、粗体文本、不同系统字体、fallback font、emoji、数字等宽/非等宽都会影响测量；不要用固定高度假设文本永远一行。
- `Text` 的 `maxLines`、`overflow`、`softWrap`、`lineHeight`、`includeFontPadding` 相关项目约定要明确。
- 富文本、可点击 span、混排图标、价格、小数、倒计时、日期、单位要用最长合理样例验证。

## 本地化、RTL 和资源

- 本地化会影响字符串长度、断行、货币、日期、复数、单位和图片文字；按钮和标签尤其要预留文本扩展空间。
- RTL 下要检查返回箭头、方向图标、进度、列表滑动方向、Row 排列、padding start/end、文本对齐和动画方向是否需要镜像。
- 资源必须有默认兜底：`drawable`、`mipmap`、`values`、`font`、`night`、`sw<N>dp`、`land`、语言资源不能只存在限定目录。
- 带文字图片要确认是否需要本地化替换；如果不替换，至少保证布局不会因不同语言资源缺失而崩溃。

## 主题、颜色和渲染

- 深色模式、高对比度、省电模式、动态主题色、透明系统栏、品牌换肤会影响颜色、阴影、分割线和系统栏图标明暗。
- ldpi 到 xxxhdpi、不同 GPU/系统版本、圆角抗锯齿、阴影、1dp/1px 分割线、矢量 viewport、图片采样可能产生视觉偏差。
- Compose 中 `clip`、`background`、`border`、`shadow`、`drawBehind`、`graphicsLayer` 的顺序会影响圆角、阴影和裁剪结果；按设计稿顺序实现。

## 内容和状态

- 覆盖加载中、空态、错误态、无权限、未登录、审核中、禁用、过期、下架、删除、弱网、分页无更多、局部刷新失败。
- 数据极值包括 0、1、多条、超长列表、重复数据、缺字段、空字符串、emoji、换行符、富文本、超大数字、负数、极短/极长昵称、图片宽高缺失。
- 交互状态包括按下、选中、禁用、加载、倒计时、防重复点击、滑动、拖拽、吸顶、展开收起、动画中断、返回恢复。
- 可访问性要检查 TalkBack 焦点顺序、触控热区、contentDescription、合并朗读、禁用态可理解、颜色对比度和可缩放内容。

## Lazy、滚动和分页

- `LazyColumn`、`LazyRow`、`LazyVerticalGrid`、瀑布流、Pager、FlowRow、吸顶 header、下拉刷新、分页 footer 叠加时，要确认滚动范围、嵌套滚动和边缘留白。
- Lazy item 使用稳定 key；动态高度、图片加载、展开收起、局部刷新不能导致错误复用、状态串位或明显滚动跳动。
- 网格列数基于可用宽度和最小 item 宽度计算；`GridCells.Adaptive` 优先于固定列数，除非设计明确固定。
- 分页列表要覆盖首屏不足一屏、加载更多失败、无更多、刷新中、删除 item、插入 item、图片迟到后的高度变化。

## 媒体和裁剪

- 静态图、动图、视频封面、直播流、透明 PNG、长图、宽图、二维码、头像、带文字图片要分别确认比例、裁剪、圆角、背景和加载失败。
- 圆角卡片、阴影、描边、父子裁剪、列表首尾 item、瀑布流边缘要检查是否误裁、露底或阴影被裁。
- 图片加载前后容器尺寸必须稳定；占位图、失败图、真实图使用同一比例和裁剪策略，避免视觉跳动。

## 性能边界

- 动态测量、`onSizeChanged`、`SubcomposeLayout`、`TextMeasurer`、富文本、图片圆角/模糊、瀑布流和复杂约束不要为了适配引入明显卡顿。
- 能用父级 constraints 和标准布局表达时，不要在 composition 阶段读取屏幕宽度后手算所有尺寸。
- 避免在 Lazy item 中创建不稳定对象、重复执行重计算或因图片状态变化触发整屏重组。

## 适配验证防坑（实测结论）

- `Dialog`/`Popup` 是独立 window：外层 `CompositionLocalProvider(LocalDensity provides …, fontScale=…)` 不会传入弹窗内容（弹窗用自己的配置派生密度）。预览宿主里"xx-font 场景"对弹窗类组件可能根本没生效——用 `settings put system font_scale` 改系统字体做真实验证，测完恢复原值；用 pixel-diff（`ImageChops.difference` 的 bbox 只落在状态栏 = 场景没生效）确认测试路径有效。
- offset 与 padding 的测量语义差异是相对定位第一大坑：offset 不改变父容器对子项的测量结果，padding 会。涉及兄弟排布的位置用 padding/alignment，纯装饰微调用 offset。
- 文本放进硬宽度约束的盒子时，`maxLines=1` 会在约束边缘直接裁字（不是溢出显示）；单 token 内容要么给足空间，要么 TextAutoSize。
- 部位级核对：整图视觉检查容易漏"小字压在按钮上"级别的缺陷；按关键交界裁剪放大（PIL crop + resize）逐项确认，"金额每个字符完整""链接与按钮有明确间隙"这类可判定的问法比"布局正常吗"可靠。
