# Library 设计规则

## 0. 使用方式

1. 先判断库是否会长期维护、是否需要对外复用、是否会继续扩展。
2. 只要答案不是“不会”，就先按 `api + core + runtime` 思路拆分，再决定是否合并。
3. 只有在明确满足“短生命周期、低复用、低复杂度、不会增长”时，才允许退回单模块。
4. 不要先讨论目录名和模块名，先讨论职责边界和依赖边界。
5. 如果你已经开始担心未来怎么扩展，这本身就是需要分层的信号。
6. 本 skill 的使用方式是先看判定清单，再看标准模板，最后才看模块职责说明。

## 1. 适用范围

1. 本规则适用于 Android library、纯 JVM library、SDK、组件库及所有以 Maven 产物对外发布的库。
2. 本规则适用于新建库、重构库、拆分库、审查库和评估库边界的场景。
3. 本规则适用于判断 `api`、`core`、`runtime`、`common`、`base`、`ktx`、`ui`、`foundation`、`material`、`compiler`、`processor` 等后缀职责的场景。

## 2. 总则

1. 库的首要目标是长期可维护，而不是短期少建模块。
2. 凡是准备长期演进、多人协作、对外复用的库，必须优先采用分层设计。
3. 只要一个库存在稳定公共契约、可复用核心逻辑、运行时接入、编译期生成或宿主适配中的任意一项，就不得将全部代码写入同一个模块。
4. 分层的目的在于固定责任边界、降低依赖耦合、减少发布风险，不是为了追求模块数量。
5. 先确定分层，再落代码；不得先把代码写满，再用注释或命名补救结构混乱。

## 2.1 决策树

1. 如果这是一个一次性内部工具库，且不会被多个模块复用，可以考虑单模块。
2. 如果这个库会给外部调用方使用，但核心逻辑极少，可以采用 `api + runtime`。
3. 如果这个库存在稳定契约，同时存在可复用算法、映射、校验、加密、解析、资源适配等逻辑，必须采用 `api + core + runtime`。
4. 如果这个库还需要注解处理、代码生成或编译期校验，必须再拆出 `compiler` 或 `processor`。
5. 如果你对“该不该拆层”没有把握，默认按更细的方案处理，而不是压成一个模块。
6. 如果一个类或者一个目录里已经同时出现契约、实现和工具，说明边界已经失效，必须拆。

## 2.2 判定型清单

### 情况 A：这是一个一次性内部小工具库

1. 如果不会被多个模块复用，可以单模块。
2. 如果后续可能扩展成公共能力，不得单模块。
3. 如果已经出现契约和实现的分离需求，直接进入 `api + runtime`。

### 情况 B：这是一个对外提供能力但逻辑不复杂的库

1. 如果调用方只需要一个稳定入口，采用 `api + runtime`。
2. 如果运行时实现明显可能变化，仍然采用 `api + runtime`，但不得把核心逻辑继续堆进 `runtime`。
3. 如果开始出现算法、映射、校验、解析、加密、资源适配等能力，必须升级为 `api + core + runtime`。

### 情况 C：这是一个长期维护的基础库或组件库

1. 默认采用 `api + core + runtime`。
2. 不得把契约、核心逻辑、宿主接入写在一个模块里。
3. 不得以“当前还小”为理由拒绝拆层。
4. 不得以“以后再拆”为理由拖延拆层。

### 情况 D：这是一个需要编译期支持的库

1. 只要存在注解处理、代码生成、编译期校验需求，就必须增加 `compiler` 或 `processor`。
2. 编译期能力不得与运行时实现混写。
3. 编译期模块通常只接 `api` 和 `core`，不接运行时入口。

## 3. 默认结构

1. 长期维护的库，默认应优先采用 `api + core + runtime` 结构。
2. `api` 负责对外契约。
3. `core` 负责纯核心逻辑。
4. `runtime` 负责宿主接入与运行入口。
5. 若库极小且短期内不会扩展，可降级为 `api + runtime` 或单模块，但该降级必须基于明确判断，不能基于“图省事”。
6. 一旦库开始增长、被多个模块复用或出现多个实现路径，必须补足 `core` 层，不得继续把所有逻辑堆进 `runtime`。

## 4. 模块职责

### 4.1 `-api`

1. `api` 仅允许承载公共契约。
2. `api` 应仅包含接口、注解、常量、回调协议、稳定模型和最小必要抽象类型。
3. `api` 不得包含具体实现、初始化逻辑、资源读取、页面、数据库、网络请求或业务流程。
4. `api` 的职责是声明“怎么使用”，不得承担“怎么实现”。

### 4.2 `-core`

1. `core` 仅允许承载可复用的核心能力。
2. `core` 应优先放纯逻辑、算法、校验、序列化、加密、映射、通用工具等能力。
3. `core` 不得直接依赖 `runtime`。
4. `core` 应尽量保持无 Android UI 依赖。
5. 如果一个类同时包含协议、业务和宿主适配，禁止放入 `core`。

### 4.3 `-runtime`

1. `runtime` 仅允许承载运行时接入能力。
2. `runtime` 应负责初始化、资源读取、宿主接入、运行时服务装配、对外 Facade 等能力。
3. `runtime` 可以依赖 `api` 和 `core`。
4. `runtime` 不得反向承载公共契约。
5. `runtime` 不得演变为页面、数据库、工具、算法和配置的混合垃圾场。

### 4.4 `-common`

1. `common` 仅允许承载轻量共享代码。
2. `common` 适合放局部工具、共享常量、轻量扩展和内部辅助类型。
3. `common` 不得承载业务主流程。
4. 任何职责明确的代码，不得继续滞留在 `common`。

### 4.5 `-base`

1. `base` 仅允许承载基础抽象。
2. `base` 适合放抽象类、模板方法、通用父类和统一实现骨架。
3. `base` 仅在存在明确继承或实现关系时使用。
4. 没有明确抽象关系时，不得人为创建 `base`。

### 4.6 `-ktx`

1. `ktx` 仅允许承载 Kotlin 扩展能力。
2. `ktx` 适合放扩展函数、扩展属性和调用层语法糖。
3. `ktx` 不得承载业务逻辑。
4. `ktx` 不得被当作复杂逻辑的隐藏容器。

### 4.7 `-ui`

1. `ui` 仅允许承载 UI 基础能力。
2. `ui` 应放通用 UI 原语、基础控件、通用样式和交互基础设施。
3. `ui` 不得直接绑定具体业务页面。

### 4.8 `-foundation`

1. `foundation` 仅允许承载与具体设计系统无关的基础 UI 构建能力。
2. `foundation` 适合放布局原语、状态容器、手势、动画和排版基础。
3. `foundation` 不得退化为业务封装层。

### 4.9 `-material` / `-material3`

1. `material` 和 `material3` 仅允许承载设计系统实现。
2. 该层应提供主题、样式和对应设计规范组件。
3. 该层应依赖 `foundation` 或 `ui`，不得反向依赖业务层。

### 4.10 `-compiler` / `-processor`

1. `compiler` 和 `processor` 仅允许承载编译期处理能力。
2. 该层应负责注解处理、代码生成和编译期校验。
3. 该层不得承载运行时业务逻辑。
4. 该层通常不进入最终运行时依赖树。

## 5. 推荐结构选择

### 5.1 单模块

1. 仅在短生命周期、低复用、低复杂度且不会持续扩展的库中使用。
2. 只要库未来存在扩展预期、复用预期或多方协作预期，就不得继续保持单模块。
3. 代码量小不构成单模块的充分理由，职责会增长才是关键判断标准。
4. 单模块不是默认方案，只是最小兜底方案。
5. 只要你已经能列出三个以上不同职责，就不该继续单模块。
6. 单模块适合“确定不长大”的库，不适合“暂时还不大”的库。

### 5.2 `api + runtime`

1. 仅在库很小、核心逻辑极少、对外入口明确且短期内不会增长时使用。
2. 若后续出现算法、校验、映射、加密、解析等可复用逻辑，必须补出 `core`。
3. 如果调用方只需要一个稳定入口，但实现可能变化，这一方案优先于单模块。
4. 如果 `runtime` 开始膨胀，就必须回头补 `core`，不能继续堆。
5. 该方案适合入口型库，不适合基础能力库。

### 5.3 `api + core + runtime`

1. 这是长期维护库的默认首选结构。
2. 该结构应作为长期演进库的基础模板。
3. 该结构的价值在于把“契约”“核心逻辑”“运行时接入”拆开，而不是增加形式上的模块数量。
4. 只要库会持续演进，这一结构就应优先于所有“简单合并”的方案。
5. 这不是可选建议，而是长期维护库的默认解法。
6. 如果你无法快速判断一个类应该放在哪一层，说明这三个层的边界还不够清晰，但仍然应该保留这三个层，而不是合并回去。

### 5.4 含编译期能力

1. 当库存在注解处理、代码生成、编译期校验、元信息导出等需求时，必须单独引入 `compiler` 或 `processor`。
2. 编译期生成若能显著减少手写代码，应优先拆层，不得混入 `runtime`。
3. 编译期层一旦存在，就必须和运行时层分开思考，不能混成一个大模块。
4. 只要编译期部分会单独演进，就必须单独成层。

## 6. 依赖方向

1. `api` 不得依赖 `runtime`。
2. `core` 不得依赖 `runtime`。
3. `runtime` 可以依赖 `api` 与 `core`。
4. `compiler` 和 `processor` 可以依赖 `api` 与 `core`，但不得反向依赖运行时实现。
5. `ui`、`foundation`、`material*` 必须自底向上叠加，不得反向穿透。
6. 任一模块若同时依赖契约、核心和实现并形成回流，必须立即拆分。
7. 依赖方向属于硬约束，不属于建议项。
8. 任何一层如果开始向上层反向输出实现细节，说明边界失守。

## 7. 发布原则

1. 对外发布的 Maven 坐标必须稳定、语义明确、职责单一。
2. 仅将调用方必须感知的类型放入 `api`。
3. `implementation`、`compileOnly`、`runtimeOnly` 的使用必须与暴露边界一致。
4. 不得为了方便把运行时依赖通过 `api` 透出。
5. 不得让调用方猜测某个类型应该依赖哪个模块。
6. 发布结构越清晰，越能避免调用方把代码重新写回一个大模块。
7. 对外发布时，调用方应只需要看模块名就能判断是否需要依赖，不应再靠猜。

## 8. 强制判断

1. 一个库是否存在稳定公共契约。
2. 一个库是否存在可复用核心逻辑。
3. 一个库是否需要宿主运行时接入。
4. 一个库是否需要编译期生成或校验。
5. 一个库是否已经出现契约、核心、接入、工具混杂在同一模块中的趋势。
6. 如果今天不分层，三个月后是否会更难维护。
7. 调用方能否一眼判断应该依赖哪个模块、导入哪个包、调用哪个入口。
8. 如果这几个问题里有两个以上答案偏向“会更难”，就必须拆层，不得再拖。
9. 如果你已经不能用一句话说清每层职责，就说明结构还不够好。

## 9. 禁止事项

1. 禁止将 `common` 用作无边界杂项容器。
2. 禁止将 `runtime` 用作契约、业务、工具、页面的混合模块。
3. 禁止将 `core` 写成依赖 Android UI 或宿主入口的实现层。
4. 禁止让 `api` 混入实现细节。
5. 禁止为了“看起来专业”强行创建空的 `base`、`ktx`、`foundation`、`material3` 模块。
6. 禁止将一个简单库拆成过多 Maven 坐标而增加调用复杂度。
7. 禁止以“为了快”为理由把所有代码写进同一个模块。
8. 禁止让一个模块同时承担对外契约、核心逻辑、运行时接入和工具函数。
9. 禁止等库变大以后再补分层，通常代价更高。

## 10. 典型反面模式

1. `runtime` 内同时包含 `ApiService`、Repository、工具类、页面入口、配置常量和初始化逻辑。
2. `core` 内混入 Android UI、宿主生命周期和业务页面。
3. `api` 内同时包含接口、实现和业务流程。
4. 所有工具、常量、模型都堆进 `common`，最终无人知道职责边界。
5. 代码一开始全部写在一起，后续依赖注释和命名去修补结构失控。

## 11. 设计结论

1. 凡是作为长期维护库的项目，默认不得把所有代码写在一个模块里。
2. 应先用分层固定责任边界，再允许具体实现增长。
3. `api / core / runtime` 是结构底线，不是装饰命名。
4. 设计时宁可一开始多一层，也不要让代码后期堆成难拆的大块头。
5. 如果你想问“能不能不拆”，默认答案是不能，除非你能明确证明它是短生命周期、低复用、低复杂度。
6. 对长期库来说，分层是默认项，合并是例外项。
