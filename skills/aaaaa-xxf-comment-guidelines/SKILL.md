# 注释规范

## 强制触发

以下场景必须先读取并执行本规范，不能等用户显式要求“加注释”才处理：

- 新增或修改 Kotlin/Java 类、接口、枚举、注解、方法、构造函数、字段、属性、常量时。
- 新增、维护或重构公共 API、跨模块 API、Maven 发布库 API、demo/sample 对外用法时。
- 修改复杂私有方法、复杂分支、边界处理、线程切换、缓存、状态码、tag、key、路由名时。
- 做 Android 项目代码审查、交付自检、风险门禁时。

执行源码改动后必须回看本次 touched 文件：凡公开 API 或容易误用的成员缺少注释，都要在同一轮修改中补齐；确实不补时必须在最终说明里写明原因。

## 总原则

- 注释优先使用中文。
- 尽可能为每个公开类、接口、方法、构造函数、字段、属性补充中文注释。
- 对外暴露的 API 注释优先级最高，跨模块、跨仓库、被 Maven 消费方使用的代码必须优先补齐。
- 目标是让读代码的人不用猜意图；注释要解释“为什么这样做”，而不是重复“这行代码在做什么”。

## 优先级

1. 公开类、接口、枚举、注解
2. 公开方法、重写方法、构造函数
3. 公开字段、属性、常量
4. 复杂私有方法、复杂分支、边界处理
5. 关键局部变量和中间步骤

## 写法

- Kotlin 的类、方法、字段、属性注释优先使用文档注释。
- 类注释说明职责、适用场景、核心规则和边界。
- 方法注释说明输入、输出、副作用、核心流程、业务规则、线程/生命周期要求和边界。
- 字段和属性注释说明语义、默认值、单位、是否可空、何时更新。
- 复杂逻辑前允许加一到两行短注释，帮助读者理解分支意图。

## 核心流程、规则和边界

- 注释必须把核心流程、关键规则和边界条件写清楚，不能只写一句笼统结论或重复代码字面。
- 当注释包含两条及以上流程、规则或边界时，必须使用连续编号的点数表达，统一采用“1、2、3、4”格式；每一点只表达一个完整事项。
- 推荐按“1、核心流程；2、业务规则；3、异常或边界；4、线程、生命周期或副作用”的顺序组织，可按实际情况删减不适用项，但不能省略已存在的关键约束。
- 编号内容要说明触发条件、处理顺序、限制条件和结果影响；涉及默认值、空值、状态转换、重试、超时或线程切换时，必须明确写出。
- 单条简单说明可以不编号；只要涉及核心流程、规则或边界，就必须优先使用编号点数，避免用一整段混合描述。

示例：

```kotlin
/**
 * 处理分页请求并更新缓存。
 *
 * 1、先校验页码，页码小于 1 时直接返回空结果。
 * 2、优先读取未过期缓存，缓存未命中才发起网络请求。
 * 3、网络请求失败时不覆盖已有缓存，并向上层抛出异常。
 * 4、所有状态更新必须在主线程执行。
 */
```

## 要求

- 公开 API 默认补注释，不要因为“名字已经能看懂”就省略。
- 业务含义强、复用强、容易误用的成员必须加注释。
- 常量、状态码、tag、key、路由名、缓存名、线程切换点都优先补注释。
- 对外 skill 文档也要使用同样的中文注释思路，避免只写结论不写上下文。

## 不要这样写

- 不要写重复代码字面的注释。
- 不要用英文长段落代替中文说明，除非原始 API 名称或第三方协议必须保留英文。
- 不要在完全显而易见的单行逻辑上堆砌无意义注释。
- 不要把注释写成历史记录或个人感想。

## 触发场景

- 新增或修改类、方法、字段、属性时
- 重构公共 API 时
- 补齐对外文档时
- 审查代码注释密度是否足够时
